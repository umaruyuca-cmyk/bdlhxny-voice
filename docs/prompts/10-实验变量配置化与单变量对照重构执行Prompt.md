# 10 · 实验变量配置化与单变量对照重构执行 Prompt

用途：将下面代码块中的全部内容复制给其他 AI，让其把当前固定“三种 Agent × 四种上下文”的实验设计重构为“实验模板 + 可控配置 + 单变量对照”。本任务需要修改设计文档、数据库设计、后端运行计划、前端实验配置和不访问真实模型的自动化验证；不得运行真实 LLM、正式压缩实验、正式 Agent 对比或公告实例测试。

```text
你是 D:\bdlh-agent\bdlhxny-agent 仓库 `touchstone` 分支的开发执行。请基于当前真实代码和数据完成一次实验架构重构：取消把“裸 Tool Calling、LangGraph ReAct、完整工程模式”固定包装成三种核心 Agent 的设计，改为“统一 Agent 运行底座 + 独立实验变量 + 受控实验模板”。目标是让每次对照只改变一个主要变量，使工具选择、治理、上下文压缩、温度、轮次和工具缺失实验都能得出可解释结论。

不要把本项目改成聊天产品。本项目仍然只运行版本化固定问题和三个固定长 Session，不新增自由输入框，不允许请求覆盖问题正文、Mock、标准答案或评判条件。

一、任务结论和重构原则

1. 当前原生 Tool Calling 与 LangGraph `create_react_agent` 在相同模型、Prompt、工具和 Mock 条件下执行逻辑接近，差别主要是循环和状态由手写代码还是框架管理。当前没有充分使用 LangGraph 的持久化、人工中断、复杂分支或多 Agent 能力，因此不再把二者作为核心能力对照组。
2. “完整工程模式”同时改变工具装载、快路径、治理、上下文和输出检查，无法判断结果改善来自哪一项能力。新设计不得继续用一个 `full-system` 标签代表多个同时变化的能力。
3. Agent 运行方式必须拆成相互独立、可记录的配置字段。一次正式实验只能指定一个主要自变量，其余条件必须冻结。
4. 不允许自动生成所有配置的笛卡尔积。系统必须由实验模板明确生成有限变体，并在提交前显示运行总数。
5. 工具全部是版本化冻结 Mock；真实 LLM负责工具选择、参数生成、循环决策和最终回答。不得把最终回答替换成 Mock答案或固定字符串。
6. `expected_tools`、可接受路径、禁止行为、标准事实和评判规则只供评测器使用，不能进入模型输入、工具搜索结果、摘要提示或公开用例正文。
7. 默认工具范围是当前启用的完整公开 Mock 工具目录。`scene`、`scene_tag`、身份标签和用例类型不能在运行前偷偷缩小工具范围。
8. 治理中间件不负责替 LLM 选择工具，只负责在 LLM 已经提出调用后决定是否允许执行、如何记录和如何向模型返回拒绝原因。
9. 本次是实验架构重构，不是从零重写项目。保留并复用固定用例、三个长 Session、Mock fixture、后台任务、运行事件、数据库、上下文压缩、结果详情和公告发布基础。

四、新的核心概念

统一使用下面的普通开发术语，不生造名称：

1. **固定用例**：版本化问题、Mock版本和评判条件，不允许运行请求修改正文。
2. **长 Session**：压缩模块使用的完整历史，最新一条用户消息是当前输入。
3. **实验模板**：规定本次实验改变哪个变量、有哪些变体、哪些条件必须锁定。
4. **运行配置**：单次运行实际生效的模型、工具、上下文、治理和限制参数。
5. **固定条件**：同一批次全部变体必须相同的条件及其版本或哈希。
6. **实验变体**：只覆盖实验模板允许变化的字段。
7. **工具提供方式**：全量发送工具定义，或先搜索目录再加载候选工具。
8. **治理配置**：调用执行前后的权限、确认、参数、预算、输出和审计检查。
9. **工具排除项**：从同一全局目录中明确移除的工具，是专项实验变量，不是标准答案。

不得继续使用“完整工程模式更高级”“裸 Agent允许区间”“本题合理工具范围”等含糊表述。

实现要求：

1. 区分“请求值”和“实际生效值”。模型不支持某参数时，不得静默忽略后仍声称该参数已生效。
2. 建立模型能力校验。对不支持温度、`top_p`、推理强度、`seed`、并行工具调用或强制 `tool_choice`的模型，提交前返回普通语言错误，或由模板明确使用模型默认值并记录原因。

6. 配置冻结后生成规范化JSON和SHA-256。运行、结果详情和发布工件都保存配置版本、哈希和可公开摘要。

六、实验模板，不允许任意笛卡尔积

至少实现以下模板定义和运行计划生成器。模板可以由代码加版本化JSON/YAML保存，也可以存数据库，但必须有单一真源、版本和静态校验。

### 1. 工具提供方式实验

唯一自变量：`tool_delivery`

~~~text
变体A：all
变体B：search
~~~

固定模型、Prompt、治理、上下文、工具目录、排除项、Mock、最大轮次和重复次数。用于比较任务成功、工具选择、工具幻觉、搜索召回、Token、轮次和时长。

### 2. 治理中间件实验

唯一自变量：`governance_profile`

~~~text
变体A：off
变体B：standard
~~~

两组必须使用相同的原生 Tool Calling循环、全量工具定义、Prompt、Mock、温度和限制。中间件只能处理已提出的调用，不能缩小模型看到的工具。用于比较应拦截召回率、误拦截率、未授权执行、未确认写入、被拒绝后的恢复和审计完整度。

### 3. 上下文处理实验

唯一自变量：`context_strategy`

~~~text
full
recent-window
single-summary
budgeted
~~~

默认固定一种参考Agent配置，不再默认乘以三种 Agent形成12格。先生成并冻结四份上下文工件，用户可以只生成上下文，不自动运行Agent；选择运行后每种上下文默认一次。只有单独的“上下文与运行方式交叉专项模板”可以在少量代表Session上产生交叉组合，不能成为所有Session默认流程。

### 4. 温度稳定性实验

唯一自变量：`temperature_effective`

预设值可以是`0/0.1`、`0.3`、`0.7`，具体以模型能力为准。固定其他条件，每档重复3次或5次。不能把模型不支持的温度配置纳入结果。

### 5. Agent轮次实验

唯一自变量：`max_agent_steps`

使用受控值，例如3、4、5。固定最大工具数、模型和其他条件，记录完成率、截断率、工具数、Token和总时长。不能把“重复5次”误写成“Agent循环5轮”。

### 6. 工具缺失与降级实验

唯一自变量：`excluded_tools`的预设集合。

例如天气用例：

~~~text
变体A：不排除工具
变体B：排除weather工具，保留web搜索
变体C：同时排除weather和web搜索
~~~

评判必须根据本次实际可见工具判断：有天气工具时优先天气工具；天气工具缺失但搜索可见时允许搜索降级；两者都缺失时诚实说明限制是正确结果。不得仍按静态`expected_tools`把诚实回答判错。

### 7. Prompt或工具描述专项实验（保留扩展位）

允许以后比较系统Prompt版本、工具描述版本和Schema严格程度，但本次不要同时改变Prompt与其他主要变量。工具描述不得泄露“本题应该调用”。

所有模板必须声明：

- `template_id`和版本；
- 实验目的；
- 唯一主要自变量；
- 允许的变体；
- 强制固定字段；
- 允许的用例类型；
- 重复次数范围；
- 单次和整批上限；
- 结果页显示指标；
- 是否允许匿名用户使用。

运行计划生成器在创建任务前输出精确运行数。超过角色对应上限时拒绝提交，不允许页面通过重复点击绕过。

七、全量工具逻辑

1. `tool_delivery=all`时，从冻结的全局公开 Mock工具目录读取所有当前启用工具，应用显式`excluded_tools`后，按稳定顺序把完整名称、普通语言描述和JSON Schema发送给LLM。
2. `allowed_tools`旧字段如果保留，只能解释为本次批次的完整可见目录快照，不能解释为用例推荐的3～5个正确工具。
3. 不再根据`market/portfolio/research/general`等场景硬编码工具集。场景只用于筛选用例、报表分组或加载场景包，不能在标准全量工具实验中缩小目录。
4. 三个实验变体若工具范围不是自变量，必须收到相同顺序、相同内容、相同哈希的工具定义。
5. 运行工件记录工具目录版本、排除项、实际可见工具名、定义哈希和实际发送给模型的Schema Token数。

八、工具搜索逻辑

1. `tool_delivery=search`时，初始只给模型目录搜索工具和完成任务所必需的通用控制能力，不直接发送全部具体工具Schema。
2. 由LLM根据用户问题提出普通语言搜索条件，不能先由代码把问题分类成固定场景工具集。
3. `search_tools`只在应用排除项后的同一个全局目录中检索。被排除工具不能出现在搜索结果中，也不能被后续调用。
4. 初期优先实现可重复的名称、说明、关键词和PostgreSQL全文检索或内存等价检索；不要为了几十到几百个工具强制引入向量数据库。未来需要时保留接口，不在本任务引入新的向量服务。
5. 搜索返回候选工具的名称和简短说明；运行器在下一轮为候选工具加载完整Schema。不要用一个万能`invoke_tool(name,args)`绕过原生工具参数校验。
6. 具体工具未加载时，模型调用该名称应记录为`TOOL_NOT_VISIBLE`，不能由执行器偷偷执行；模型可以再次搜索后恢复。
7. 记录搜索查询、候选结果、排名、Top K、检索耗时、正确工具是否召回、加载后的工具定义哈希和Token。
8. 评测结果分开显示：
   - 检索错误：可接受工具没有进入候选集合；
   - 选择错误：可接受工具已经进入候选集合，但模型选择错误；
   - 调用错误：工具正确但参数、依赖或顺序错误。

九、治理中间件必须产生真实差异

将`governance_profile=standard`落实为可观察的执行控制，不要只记录日志：

1. 工具是否属于本次可见目录；
2. 身份和权限范围是否允许调用；
3. `side_effect`是否需要确认；
4. `requires_confirmation=true`时是否存在本次调用绑定的有效确认；
5. 参数是否通过JSON Schema和业务限制；
6. 工具调用总预算、单工具重复预算和Agent轮次预算；
7. Mock Observation的来源、时间、状态和不可信文本标记；
8. 最终回答的数字依据、敏感信息和禁止行为检查；
9. 每项检查的通过、拒绝、原因、耗时和审计事件。

`governance_profile=off`仍需保留最基本的程序正确性和沙箱边界，例如不能执行不存在的Python函数、不能访问真实外部服务、不能绕过Mock。关闭的是待评测治理策略，不是关闭系统安全。

为了让治理实验有效，至少准备只读正常、权限不足、需要确认的写入、参数非法、预算超限和工具结果注入等Mock用例。写工具只能模拟结果，不产生外部副作用。

十、上下文压缩调整

1. 保留三个版本化长Session，最新一条用户消息是当前批次输入；不恢复旧`ctx-*`长上下文普通用例。
2. “只压缩”和“压缩后运行Agent”继续拆开。页面加载、代码生成、服务启动和上下文生成完成后都不能自动运行Agent。
3. 四种上下文方式必须从同一Session版本和同一当前事件生成。生成后冻结内容、Token、耗时、保留项、遗漏项和哈希。
4. 默认上下文实验固定一种参考Agent运行配置。移除产品文档和默认页面中“所有Session都必须4×3”的硬性要求。
5. 可保留专项交叉模板，但必须显式选择、显示组合数量，并说明它研究的是变量交互，不把单次12格样本当作稳定性结论。
6. 上下文配置至少支持：Token预算、最近轮数、压缩目标Token、当前轮预留Token。强制约束、当前问题和必要引用不得被普通配置删除。
7. 压缩算法的评分公式、强制保留规则和评测gold仍由版本控制，不允许匿名用户直接编辑。

十一、参数开放分层

前端和API按权限区分，不得把所有内部字段暴露成任意表单。

### 匿名用户

- 只能选择允许公开运行的固定用例和实验模板；
- 使用模板规定的模型、Prompt、Mock和评判版本；
- 重复次数只允许3次或平台当前限制；
- 最大轮次只允许受控预设，建议3～5；
- 可以在允许的工具缺失模板中选择预设排除项，不能提交任意工具名；
- 任务后台执行，断开页面不停止；只能通过匿名身份读取自己的任务和结果；
- 结果不自动进入公告。

### 登录所有者

- 可以选择允许列表中的模型、温度、推理强度、最大输出、上下文预算、搜索Top K、最大轮次和重复次数；
- 可以创建自定义工具排除集合和治理专项实验；
- 可以查看请求值与实际生效值、完整内部运行记录；
- 可以审核并发布合规批次。

### 系统固定

- 问题正文和Session原文；
- Mock正文、fixture版本和工具Schema版本；
- gold、标准事实、可接受路径、禁止行为和评判规则；
- 密钥、安全硬边界、公开脱敏规则；
- 已冻结批次的配置和哈希。

十二、API和运行计划

创建统一的实验计划接口或等价服务，不再由页面分别拼接三种Agent和4×3数组。请求示例：

~~~json
{
  "template_id": "tool-delivery-comparison",
  "case_id": "cmp-weather-01",
  "template_parameters": {
    "repeat_count": 3
  },
  "advanced_overrides": {
    "temperature": 0.1,
    "max_agent_steps": 4
  }
}
~~~

后端必须：

1. 根据`case_id`读取正文、Mock和评判条件，拒绝请求中的`message/prompt/system_prompt/expected_tools/mock_result`；
2. 根据模板生成变体，不接受客户端直接上传任意变体数组；
3. 校验角色、模型能力、参数范围、工具目录和运行数量；
4. 冻结固定条件、每个变体配置和哈希；
5. 创建后台批次和运行；
6. 返回批次总数、预计上限、固定条件摘要和唯一自变量；
7. 支持查询进度、取消未开始任务和服务重启恢复；
8. 防止重复提交造成重复计费；
9. 保存每个阶段的排队、上下文、LLM、工具、治理、评判和总耗时。

旧接口保留兼容时，只能映射到明确的新模板。不能继续创建语义不清的`agent_mode=full-system`新正式批次。

十三、数据库设计和手动执行方案

在现有表基础上设计增量变更，不执行SQL。至少支持：

1. 实验模板及版本；
2. 批次的模板编号、唯一自变量、固定条件JSON和固定条件哈希；
3. 单次运行的完整配置JSON、配置版本和配置哈希；
4. 请求参数与实际生效参数；
5. 工具提供方式、目录版本、排除项、实际可见工具哈希；
6. 治理配置版本及各检查事件；
7. 上下文策略和冻结上下文工件引用；
8. 温度、推理强度、最大输出、最大轮次、最大工具数、重复编号；
9. 搜索查询、候选工具、排名和加载工具记录；
10. 历史`agent_mode`只读兼容和新实验定义标记。

核心检索字段可以规范化为列，完整不可变快照可以使用JSONB。不要为每个模型参数建立无法维护的独立表，也不要只存JSONB而失去常用筛选和约束。

在`db/postgresql/changes/`新增日期前缀增量脚本，同步更新`db/docs/01-数据库总体设计.md`和`db/README.md`。应用启动不得执行脚本。交付说明必须给出维护者手动执行顺序、前置条件、备份提示和只读核验SQL。

十四、评测调整

1. 评测器读取实际运行配置，不以旧`agent_mode`名称推断能力。
2. 工具选择评测支持多条可接受路径，区分必需、可选、替代、禁止和需要确认的调用。
3. 工具缺失实验使用可见性相关的判断规则，不能要求调用已排除工具。
4. 工具搜索实验区分检索召回、模型选择和参数执行三个阶段。
5. 治理实验至少计算应拦截召回率、误拦截率、未授权执行次数、未确认写入次数、拒绝后恢复率和审计完整率。
6. 温度和重复实验展示成功次数、分布和离散程度，不只显示平均总分。
7. 上下文实验展示原始Token、工作Token、压缩成本、构建耗时、强制项保留和最终任务结果。
8. 429、余额不足、模型不支持参数、工具服务配置错误和评判器失败归为无效运行，不混入Agent能力失败。
9. 代码规则负责结构、参数、调用事实、权限和数值来源；LLM语义判官如果以后接入，必须独立记录模型、Prompt、Token和结论依据。本任务不得调用真实LLM判官。

十五、页面调整

实验入口保留“对比用例”和“压缩用例”，但改变操作逻辑：

### 对比用例

1. 先选择固定用例；
2. 选择实验模板，而不是固定选择三种Agent；
3. 显示该模板的唯一变量、变体和锁定条件；

5. 登录所有者可展开高级设置；

### 压缩用例
```
