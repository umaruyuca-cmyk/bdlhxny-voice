# 12 · 实验结果与原始证据优先展示重构执行 Prompt

用途：将下面代码块中的全部内容复制给开发 Agent，用于把当前站点从“可发起实验、可试用、模块众多的平台”收敛为“以实验结果和原始证据为核心的完整系统展示”。本任务包含公开站信息架构重做、页面与文案重做、无用公开交互和前端代码清理，但不删除生成实验数据所需的引擎、数据、评测与发布能力。

```text
你是 D:\bdlh-agent\bdlhxny-agent 仓库的产品设计负责人和前端开发负责人。请基于当前真实代码与公开数据契约，完成一次“展示优先”的站点重构。

═══════════════════════════════════════════
一、唯一核心目标
═══════════════════════════════════════════

把当前系统改造成一个完整、可信、易读的 Agent 实验成果展示站。

访问者进入站点后，应当按以下顺序获得答案：

1. 这个系统解决什么问题；
2. 系统做了哪些正式实验；
3. 实验取得了什么结果；
4. 每个汇总数字由哪些单次运行支持；
5. 单次运行中 Agent 实际执行了哪些步骤；
6. 输入、工具调用、中间结果、最终输出和评测断言等原始证据是什么；
7. 测试逻辑和系统调用关系是什么。

本阶段最重要的是“实验结果”和“原始证据”的呈现，其次是完整说明系统执行逻辑和测试逻辑。当前不建设面向访客的试用产品，也不把“可复现实验”作为页面目标。

不要把本任务理解为简单换皮、增加一个结果页，或继续给现有所有模块各做一张入口卡。必须真正重组信息架构、删除重复内容、移除公开试用路径，并让结果与证据成为全站主线。

═══════════════════════════════════════════
三、新的信息架构
═══════════════════════════════════════════

公开站顶层导航收敛为五项，顺序不得改变：

1. `/`：系统总览
2. `/results/`：实验结果
3. `/evidence/`：原始证据
4. `/system/`：执行逻辑
5. `/methodology/`：测试逻辑

GitHub 可以作为普通文本链接放在页脚或系统页，不做主视觉 CTA。

不得继续把“公告、实验、我的测试、数据资产、文档”作为顶层主导航。不得继续按“上下文、评判、引擎、工具、用例、运维”等内部模块平铺十几个入口。旧内容按用户理解顺序合并进上述五个页面。

页面职责如下。

A. 系统总览 `/`

- 首屏用一句明确陈述说明这是“受控 Agent 实验与证据展示系统”，不是聊天产品或公开试用工具；
- 展示最新正式发布批次、实验数量、有效运行数、核心结果指标和证据覆盖情况；
- 展示一条端到端系统流程：固定任务 → 上下文构建 → Agent 规划与工具调用 → 治理检查 → 结果生成 → 评测 → 证据发布；
- 用简短段落说明实验结论，结论必须来自真实公开数据；
- 如果尚无正式发布批次，首屏明确显示“尚无正式实验结果”，同时保留系统结构说明，不用工具数、模板数或用例数伪装成实验成绩；
- 不出现“立即体验、开始测试、发起实验、运行 Agent、登录、我的测试”等按钮或入口。

B. 实验结果 `/results/`

- 这是全站第一核心页面；
- 默认展示最新正式批次，并允许通过轻量筛选切换批次、实验、变体、场景和状态；
- 依次展示：实验目的、唯一自变量、固定条件、样本规模、有效/无效运行、核心指标、变体对比、分场景结果、失败类型和代表性案例；
- 汇总指标必须显示分母、样本数、指标方向和口径，不能只放一个百分比；
- 每个汇总结果必须能下钻到支持它的运行证据集合；
- 成功与失败都展示，不能只挑系统获胜案例；
- 图表只用于清晰比较，优先使用朴素柱状图、分布图、趋势图和数据表，不做装饰性仪表盘；
- 无真实数据时使用统一空状态，不展示模拟图表或估算数字。

C. 原始证据 `/evidence/`

- 这是全站第二核心页面；
- 首页为证据索引，可按批次、实验、用例、变体、结果和失败原因筛选；
- 每条记录至少显示运行编号、用例、实验变体、状态、得分/断言结果、步骤数、耗时和发生时间；缺失字段显示“未记录”，不得推断；
- 单次运行详情必须形成一条连续证据链，按实际发生顺序展示：
  1. 运行身份与来源；
  2. 固定任务输入；
  3. 实际生效的运行配置；
  4. 上下文构建摘要；
  5. Agent 执行时间线；
  6. 每次工具调用的工具名、参数、状态、耗时和返回摘要；
  7. 中间工件或治理拦截；
  8. 最终输出；
  9. 评测断言、通过/失败项和失败原因；
  10. Token、总耗时、成本等遥测；
  11. 允许公开的原始 JSON。
- 展示的是可审计执行记录和“决策依据摘要”，不得声称展示模型内部完整思维链，也不得泄露系统提示词、密钥、私有账户数据、gold 标准答案或未脱敏工具原文；
- 原始 JSON 可以折叠查看，但本阶段不做下载、复现或重新运行按钮。

D. 执行逻辑 `/system/`

- 用一张主流程图说明一次 Agent 运行的完整链路；
- 对流程中的每一步说明：输入、执行模块、关键规则、输出、写入的证据；
- 说明 web、engine、data、PostgreSQL 和公开快照之间的关系与公私边界；
- 说明 Agent 循环、工具提供、治理中间件、上下文处理、评测器和发布校验分别负责什么；
- 使用普通工程语言，不堆砌源码类名，不把系统页写成部署教程；
- 页面中的流程节点能链接到一条真实证据示例时才提供链接。

E. 测试逻辑 `/methodology/`

- 清楚解释固定用例、实验模板、唯一自变量、固定条件、变体、有效运行、无效运行和评测断言；
- 列出当前实际存在的实验及其变量，不把规划项写成已完成；
- 说明样本选择、重复次数、对照关系、数据冻结、指标计算和失败归因；
- 说明哪些结果由确定性代码断言产生，哪些字段只是运行遥测；
- 公开必要测试逻辑即可，不建设环境安装、CLI、数据库初始化或一键复现教程；
- 评判指标定义只保留一份，其他页面引用它，不重复维护不同版本。

四、公开交互与功能边界
═══════════════════════════════════════════

必须移除公开站中的以下内容：

- 登录、退出和账号状态 UI；
- “我的测试”；
- 匿名测试；
- 实验模板选择与发起；
- 运行下一个样本；
- 重试、取消、发布等操作；
- 自由输入、参数编辑和任何会调用模型的公开控件；
- 以“试试看”为目的的上下文工作台、上下文 Demo；
- 复现命令、部署操作和数据库维护作为公开主内容；
- 与结果和证据无直接关系的路线图、内部运维说明、重复工具清单和重复系统介绍。

“不做试用按钮”不等于完全禁止浏览交互。允许保留且应正确实现：

- 页面导航；
- 结果筛选和排序；
- 展开/收起证据；
- 表格分页；
- 图表与证据之间的下钻；
- 复制运行编号或公开 JSON 的轻量操作。

这些浏览操作不得发起运行、修改数据或访问私有 API。

═══════════════════════════════════════════
五、视觉与内容设计原则
═══════════════════════════════════════════

1. 视觉定位是“研究报告 + 工程审计记录”，不是 SaaS 营销首页，也不是后台管理台。
2. 首屏先给结论和证据规模，再解释系统，不用口号、大面积渐变、发光效果或装饰性插图掩盖数据不足。
3. 页面层级稳定：结论 → 指标 → 对比 → 案例 → 原始证据 → 方法说明。
4. 数字、单位、样本数、状态和时间格式全站统一。
5. 成功、失败、无效、未运行和缺失数据使用固定且可访问的颜色与文字组合，不能只靠颜色区分。
6. 减少卡片数量。连续逻辑优先使用时间线，指标映射优先使用表格，系统关系优先使用流程图。
7. 中文为主，必要英文术语作为辅助标签，不使用大量无信息量的英文 eyebrow。
8. 桌面端优先保证宽表与证据时间线可读，移动端不得横向溢出或隐藏关键证据。
9. 所有结论必须能指向数据；没有数据的内容明确标注“未发布、未记录或设计说明”。

═══════════════════════════════════════════
六、代码与内容清理规则
═══════════════════════════════════════════

清理目标是减少公开展示层的重复和无效代码，不是删除底层实验系统。

必须保留：

- `engine/` 中生成运行与评测证据所需能力；
- `data/`、数据库设计与运行记录契约；
- `web/schema/showcase-data/`；
- 公开快照生成、脱敏校验和发布脚本；
- 正式结果与运行证据的数据结构；
- 与新五页信息架构直接相关的测试。

允许并要求清理：

- 被新信息架构替代的公开 HTML 页面；
- 仅服务于公开登录、试用、发起运行、我的测试和上下文工作台的前端 JS/CSS；
- 删除页面后不再使用的 CSS 选择器、图标、帮助文案和事件监听；
- 重复的导航、重复指标定义、重复架构说明；
- 指向已删除页面的测试、生成模板和重定向规则；
- 无实际数据来源的占位统计和纯展示假数据。

执行删除时必须遵循：

1. 删除文件前用 `rg` 检查全部引用；
2. 区分“公开前端调用代码”和“底层运行能力”，不能因为页面不再发起实验就删除实验执行、评测或发布链路；
3. 旧公开 URL 设置到最接近的新页面的明确重定向，避免死链；不保留重复页面壳；
4. 不保留大量注释掉的旧代码，不创建 `legacy/` 垃圾目录；历史由 Git 保存；
5. 不为追求测试通过而降低数据真实性、脱敏或公开契约断言；
6. 不执行 SQL，不调用真实 LLM，不创建或伪造正式实验数据，不 commit，不 push。

建议的旧路由迁移：

- `/showcase/*` → `/results/` 或对应 `/evidence/` 详情；
- `/experiment/*` → `/methodology/`；
- `/test/*` → `/evidence/`；
- `/context/*` → `/system/`、`/methodology/` 或对应结果筛选；
- `/judging/*` → `/methodology/`；
- `/engine/*` → `/system/`；
- `/ops/*`、`/assets/*`、`/tools/*`、`/cases/*`、`/about/*`、`/docs/*` → 根据实际内容迁移到五个新页面中的唯一位置。

不要机械把所有旧路由都跳到首页。

七、数据实现要求
═══════════════════════════════════════════

1. 公共页面只读取静态公开快照，不调用私有运行 API。
2. 继续以发布校验后的公开数据为唯一结果来源；匿名临时结果、调试运行和未审核批次不得混入正式指标。
3. 聚合数字必须由运行记录计算或来自同一批次报告，并可以追溯到运行 ID；不得在 HTML 中手写正式成绩。
4. 建立统一前端数据适配层，把 publication、batch report、run artifact 映射为页面视图，避免每个页面各自解析不同字段。
5. 正确处理：无发布批次、部分字段缺失、无效运行、失败运行、旧版本工件和公开字段被脱敏等情况。
6. 若当前公开 Schema 缺少证据页面必须字段，先以向后兼容方式扩展 Schema、发布脚本和测试，再使用该字段；不要让页面直接读取私有数据绕过发布白名单。
7. 原始证据展示必须通过公开字段白名单，任何敏感或内部字段默认不输出。

八、实施顺序
═══════════════════════════════════════════

阶段 1：审计与映射
- 输出旧路由/内容/代码到新五页的映射；

- 完成汇总到运行证据的下钻；
- 完成单次运行时间线和公开原始 JSON；
- 补齐必要 Schema、生成器、发布器与契约测试。

阶段 4：补齐系统与测试说明
- 完成 `/system/` 和 `/methodology/`；

阶段 5：清理与迁移
- 删除确认无用的公开页面、JS、CSS 和测试；

阶段 6：验证

- 运行视觉 smoke test 或 Playwright 检查桌面与移动端；
- 检查浏览公开页面时没有私有 API 请求、模型调用或控制台错误；
- 检查每个现存真实汇总指标是否可下钻到证据。

九、最终验收标准
═══════════════════════════════════════════

1. 顶层导航只有：系统总览、实验结果、原始证据、执行逻辑、测试逻辑。
2. 全站没有登录、运行、试用、我的测试、重试、发布或模型调用入口。
3. 首页首屏优先显示正式实验结论和证据状态，不以工具数、模板数或用例数冒充实验结果。
4. `/results/` 能展示真实批次、变体、样本数、指标、失败分布和代表性案例。
5. 每个汇总指标可下钻到组成该指标的单次运行。
6. `/evidence/` 能展示单次运行从输入到评测的完整公开证据链。
7. Agent 步骤展示为结构化审计轨迹，不泄露内部思维链、密钥、gold 或私有数据。
8. `/system/` 清楚写明一次运行中每个模块的输入、执行、输出和证据。
9. `/methodology/` 清楚写明实验变量、固定条件、样本、指标和无效运行口径。
10. 所有结果数字来自公开快照；无数据时明确空状态，不使用演示成绩。
11. 重复内容、无用公开页面和对应死代码已删除，没有注释掉的旧实现或空页面壳。
12. 旧链接有合理重定向，站内无死链，桌面和移动端均可读。
13. 发布白名单、脱敏、Schema 和数据真实性检查没有被削弱。
14. 自动化验证通过，且验证过程不调用真实 LLM、不执行 SQL、不创建正式实验实例。
```
