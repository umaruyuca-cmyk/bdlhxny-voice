# StockWise 历史版本档案 05：金融随身管家 v1.0～v2.1

> 版本性质：上一代产品需求基线；其安全和运行边界仍被 00 号统一生产架构继承  
> v1.0 形成日期：2026-08-08  
> v2.1 冻结日期：2026-08-09  
> 代表提交：`16312c8`、`42b0722`

## 1. 版本定位

这一版本将 StockWise 从固定股票分析工作流扩展为面向金融领域的通用对话式智能管家。

系统不再要求每个问题都包含股票代码或命中固定业务 Route，但仍通过外层 Runtime、Planner、Guardrails 和 Capability Gateway 保持可控执行。

## 2. 产品需求

必须支持：

- 普通金融知识问答；
- 单点行情和单一事实查询；
- 股票名称解析；
- 单只股票分析；
- 市场整体问题；
- 跨市场和宏观影响研究；
- 多轮上下文引用；
- 用户持仓与账户影响分析；
- 工具失败后的有限回答；
- 高风险请求的拒绝或确认。

用户问题示例：

```text
什么是市盈率？
600519 现在多少钱？
茅台现价？
美国非农数据对 A 股有什么影响？
我的持仓整体暴露在哪些风险上？
刚才提到的那只股票最近风险怎么样？
```

## 3. 核心原则

1. 没有股票代码不等于无法回答；
2. Agent 只能提出计划或动作，不能直接访问底层能力；
3. 工具调用、预算、权限和恢复由外层 Runtime 控制；
4. 金融计算保持确定性和可复现；
5. Checkpointer、分析历史和长期记忆分别管理；
6. 当前只提供只读分析和研究辅助；
7. 用户身份必须来自认证会话。

## 4. 三层执行架构

```text
第一层：执行模式选择
  ├─ DIRECT_RESPONSE
  ├─ SINGLE_CAPABILITY
  └─ AGENT_LOOP

第二层：Agent Loop
  → Planner
  → Executor
  → Guardrails
  → 有界重规划

第三层：确定性执行
  → Tool / Capability Gateway
  → Observation
  → AnalysisInput
  → Domain Analysis
  → AnalysisResult
```

## 5. 执行模式需求

### 5.1 DIRECT_RESPONSE

- 只回答稳定金融知识；
- 不调用外部工具；
- 不回答依赖实时市场数据的问题；
- 不根据未验证账户信息生成个性化建议。

### 5.2 SINGLE_CAPABILITY

- 适用于标的已经解析的单点数据或单一事实；
- 原则上执行一次统一 Capability；
- 快路径不满足条件时必须升级到 Agent Loop；
- 不允许通过快路径绕过权限和数据质量校验。

### 5.3 AGENT_LOOP

- 适用于名称解析、多实体、跨市场和复杂研究；
- Planner 先生成动态 TaskPlan；
- Executor 每次只选择当前可执行动作；
- 默认最多重规划两次；
- 必须受预算、白名单和 Guardrails 控制。

## 6. QueryIntent 边界

`QueryIntent` 负责表达：

- 用户目标；
- 股票、市场、账户等实体；
- 上下文引用；
- 已知约束；
- 缺失信息。

`QueryIntent` 不再直接等于执行路线。实际执行步骤由 Planner、Executor 和 Runtime 根据能力、权限和数据状态决定。

## 7. Planner 与 Executor

### Planner

- 生成结构化 TaskPlan；
- 声明任务依赖；
- 声明需要的能力类别；
- 不直接指定或执行原始 MCP Tool；
- 不绕过 Guardrails。

### Executor

- 从 TaskPlan 中选择可执行步骤；
- 每轮生成一个 AgentAction；
- 不能直接调用底层数据源；
- 执行结果必须回写标准化 Observation；
- 失败后根据明确规则重试、降级或重规划。

## 8. 四时点 Guardrails

安全与策略判断发生在四个时点：

1. Plan Guard：检查计划是否合法、只读且在授权范围内；
2. Action Guard：检查具体动作、能力和参数；
3. Data Guard：检查来源、质量、用户隔离和敏感信息；
4. Response Guard：检查限制披露、个性化结论和风险表达。

Tool Gateway 负责技术执行，Guardrails 负责策略判断，两者不能混为一体。

## 9. 身份、权限与只读边界

- 用户身份来自已认证会话或服务端令牌；
- 禁止直接信任请求体中的 `user_id`；
- 账户和持仓数据按用户隔离；
- Agent 不直接访问数据库；
- MCP 和 Java API 通过受控 Gateway 调用；
- 不下单、不调仓、不转账、不修改账户；
- 日志不得记录令牌和完整敏感账户信息。

## 10. 状态、历史与记忆

- `thread_id`：持续对话标识；
- `run_id`：一次执行标识；
- Checkpointer：保存 Graph 运行和恢复状态；
- Analysis History：保存结构化分析历史；
- Mem0：保存经筛选的长期用户偏好和事实。

三者不得互相替代。

## 11. Observation 与数据质量

- MCP、Java API、Web Search 等结果统一为 Observation；
- 记录来源、观察时间和数据时间；
- 区分成功、失败、空数据和不完整数据；
- 结果覆盖状态使用 `COMPLETE / PARTIAL / LIMITED`；
- 工具错误必须对用户可见，不得包装成确定结论。

## 12. API 与事件流

- 保持统一请求入口；
- 支持 SSE 事件；
- 支持 `thread_id / run_id`；
- 支持中断恢复；
- 事件 Schema 保持稳定；
- 内部状态不得直接暴露敏感用户数据。

## 13. 当前阶段不做

- Letta、Hermes、Phoenix 等新 Agent 平台；
- 任意动态加载第三方 Skill；
- Agent 直接调用原始 MCP；
- 交易、下单、调仓、撤单和转账；
- 把所有问题重新塞入固定股票 Route；
- 让 DIRECT_RESPONSE 回答实时数据问题。

## 14. 实施顺序

1. 修正主流程语义和三种执行模式；
2. 固化 Capability、Tool 和 Analysis 边界；
3. 完善多轮上下文、状态和记忆；
4. 实现复杂问题与有界 Agent Loop；
5. 完成身份、安全、数据质量和回归验收。

## 15. 对下一代架构的影响

深层认知与个人金融架构继续继承本版本的以下不可放宽约束：

- 服务端认证身份；
- 用户数据隔离；
- 外部金融操作只读；
- Agent 不直接访问原始工具；
- 四时点 Guardrails；
- 数据质量和限制披露；
- `thread_id / run_id` 分离；
- Checkpointer、历史、记忆和任务分别管理。

下一代架构主要改变的是顶层认知模型和金融领域组织方式，而不是放宽这些安全边界。
