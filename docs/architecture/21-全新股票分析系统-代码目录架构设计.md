## 1. 设计原则

本目录架构遵循五条原则，每条都对应设计文档的明确要求：

| 原则 | 来源 | 在目录中的体现 |
|---|---|---|
| **分层不混编**：编排 / 能力 / 计算 / 接入 各自独立 | 设计 §2.1–§2.3 | `graphs/` `agents/` `domain/` `api/` 顶层隔离 |
| **Domain Service 零框架依赖** | 设计 §13.8 | `domain/` 不 import LangChain / LangGraph |
| **动态路径 + 固定边界** | 设计 §2.4 | 边界（节点类型、状态、终态、预算）集中在 `models/` `runtime/budget.py` |
| **Observation 普适化** | 设计 §16 + 复核 P1-2 | 独立 `observation/` 包，所有子图调用 |
| **安全 / 运行守卫显式存在** | 复核 P0-1 / P0-2 / 缺失模块 | `budget_guard` `orchestrator` `auth/` `cache/` `ratelimit/` |

## 2. 分层依赖规则（防止架构腐化）

```text
依赖只能自上而下，禁止反向、禁止同层跨域绕行：

  api/  ──────────────────────────────── 接入层（HTTP / SSE）
    │
    ▼
  runtime/  ──────────────────────────── 应用承载层
    │
    ▼
  graphs/  ───────────────────────────── 编排层（LangGraph）
    │
    ▼
  agents/  nodes/  tools/  ───────────── 能力层
    │
    ▼
  domain/  ───────────────────────────── 计算层（不依赖任何上层）
    │
    ▼
  infrastructure/  ───────────────────── 基础设施层
    │
    ▼
  models/  observation/  ─────────────── 纯数据模型（无依赖，谁都能 import）

禁止规则：
  ✗ domain/ 不得 import graphs / agents / tools / langchain / langgraph
  ✗ infrastructure/ 不得 import graphs / agents（反向依赖）
  ✗ graphs 之间不得横向 import（root 不直接 import 子图内部节点，只引用子图构造器）
  ✓ 每层只能依赖它正下方一层 + models / observation
```

> 用 `import-linter` 或 `lint-imports` 在 CI 里强制执行这套规则（见 §7）。

## 4. 各层职责详解

### 4.1 接入层 `api/`

- **只做协议适配**：HTTP/SSE ↔ 内部调用，不含业务逻辑。
- `auth.py` + `auth/` 包补齐复核「缺失模块-认证」：解析身份、注入 `Principal`，组合数据强制走 `portfolio_acl`。
- `schemas.py` 与内部 `models/` 分离——避免外部 DTO 变动污染领域模型。

### 4.2 应用承载层 `runtime/`

- **不是编排框架**（设计 §2.3）：它只是「启动 Graph + 管理运行事项」。
- `orchestrator.py` 落地 **P0-2**：把 Root 的单选路由升级为「多目标编排计划执行」——接收 `targets + plan`，负责 fan-out（并行/串行）与 fan-in（合并）。
- `budget.py` + `graphs/*/budget_guard.py` 落地 **P0-1**：预算对象贯穿 run，内层 Agent 每步扣减，触顶强制 `STOP_LIMITED`。
- `errors.py` + `retry.py` 补齐「错误分类与重试策略」。

### 4.3 编排层 `graphs/`

- **按领域分子目录**，每个子图自包含（图定义 + 节点 + 该图专属逻辑如 `evaluate` / `budget_guard`）。
- `root/classify.py` 返回**目标集合 + 执行计划**（P0-2），而非单一 workflowType。
- `root/routing.py` 的条件边函数**纯代码**，读 State 返回有限状态集合（设计 §18.3）。
- 子图之间**不横向 import**，只由 `root_graph` 引用各子图构造器。

### 4.4 能力层 `nodes/` `agents/` `tools/`

- `nodes/` 按 **Agent 模式**（§3）分文件，每个节点能对号入座声明自己用哪种模式。
- `agents/base.py` 实现**单步 ReAct**（§8.4）：每次 `select_next_action` 只产出一个结构化动作，循环交给外层图——这是 P0-1 方案 A 的实现位置。
- `tools/registry.py` 是「固定边界」的落点：每个子图从这里取自己的 `allowed_tools`，Agent 不能越权。

### 4.5 计算层 `domain/`（核心不可变资产）

- **零框架依赖**（§13.8）：`domain/` 里不出现 `langchain` / `langgraph` import，保证换框架时计算/回测逻辑原样复用。
- 按领域分子包：`market` / `portfolio` / `risk` / `strategy` / `backtest`。
- `backtest/bias_checks.py` 落地 **P2-4**：把「前视偏差/生存者偏差」从一段 reminder 变成可断言的校验。

### 4.6 `observation/`（P1-2 的落点）

- 独立成包，所有子图的 normalize 节点都调用它——把 §16 的「普适原则」变成**唯一实现**，避免每个子图各写一套。
- `provenance.py` 集中管理来源/时间/版本，回测复权方式、数据源版本都在这里落字段。

### 4.7 基础设施层 `infrastructure/`

- 把所有「外部世界」（DB、Redis、数据源、模型、MCP、缓存、限流）隔离在此层。
- `data_providers/` **一个 provider 一个文件**，新增数据源不改上层。
- `model_providers/fallback.py` 补齐「模型降级链」。
- `cache/` + `ratelimit/` 补齐两个硬缺口：外部数据源限速场景必备。

### 4.8 `models/`（纯数据，全局共享）

- State、枚举、结构化结果全集中于此，**无任何业务 import**——任何层都能依赖它而不产生循环。

## 7. 关键工程配置（建议 Phase 0 一并建立）

### 7.1 依赖管理

- 用 `uv` + `pyproject.toml`（比 pip/poetry 快，锁文件可靠）。
- 依赖分组：`[project.dependencies]`（运行）+ `[project.optional-dependencies]` 的 `dev`（ruff/mypy/pytest）/ `data`（akshare/tushare）。

### 7.2 分层守护

`importlinter.toml`（核心节选）：

```toml
[importlinter]
root_package = "app"

[[importlinter.contracts]]
name = "Layered architecture"
type = "layers"
layers =
  "app.api",
  "app.runtime",
  "app.graphs",
  "app.agents | app.nodes | app.tools",
  "app.domain",
  "app.infrastructure",
  "app.models | app.observation"

[[importlinter.contracts]]
name = "Domain has no framework deps"
type = "forbidden"
source_modules = ["app.domain"]
forbidden_modules = ["langchain", "langgraph"]
```

### 7.3 质量门禁

- `ruff`（lint + format）+ `mypy --strict`（domain/ models/ 必须 strict）。
- `pytest` 分层：`unit`（快，无 IO）/ `graphs`（内存 checkpointer）/ `integration`（带 DB/Redis）。

## 8. 与设计 §21 推荐目录的差异说明

设计 §21 给的目录是对的，但偏粗。本文主要在三处加强：

| 维度 | 设计 §21 | 本文 | 理由 |
|---|---|---|---|
| **子图组织** | `graphs/*.py` 平铺 | `graphs/<domain>/` 子目录 | 每个子图有专属逻辑（evaluate/budget_guard），平铺会膨胀 |
| **复核修复点** | 未体现 | 显式落点（见 §5 对照表） | P0/P1 必须有文件归属，否则修订悬空 |
| **缺失模块** | 无 cache/ratelimit/auth | 独立包 | 这些是上线硬缺口，目录里没有就不会被建 |
| **分层守护** | 无 | `importlinter.toml` + §2 规则 | 防止 Layered 架构随 Phase 增多而腐化 |

## 9. 结论

这套目录架构的判断标准只有一条：**设计文档里每个组件、复核意见里每个修复点，都能在目录树里指到一个明确的文件**。如果指不到，就是设计落地有缺口——以此作为后续开发的验收基线。
