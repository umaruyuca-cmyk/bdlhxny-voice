## 0. 本文档要解决的问题

v2.x 设计基于 LangGraph 单一编排引擎，并已确立"数据/分析分离"的职责边界（MCP 取数、Skill 纯分析、stock-wrapper 退役）。在 v2.x 成果基础上，经对 Letta（MemGPT）、Mem0 的深入对比评估，本系统进一步确立：

- **主版本**：LangGraph + Mem0（主流稳态，可测可控，求职硬通货）
- **对比版本**：Letta（自主 agent 范式，用于架构对比研究）
- **共享层**：工具 / 计算 / 数据 完全独立，两个 runtime 等价调用

本文档定义这套「双 Runtime 平行 + 共享层独立 + Mem0 记忆层」的最终架构，并**完整继承** v2.x 的以下设计成果（详见相应章节）：

- 数据/分析分离：MCP 只取数，Skill 纯分析，stock-wrapper 退役（§3、§7）
- MCP 数据域风险分层：push2 系高危 / datacenter 低危（§9，**2026-08-06 实测校准**）
- akshare-one 历史K线 indicators_list 默认 null，不传即得纯 OHLCV（§9）
- 运行预算按 analysis_type 分档（§11）
- 同源失效逃生阀：如实标记"已知不可用"，不编造（§11）

> 注：v2.x 的"两个 MCP 同源、必须接第三方异构备份"判断，已被 §9.0 实测修正——akshare-one 内部的 `source=xueqiu`（实时）和 `source=sina`（K线）即为可用异构备份。

## 1. 核心架构决策

| 决策项 | 结论 | 理由 |
|---|---|---|
| 编排引擎（主版本） | **LangGraph** | agent 求职市场硬通货，流程确定性可测 |
| 记忆层（主版本） | **Mem0**（仅首尾读写） | 黑箱可控，局限在记忆子系统，不污染主流程 |
| 编排引擎（对比版本） | **Letta** | 自主 agent 范式，体现架构深度，面试有故事 |
| 记忆层（对比版本） | **Letta 自带**（core + archival） | 与 Letta 一体，不另用 Mem0 |
| 工具层形态 | **独立包 + 统一 ToolRegistry** | 解耦编排引擎，未来换框架零成本 |
| 确定性计算 | **domain/ 零框架依赖** | 两版共享，保证回测/风险可复现 |
| 目录组织 | **runtimes/ 统一层** | langgraph/ 和 letta/ 平级，意图清晰 |

### 1.1 关键原则：黑箱边界

本架构的核心设计哲学是「**把黑箱关进笼子**」：

```
确定性的东西（回测/风险/计算）→ domain/ 做成硬工具，agent 管不到内部
灵活的东西（研究/对话/记忆）  → runtime 层，允许 LLM 自主决策
```

无论 LangGraph 版还是 Letta 版，**确定性计算的边界都不变**——这是系统可信度的根基。

## 3. 各层职责

### 3.1 API 层 (api/)

- HTTP/SSE 入口，接收用户请求
- 按 `runtime` 配置路由到 langgraph 或 letta 实现
- 将 runtime 的输出转为 SSE 事件流
- **不含业务逻辑**

### 3.2 Runtime 层 (runtimes/) — 可替换编排引擎

这是本架构的核心抽象。两个 runtime 实现**同一套对外契约**（定义在 `runtimes/shared/`），但内部实现完全不同。

#### 3.2.1 LangGraph 版 (runtimes/langgraph/)

| 子目录 | 职责 |
|---|---|
| `graphs/` | StateGraph 定义、子图、条件边 |
| `agents/` | ReAct agent 逻辑（自写循环，每步一个结构化动作） |
| `nodes/` | 各类节点（CODE / STRUCTURED_LLM / TOOL_ONLY） |
| `context/` | **ContextBuilder**：每轮组装完整上下文喂给模型 |

**记忆读写时机（仅首尾）**：
```
对话开始 → memory.search() 召回记忆 → 注入 context
对话进行 → agent 跑 ReAct 循环（不碰记忆）
对话结束 → memory.add() 沉淀本轮要点
```

#### 3.2.2 Letta 版 (runtimes/letta/) — 后续平行实现

| 特性 | 说明 |
|---|---|
| 编排 | Letta agent 自主跑 loop（LLM 决定调工具/何时停） |
| 记忆 | Letta 自带 core memory（画像）+ archival memory（向量） |
| 上下文 | Letta 自动组装（不需 ContextBuilder） |
| 工具 | 共享同一套 ToolRegistry |

**与 LangGraph 版的根本差异**：Letta 版「记忆 + 上下文 + 编排」三位一体由 agent 自主完成，是「黑箱贯穿主流程」的范式；LangGraph 版这三者由代码显式控制，是「黑箱关在记忆层」的范式。

#### 3.2.3 共享契约 (runtimes/shared/)

定义两个 runtime 都要遵守的接口契约：
- runtime 输入/输出 Schema
- 事件类型定义
- 与工具层/记忆层/计算层的交互协议

### 3.3 记忆层 (memory/) — 仅服务 LangGraph 版

| 文件 | 职责 |
|---|---|
| `base.py` | 统一抽象：`search(query, user_id)` / `add(content, user_id)` / `get_profile(user_id)` |
| `mem0/` | Mem0 实现（调 Mem0 的 add/search） |

**为什么 Letta 版不走此层**：Letta 的记忆是 agent 内部自管的（LLM 通过 function call 读写 core/archival），你的代码不需要插手。硬要走抽象层反而多此一举。

### 3.4 工具层 (tools/ + integrations/mcp/)

**独立包 + 统一 ToolRegistry**，是本架构「解耦」的关键：

```python
# ToolRegistry：两个 runtime 都通过它取工具，工具实现与编排引擎无关
class ToolRegistry:
    def get(self, name: str) -> Tool: ...
    def all_tools(self) -> list[Tool]: ...
    def for_agent(self, allowed: list[str]) -> list[Tool]: ...
```

| 工具来源 | 位置 | 说明 |
|---|---|---|
| 自研（Domain 封装） | `tools/` | 行情/回测/风险等，内部调 domain/ |
| MCP 服务 | `integrations/mcp/` | akshare-one-mcp、cn-financial-mcp |
| Skill | `skills/` | StockWise Skill 纯分析服务（见 §3.7） |

**工具层完全不依赖 runtime**——这是未来换 Letta 零成本的基础。

### 3.5 确定性计算 (domain/) — 零框架依赖

- 不 import LangGraph / LangChain / Letta / Mem0
- 纯 Python 确定性逻辑：技术指标、回测引擎、风险计算
- **两版共享，保证回测结果可复现**
- 被工具层封装为 Tool，agent/runtime 调用但不改其内部

### 3.6 基础设施 (persistence/ + integrations/)

| 设施 | 用途 |
|---|---|
| PG | 业务数据、会话、审计、user_profile |
| pgvector | 向量存储（Mem0 archival / 历史研究检索） |
| Redis | 热层对话缓存、限流 |
| DeepSeek | 大模型推理 |
| Qwen3-Embedding | 向量化（Mem0 / 检索用） |

### 3.7 StockWise Skill 纯分析服务（继承自 v2.x）

StockWise Skill 是独立 Node HTTP 服务，承担**纯领域分析**，不是查询服务，也不是主 Agent。`stock-wrapper` 已退役——代码保留仅作离线回归测试，不进运行时，不作为数据备份源（见 §9 同源风险）。

```text
Runtime（LangGraph/Letta）组装 AnalysisInput
  ↓
SkillAdapter
  ↓
Node StockWise Skill（纯计算，断网也能跑）
  ↓
AnalysisResult
```

生产接口只保留：

```text
GET  /health
GET  /ready
POST /api/v2/analyze
```

Skill 禁止：查询 MCP / Java / 数据库 / 行情接口；按股票代码自行补数；内部启动 ReAct；决定下一步工具。

**AnalysisInput 契约**（由 runtime 组装，喂给 Skill）：

```python
class AnalysisInput(BaseModel):
    analysis_id: str
    analysis_type: str
    instrument: dict
    realtime_quote: dict | None
    historical_prices: list
    financial_data: dict | None
    valuation_data: dict | None
    industry_context: dict | None
    news_context: list
    portfolio_context: dict | None
    overseas_context: dict | None   # 外围面，MCP 不覆盖，来源待定
    data_quality: dict
    provenance: list
    methodology_version: str
```

**AnalysisResult 契约**（Skill 产出）：

```python
class AnalysisResult(BaseModel):
    analysis_id: str
    status: str            # SUCCESS / PARTIAL / LIMITED / FAILED
    facts: list
    calculated_indicators: dict
    signals: list
    risk_flags: list
    conclusions: list
    limitations: list
    provenance: list
    methodology_version: str
```

计算责任（MCP 返原始数据，Skill/Domain 负责计算）：

```text
OHLCV
  → MA / EMA / MACD / RSI / ATR
  → 波动率 / 最大回撤 / 支撑阻力
  → 技术信号 / 风险标记 / 分析结论
```

必须记录指标参数、复权方式、时间范围、算法版本，并防止未来函数。MCP 预计算指标最多用于校验，不作为默认最终结论。

> **Skill 服务化改造（强制前置）**：现有 Node skill 的 `src/data/*` 反向依赖 `src/analysis/*`，需切断这些依赖、移除 data 层所有 HTTP 取数实现，新增 `/api/v2/analyze` 纯计算端点。验收：断网状态下喂入固定 AnalysisInput 仍能产出结构完整的 AnalysisResult。详见 §10 Phase 0.5。

## 4. 两个版本的对比（核心设计点）

这是本架构最有价值的部分——**一个系统，两种范式，可对比可切换**。

| 维度 | LangGraph 版（主） | Letta 版（对比） |
|---|---|---|
| **编排** | LangGraph 画图，条件边/子图 | Letta agent loop，LLM 自主 |
| **记忆管理** | Mem0 显式调（代码控制） | Letta 自带（agent 自主） |
| **上下文组装** | ContextBuilder（手写，可测） | Letta 自动（黑箱） |
| **工具调用** | 共享 ToolRegistry | 共享 ToolRegistry |
| **计算确定性** | 共享 domain/ | 共享 domain/ |
| **黑箱位置** | 仅记忆子系统 | 贯穿主流程 |
| **可测试性** | 高（流程确定性） | 低（LLM 决定路径） |
| **开发量** | 大（画图 + ContextBuilder） | 小（配置为主） |
| **求职定位** | 主流栈硬通货 | 前沿范式亮点 |

### 4.1 为什么做两个版本

1. **求职展示**：主版本用主流栈（LangGraph+Mem0）保证 HR 认；对比版本（Letta）体现架构深度，面试有故事
2. **架构研究**：通过同一套工具/计算层，对比两种 agent 范式的实际差异
3. **风险对冲**：若 Letta 范式验证成功，可平滑切换为主版本；若不成功，主版本不受影响

## 5. Mem0 记忆设计（主版本）

### 5.1 读写边界（仅首尾）

```
对话开始（LangGraph Root Graph 的 load 节点）:
  profile = memory.get_profile(user_id)         # 结构化画像
  recalled = memory.search(user_input, user_id) # 语义召回
  → 注入 context

对话进行（agent ReAct 循环）:
  不碰 memory（保证流程确定性）

对话结束（Root Graph 的 persist 节点）:
  memory.add(本轮对话摘要 + 抽取要点, user_id)  # 沉淀
```

### 5.2 记忆内容分层

| 层 | 存什么 | 形态 | 来源 |
|---|---|---|---|
| 结构化画像 | 风险偏好、偏好板块、禁忌标的 | PG 表字段 | LLM 定期归纳 |
| 语义记忆 | 历史研究结论、用户观点、知识片段 | Mem0（pgvector） | 对话结束时 Mem0.add |
| 热层对话 | 最近 N 轮原文 | Redis | 实时写入 |

### 5.3 为什么用 Mem0 而非自己向量化

- Mem0 多做了「LLM 抽取要点 + 去重更新 + 重排」三件事，记忆质量优于裸向量化
- 这些逻辑自己调 prompt 成本高，Mem0 开箱即用
- Mem0 的黑箱局限在记忆质量（抽准不准），不影响主流程确定性——可接受

### 5.4 工程约束（Phase 0 接入时必须明确）

Mem0 不是零成本接入，它内部会调 LLM 做抽取/去重/重排，带来额外开销和故障面：

| 约束项 | 要求 |
|---|---|
| **Mem0 内部 LLM** | 显式配置为 DeepSeek（与主链路同模型），不得使用 Mem0 默认的 OpenAI；通过 Mem0 的 `llm` 参数注入 |
| **Embedding** | 显式配置为 Qwen3-Embedding（与 §3.6 一致），不得走默认 |
| **成本上限** | Mem0.add 单次调用内部 LLM 轮数需有上限，避免长对话抽取失控；建议配置 Mem0 的 token 预算参数 |
| **失败降级** | Mem0 不可用时，记忆层降级为"无记忆继续跑"——`memory.search` 失败返回空、`memory.add` 失败仅记录日志不阻塞主流程。**记忆是增强项，不是关键路径，挂了不能拖垮分析流程** |
| **延迟计入** | load 节点的 `search` 和 persist 节点的 `add` 耗时计入 §10.1 的总请求预算 |
| **可观测** | Mem0 每次调用记录：操作类型、user_id、耗时、是否命中降级、内部 LLM token 消耗 |

## 6. ContextBuilder 设计（LangGraph 版专属）

LangGraph 版每轮调用大模型前，由 `runtimes/langgraph/context/` 组装完整上下文：

```text
① System Prompt     固定（你写死）
② 用户画像          来自 PG 结构化表（确定性）
③ 工具清单          来自 ToolRegistry（确定性）
④ 近期对话历史      来自 PG/Redis（确定性，带截断）
⑤ 召回的相关记忆    来自 Mem0（语义，带容差）
⑥ 本轮已取数据      工具调用结果（本轮）
⑦ 用户当前输入      HTTP 请求体
```

7 块中 6 块确定性，仅 ⑤ 是语义召回（不准则只影响「是否贴合历史」，不影响计算正确性）。

**这是 LangGraph 版「黑箱可控」的体现**——每块都能单元测试。

## 9. 数据源接入（MCP）

两个金融 MCP 服务已云端部署，作为工具层的数据来源：

| MCP 服务 | 地址 | 工具数 | 定位 |
|---|---|---|---|
| akshare-one-mcp | `http://118.25.178.86:8083/mcp` | 9 | 补充（新闻/内部交易） |
| cn-financial-mcp | `http://118.25.178.86:8000/sse` | 42 | 主数据源（A股全） |

接入方式：通过 `integrations/mcp/` 适配为 ToolRegistry 中的工具，两个 runtime 等价调用。

> ⚠ **传输协议不同，必须分别配置**：cn-financial 用 SSE（`:8000/sse`，2 元组解包），akshare-one 用 Streamable HTTP（`:8083/mcp`，2 元组解包）。客户端调用代码不能假设统一接口。

### 9.0 实测可用性结论（2026-08-06 校准）

push2 系域名（实时行情/历史K线）的 eastmoney 源在云端**仍被风控**（`RemoteDisconnected`），但 **akshare-one 内部的异构 source（xueqiu/sina）可用**，构成真正的异构备份。完整验证矩阵：

| 能力 | cn-financial（默认源） | akshare-one（eastmoney） | akshare-one（xueqiu/sina） |
|---|---|---|---|
| 实时行情 | ✅ 18.6s（慢，内部已降级） | ❌ 风控 | ✅ **xueqiu 0.6s** |
| 历史 K 线 | ✅ 0.8s（内部已降级） | ❌ 风控 | ✅ **sina 0.6s** |
| 三大报表 | ✅ 5-6s（中文 key，亿元） | ✅ 0.7-1.2s（英文 key，元，更快） | — |
| 北向资金 | ✅ 0.9s | — | — |
| 行业板块 | ✅ 5.6s | — | — |
| 个股资金流 | ❌（服务端吞错，见 9.4） | — | — |
| 市场总览 | ❌（服务端吞错，见 9.4） | — | — |
| 新闻 | ✅ 0.1s | ✅ 0.1s | — |

**核心结论**：v2.x 关于"同源不构成备份、需接第三方"的判断**已被实测修正**——akshare-one 的 `source=xueqiu`（实时）和 `source=sina`（K线）就是可用的异构备份，无需外接第三方。

### 9.1 统一能力与路由

Agent 只看到统一能力名，不直接看到两个 MCP 的原始工具名：

```text
market.resolve_instrument
market.get_realtime_quote
market.get_historical_prices
market.get_financial_statements
market.get_valuation
market.get_industry_context
market.get_money_flow
market.get_news
```

> 交易日历**不作 MCP 能力**。两个 MCP 均无真正交易日历工具。由 `domain/` 层用 `exchange_calendars` 本地确定性计算。

路由表（**2026-08-06 实测校准版**，依据 §9.0 验证矩阵）：

| 统一能力 | 首选 | 备选 | 实测备注 |
|---|---|---|---|
| 标的搜索 | `cn-financial-mcp` search_stock | — | 低风险 |
| 实时行情 | `akshare-one` **source=xueqiu** | `cn-financial` get_realtime_quote（慢 18s） | eastmoney 系被风控；xueqiu 0.6s 可用 |
| 原始历史 K 线 | `cn-financial` get_historical_price（0.8s） | `akshare-one` **source=sina**（0.6s） | cn-financial 内部已降级；akshare-one 必须传 sina |
| 财务报表 | `cn-financial`（中文 key，亿元） | `akshare-one`（英文 key，元，更快） | 两者均走 datacenter，稳定；按消费方字段需求选 |
| 估值、行业 | `cn-financial` | — | datacenter 系，稳定 |
| 个股资金流 | `cn-financial` get_money_flow | — | ⚠ 实测服务端吞错（见 9.4），接入时须处理 |
| 市场总览 | `cn-financial` get_market_overview | — | ⚠ 实测服务端吞错（见 9.4），接入时须处理 |
| 新闻和公告 | `cn-financial` get_stock_news | `akshare-one` get_news_data | 两者均可用，cn-financial 字段更全 |

### 9.2 数据域风险分层

| 数据域 | 底层接口域名 | 风险等级 | 说明 |
|---|---|---|---|
| 财务报表、北向资金、宏观 | `datacenter-web.eastmoney.com` | 低 | 稳定，几乎不被风控 |
| 实时行情 | `push2.eastmoney.com` / `82.push2` | 高 | 易被 TLS 指纹/IP 段风控 |
| 历史 K 线 | `push2his.eastmoney.com` | 高 | 同上，且存在间歇性失败 |
| 板块、个股资金流 | `17.push2.eastmoney.com` | 高 | 同上 |

### 9.3 强制约束

1. **两个 MCP 连续失败时不得调用 Skill 补查**。runtime 必须返回结构化失败或 `LIMITED`。`stock-wrapper` 和旧 `/api/v1/*` 不作备份源（已退役）。**异构备份通过 akshare-one 的 `source` 参数实现**（xueqiu/sina，见 §9.0），无需外接第三方——此结论已由 2026-08-06 实测确认，修正了 v2.x"必须接第三方"的预判。
2. **两个 MCP 不能同时作为同一字段的并行默认源**。仅在数据校验或冲突分析场景下才主动调第二源。
3. **`akshare-one-mcp` 的历史 K 线不是纯原始数据**。其 `get_hist_data` 的 `indicators_list` 参数（SMA/MACD/RSI/BOLL 等）默认 null——**调用时不传该参数即得纯 OHLCV**；若误传则返回带预计算指标的数据，此时预计算指标最多作校验，不作默认结论（与 §3.7 计算责任一致）。
4. **两个 MCP 的参数 schema 不同，MarketDataGateway 必须分别适配**：
   - akshare-one 用 `interval`（day/week/month）+ `interval_multiplier` + `source`，**不是** `period`；
   - cn-financial 用 `period`（daily/weekly/monthly）+ `start_date`/`end_date`；
   - 统一能力层（§9.1）做参数翻译，不让 Agent 感知差异。
5. **cn-financial 的部分工具会把数据源失败包成正常响应**（`{"error": true, "message": "..."}`），MCP 协议层 `isError=false`。**Observation 标准化层（`observations/normalizer.py`）必须解析响应体里的 `error` 字段**，将其识别为失败并触发降级，不能只依赖 MCP 协议的 isError 标志。已确认 `get_money_flow`、`get_market_overview` 存在此问题。

## 10. 运行预算、降级与逃生阀（继承自 v2.x）

### 10.1 运行预算（按 analysis_type 分档）

ReAct 仅用于市场数据获取子图，不进入 Skill。预算按 `analysis_type` 分档（云端 MCP 调用需叠加往返延迟）：

| analysis_type | ReAct 轮数上限 | Tool 调用上限 | 子图预算 | 总请求预算 |
|---|---|---|---|---|
| `market_snapshot` | 2 | 3 | 25s | 40s |
| `technical` | 4 | 5 | 45s | 70s |
| `fundamental` | 5 | 7 | 55s | 90s |
| `valuation` | 4 | 5 | 45s | 70s |
| `portfolio_impact` | 6 | 8 | 60s | 100s |
| `comprehensive` | 10 | 14 | 150s | 240s |

公共约束：单轮模型决策 10s；单个 MCP Tool 20s（含云端 RTT）；单个 Java Tool 10s；单次 Skill 调用 60s；主源失败后最多切换 1 次同源备用源；财报分页超时应支持续传而非整体失败。

`market_snapshot` 走快路径（确定性规划，不经 ReAct），仅 `comprehensive` 才进完整 ReAct。超出预算必须停止并输出 `LIMITED`。

### 10.2 降级策略

- 非关键数据缺失：继续并标记 `PARTIAL`；
- 关键数据缺失：输出 `LIMITED`；
- 外围面（海外指数）缺失：两个 MCP 均不覆盖，标记 `PARTIAL`，在 limitations 说明，不得编造；
- 主 MCP 失败：按 §9.1 路由切换备用 MCP；
- 两个 MCP 都失败（同源失效）：触发逃生阀（§10.3）；
- Skill 失败：有限重试或输出结构化失败；
- 超出预算：停止执行并输出缺失项。

### 10.3 逃生阀（同源失效处置）

两个 MCP 同源，对同一数据域（尤其 push2 系的实时行情、历史K线）可能同时失效。此时：

1. 将该数据域标记为"**已知不可用**"，写入本次运行的 `data_quality`；
2. 在 `AnalysisResult.limitations` 如实说明"行情数据当前因数据源问题不可获取，以下分析基于截至 X 时的数据"；
3. 不得调用 Skill、stock-wrapper 或旧 `/api/v1/*` 补查，不得编造；
4. Phase 0 实测验证若发现某数据域长期不可用，应据此评估是否接入独立的第三方市场数据服务作为真正异构备份——**是否接入由实测数据决定，不在未验证前预设**。

## 13. 补充规格（从 v2.2 迁移）

> 本节内容从被取代的 `21-…统一架构设计.md`（v2.2）迁移，在 v3.x 双 runtime 架构下仍然有效。

### 13.1 系统目标与非目标

系统面向完整的股票研究和交易辅助场景，支持：

- 标的识别和市场数据查询；
- 实时行情和历史行情分析；
- 技术面、基本面和估值分析；
- 行业、板块、资金流向和新闻分析；
- 用户持仓和账户影响分析；
- 策略设计和回测；
- 用户确认后的知识沉淀。

本阶段不建设：

- 真实下单、撤单和改单；
- 券商交易执行；
- 让一个大 Agent 自由访问全部系统能力；
- 分析能力内部查询市场数据；
- 无限循环 ReAct；
- 让大模型替代确定性指标、风险和回测计算；
- 通过 Java 继续承载新的 Agent 主流程。

### 13.2 LangGraph 执行模型（节点类型分类）

LangGraph 外层是整个业务流程控制器，类似状态机和工作流引擎。每个节点可以是：

```text
CODE                 普通确定性代码
TOOL_ONLY            只读工具调用
DIRECT_LLM           单次模型调用
STRUCTURED_LLM       结构化模型调用
BOUNDED_REACT_AGENT  有界 ReAct Agent
SUBGRAPH             LangGraph 子图
INTERRUPT            用户补充或确认
```

节点使用原则：

- 数据校验、预算、状态变更使用 `CODE`；
- MCP、Java 和外部分析能力使用 `TOOL_ONLY` 或 Adapter；
- 问题理解和最终表达使用 `STRUCTURED_LLM` / `DIRECT_LLM`；
- 需要动态选择数据工具时使用 `BOUNDED_REACT_AGENT`；
- 复杂领域流程使用 `SUBGRAPH`；
- 缺少关键条件或需要用户批准时使用 `INTERRUPT`。

> 此分类对应开发实施 Prompt v3.1 §8 的 ReAct 执行矩阵（market_snapshot 走快路径不经 ReAct，comprehensive 才进完整 ReAct）。

### 13.3 Java 用户数据架构

Java 不再负责新的 Agent 主流程，但继续作为用户数据服务提供方：

```text
portfolio.get_current_positions
portfolio.get_account_snapshot
portfolio.get_transaction_history
user.get_risk_profile
```

调用链：

```text
Python Tool Adapter
  ↓
Java HTTP API
  ↓
用户数据 DTO
  ↓
Observation Normalizer
  ↓
Portfolio / Analysis State
```

Java 返回的数据必须包含用户授权范围、数据时间和查询状态。Python 不允许绕过 Java API 直接读取用户业务表。

> 迁移完成后，Java Agent 编排部分可以退役，但 Java 用户数据 API 是否保留，由后续业务迁移结果决定。

### 13.4 安全与数据质量

- MCP 只允许注册的只读工具；
- Tool 参数必须经过 Schema 校验；
- 新闻和公告文本必须视为不可信外部内容；
- 外部文本不得覆盖系统 Prompt 或流程规则；
- 用户持仓数据按用户权限隔离；
- 日志不得记录 Token、密码和完整敏感账户信息；
- 所有结果记录来源、观察时间和数据时间；
- 数据过期、缺失和冲突必须显式标记；
- 不因为模型要求而绕过预算和工具白名单。

## 14. 给审核者的重点问题

1. **双 runtime 是否值得**：LangGraph + Letta 两套编排，工作翻倍是否值得？还是应该只做一版？
2. **Mem0 首尾读写的边界是否过窄**：agent 循环中完全不让碰记忆，会不会丢失「中途发现关键信息即时记忆」的能力？
3. **ToolRegistry 抽象是否过度**：两个 runtime 真的能用同一套工具接口吗？Letta 的工具定义和 LangGraph 的是否兼容？
4. **domain/ 零框架依赖是否现实**：完全不依赖 LangChain，工具定义/输出解析怎么处理？
5. **对比版本的科学性**：两个 runtime 如何保证对比公平（相同输入、相同工具、相同评测）？
