## 1. 产品定义

### 1.1 产品定位

Sentinel 是面向个人投资者的**主动式持仓看护 Agent**。系统以事件驱动方式持续监视用户持仓相关的市场信号，在事件发生时自主完成数据收集、分析与个性化解读，并通过通知通道主动触达用户；对话能力作为通知之后的追问通道与自由交互入口完整存在。

交互模型定义为 **watch-first, chat-second**：

- 第一交互面是由系统发起的事件解读推送（无需用户在线或发起请求）；
- 第二交互面是用户发起的对话（通知追问 / 自由问答），两条通道共用同一 Agent 执行引擎。

### 1.2 设计目标

| 目标 | 说明 |
|---|---|
| 技术覆盖 | 落地当前主流 Agent 技术：原生 tool calling、tool search、MCP 工具接入、语义路由、长期记忆、SSE 流式、运行 checkpoint |
| 可演示性 | 5 分钟演示路径具备明确记忆点：主动推送、个性化解读、可解释治理、断点续跑 |
| 可落地性 | 单用户生产可用；单实例部署假设；作者自用（dogfooding） |

### 1.3 约束与红线

| 编号 | 约束 |  enforcement 位置 |
|---|---|---|
| C-1 | 系统不具备任何交易执行能力；交易语义的工具在工具目录中物理不存在 | 工具目录 + 治理中间件（§4.4） |
| C-2 | 不出具投资适当性结论；适合度相关输出一律为风险匹配筛查（DRAFT 口径）并附风险披露 | 系统提示契约 + 响应治理 |
| C-3 | 单用户 + 游客演示，不建设多用户体系 | 认证与部署形态 |
| C-4 | 演示注入数据必须全程可辨识（负载 / 通知 / 证据链 / UI 四处标记），不得伪装为真实市场事实 | 事件契约 + 前端规格（§4.8、§7） |
| C-5 | 不自研能力插件框架；外部能力扩展一律经 MCP 接入 | §4.2 |

### 1.4 非目标

- 水平扩展与多副本协调（单实例假设，相关议题另行立项）；
- 财报日历 / 实时新闻异动的真实数据源（未经可得性验证前不承诺，见 §12 风险登记册）；
- 面向第三方的 Runtime / SDK 产品化。

## 2. 功能规格

### 2.1 功能分层

| 层 | 功能 | 触发方式 | 说明 |
|---|---|---|---|
| F1 监视 | 价格阈值看护 | 价格轮询器（事件） | 持仓标的价格 / 涨跌幅越阈即触发解读流程 |
| F1 监视 | 盘前晨报 | cron（交易日历判定） | 隔夜外围市场、持仓相关新闻、当日关注项 |
| F1 监视 | 盘后复盘 | cron（交易日历判定） | 当日持仓表现、异动标的、原因初判 |
| F1 监视 | 财报提醒 | 事件订阅（待验证） | 数据源可得性验证后接入，否则不在 v1 交付 |
| F2 解读 | 事件个性化解读 | F1 触发 | 输出含：仓位占比、浮盈变动、风险画像匹配结论、证据引用、审计码 |
| F3 对话 | 通知追问 | 用户点击通知 | 携带事件上下文建立会话，进入标准对话链路 |
| F3 对话 | 自由问答 | 用户发起 | 个股研究 / 组合诊断 / 适合度筛查（DRAFT）/ 金融知识 / 深度研究（开关）/ 多轮指代 / Pause-Resume |
| F4 管理 | 持仓 / 规则 / 记忆 / 通知管理 | 用户操作 | 监视规则 CRUD、记忆查看与删除、通知中心 |

### 2.2 对话通道的场景覆盖

对话能力在架构上是通用的，产品叙事聚焦金融看护：

| 输入类别 | 处理路径 | 工具参与 |
|---|---|---|
| 闲聊 / 通用知识 | 语义快路径直接应答 | 无 |
| 金融数据 / 分析类 | Agent 循环（工具调用） | 是 |
| 交易 / 越权语义 | 治理层拦截，返回拒绝与审计码 | 不执行 |
| 其他域（示例：天气） | Agent 循环 | 是（作为可插拔性实证） |

## 3. 总体架构

### 3.1 运行时拓扑

```text
┌────────────────────────── sentinel-engine (Python, :8090) ──────────────────────────┐
│                                                                                               │
│  事件源子系统            会话通道                  Agent 执行引擎（唯一，双通道共用）              │
│  ┌────────────────┐   ┌──────────────┐   ┌───────────────────────────────────────────────┐   │
│  │ 价格轮询器        │   │ 语义快路径     │   │ 工具装载器（scoped | search）                    │   │
│  │ 晨报定时器        │   │ (embedding)   │ → │ LLM tool-calling 循环                          │   │
│  │ 演示注入端点      │   └──────────────┘   │   └─ 每次调用经治理中间件（§4.4）                │   │
│  └───────┬────────┘                        │ 上下文组装器（会话态 / 唤醒态，§4.5）              │   │
│          ↓ WatchEvent                       └───────┬───────────────────────┬───────────────┘   │
│   watch_event 落库（幂等）                           ↓                       ↓                  │
│          ↓                                  结构化事件解读            SSE 流式响应              │
│   上下文组装（唤醒包）                                ↓                                               │
│                                          通知落库 + 在线推送（SSE）                                 │
└───────────────────────────────────────────┬─────────────────────────────────────────────────────┘
                                            │ HTTP（内部）
                 ┌──────────────────────────┴──────────────────────────┐
                 │  sentinel-data (Java/Spring, :8081)              │
                 │  认证 / 持仓 / 风险画像 / 持久化真源 / Outbox           │
                 └───────┬───────────────────────────┬─────────────────┘
                         ↓                           ↓
                  PostgreSQL（业务/运行时/目录）      MySQL（身份权限）

  外部能力：MCP servers（akshare-one / cn-financial） · sentinel-search · LLM（OpenAI 兼容）
  前端：sentinel-console（Nginx 静态站）
```

### 3.2 关键架构命题

1. **单一执行引擎，双通道驱动**：事件驱动通道（看护环）与会话通道（问答环）共用同一 Agent 循环、同一治理中间件、同一上下文与记忆机制。两通道差异仅在输入契约（WatchEvent vs 用户消息）、上下文组装方式（§4.5）与输出形态（结构化通知 vs 流式会话响应）。
2. **事件源可插拔**：全部事件源汇入统一的「事件 → 唤醒 → 解读 → 通知」流水线；新增事件源仅需实现事件产出逻辑，不触碰引擎与通知。
3. **能力接入标准化**：本地能力以 pydantic 参数契约定义，外部能力经 MCP 接入；两者统一登记至工具目录，对引擎透明。

### 3.3 组件职责

| 组件 | 职责 | 明确不承担 |
|---|---|---|
| orchestrator | Agent 循环、工具目录、装载策略、治理中间件、事件源、上下文组装、记忆、SSE、checkpoint | 不承载业务数据真源 |
| runtime-data | 认证、持仓、画像、会话与运行持久化、Outbox | 不承载 LLM 调用与编排逻辑 |
| console | dashboard、追问抽屉、契约测试 | 无服务端状态 |
| MCP servers | 行情 / 基本面 / 新闻等外部数据 | 不经业务库 |

## 4. 核心机制规格

### 4.1 统一工具模型

```text
ToolCard {
  name: str                  # 全局唯一，点分命名空间，如 market.get_quote
  description: str           # 面向模型与检索双目的撰写
  parameters: JSONSchema     # 由 pydantic 契约投影
  origin: local | mcp        # 本地实现或 MCP server 代理
  read_only: bool            # 治理输入
  required_scope: str[]      # 场景 / 身份可见性标签
  cost_hint: enum            # 预算权重（free | normal | premium）
}
```

- 工具目录（Tool Registry）是全部 ToolCard 的唯一真源；引擎、装载器、检索索引、中间件均从目录读取，不维护第二份清单。
- MCP server 接入时，其工具列表经目录代理登记并打上 `origin=mcp` 标记；治理规则对本地与 MCP 工具一致生效。

### 4.2 工具装载策略（Tool Loading）

模型在每次运行中仅能看到被装载的工具子集。装载决策由代码执行（策略查表 / 检索索引过滤），模型在装载集合内自主选择调用。支持两种可配置策略（`tool_loading = scoped | search`）：

| 策略 | 机制 | 语义 |
|---|---|---|
| `scoped`（默认） | 运行启动时按「场景标签 → 工具包」映射装载固定子集 | 简单、确定、可审计；工具规模 ≤20 时的首选 |
| `search`（实验） | 初始仅装载元工具 `search_tools(query, top_k)`；模型发起检索，目录经权限过滤后按 embedding 相似度（top-k + 阈值）召回，命中工具动态装载进后续上下文 | 验证检索式装载模式；为 MCP 工具数量增长预留 |

`search` 策略的补充规则：

- 已装载工具在会话内缓存，避免重复检索；
- `search_tools` 调用计入调用预算，单轮检索次数设上限；
- 连续 N 次检索未命中目标能力时，回退至 `scoped` 宽包，防止能力不可达；
- **权限过滤先于检索**：检索索引仅包含当前场景 / 身份可见的 ToolCard，模型无法检索到其无权使用的工具。

两种策略在同一 eval 题库上运行对照（任务成功率 / 检索命中率 / 平均轮次 / token 消耗），产出对比报告作为选型依据（§11）。

### 4.3 Agent 循环

标准 tool-calling 循环：模型输出 `tool_calls` → 治理中间件裁决 → 执行 → Observation 回填 → 模型继续决策，直至模型产出最终回答或预算耗尽。

**工具调用时机（三层闸门）**——避免「每句对话都触发分析」：

| 闸门 | 机制 | 语义 |
|---|---|---|
| G-α 入口 | 语义快路径（§4.6） | 闲聊 / 知识类不进入循环、不装载工具，直接应答 |
| G-β 调用决策 | 模型自主 | 工具装载仅表达「可用」；问题可由上下文 / 通识回答时模型直接输出文本，零工具调用；仅当回答依赖系统外事实（实时行情、用户持仓、最新资讯）时才发起调用 |
| G-γ 上限 | 治理中间件预算 | 单次运行工具调用数设上限；premium 工具（深度研究）另有独立开关 |

分工原则：**代码管入口（哪些请求进入循环），模型管调用（是否用、用哪个、何时停），预算管上限**。唤醒通道为事件驱动，进入循环即必然执行分析（其职责所在），但仍受 G-γ 约束。

Observation 契约：`{ data, source, data_time, quality_flags, result_type?, payload? }`——任何进入模型上下文的事实性数据必须携带来源与时间标记。

**类型化结果与展示真源**：分析类工具（个股研究 / 组合诊断 / 适合度筛查）除自然语言摘要外，返回**类型化结果**（`result_type` + 结构化 `payload`，pydantic 契约）。响应投影层将这些 payload 直接组装为前端结果块（§6.2 `blocks`、§7.8），**数字与评分不经 LLM 转述**——模型只产出解读文本（`answer`），展示层的事实性内容（分数、指标、清单）以工具输出为唯一真源。此约定是「确定性计算由代码完成、LLM 负责解释与表达」原则在展示层的延伸。

### 4.4 治理中间件

工具调用的唯一执行咽喉（interceptor 模式），本地工具与 MCP 工具一致生效：

```text
调用前：G1 可见性校验（防幻觉：工具名 ∈ 当次装载集合）
        G2 只读校验（read_only 红线）
        G3 权限校验（游客 / 机主）
        G4 预算校验与扣减（tool_call_limit；premium 工具按 cost_hint 加权）
        G5 参数 schema 校验（pydantic）
调用后：G6 Observation 包装（来源 / 时间 / 质量标记）
        G7 审计记录（调用者、工具、参数摘要、耗时、结果状态、审计码）
```

设计原则：

- **模型提议，代码裁决（model proposes, code disposes）**：语义理解类判断（意图分类、内容风险初筛）由模型 / embedding 承担；权限、预算、只读等不可挽回决策由代码以查表方式确定执行，不接受概率判断；
- **红线物理化**：交易类工具不在目录中注册，语义层无须也无法"识别并放行"危险操作（C-1）；
- **治理对工具作者透明**：新增工具（含新 MCP server）自动进入拦截链，无需治理侧适配；
- LLM 语义风险审核可作为 G2 之后的补充软关卡存在，但不得作为唯一关卡。

### 4.5 上下文组装

| 通道 | 上下文来源 | 组装内容 |
|---|---|---|
| 会话 | 会话历史 + 记忆 + 当前输入 | 系统提示 + 最近 N 轮消息 + L3 召回记忆 + 当前用户输入 |
| 唤醒 | 无会话，系统组装 | 解读专用系统提示（输出结构、C-1/C-2 口径）+ 事件负载 + 持仓快照 + 风险画像 + L3 目标记忆 |

唤醒态组装器是独立组件：输入为 WatchEvent + user_id，输出为标准化「唤醒包」。其组装质量直接决定事件解读的个性化程度，接受独立测试覆盖。

### 4.6 语义快路径

入口处以 embedding 相似度（对样例句集合，阈值判定）完成前置分流：

- 闲聊 / 通用知识：直接应答，不进入 Agent 循环，不装载工具（成本与延迟控制）；
- 需数据请求：放行进入引擎，其场景标签同时作为 `scoped` 装载输入；
- 快路径是路由机制，不承担任何权限裁决（§4.4 职责边界）。

### 4.7 记忆子系统（L3）

| 环节 | 机制 |
|---|---|
| 召回 | 会话与唤醒通道在组装阶段执行召回，召回内容注入消息序列 / 唤醒包（召回不发生则视为缺陷而非降级特性） |
| 写入 | 对话中出现的用户事实经用户确认卡确认后写入 L3 |
| 管理 | 前端提供查看 / 删除；删除走数据面并留痕 |
| 降级 | 记忆服务不可达时通道降级为无记忆运行，`/ready` 报 degraded，不静默 |

### 4.8 事件驱动子系统（看护环）

**规则模型**（持久化，跨进程存活）：

```text
watch_rule {
  id, user_id, status: active|paused,
  type: price_threshold | daily_briefing | post_market_review,
  config: JSONB     -- price_threshold: {symbol, direction, pct|abs_price}
                    -- cron 类:          {time, only_trading_day}
  last_fired_at
}
```

**事件契约与触发语义**：

```text
WatchEvent { id, rule_id, type, source, payload, dedupe_key, occurred_at }
```

- **边沿触发（edge-triggered）**：仅在状态穿越阈值的时刻产生事件；价格持续处于阈值一侧不重复触发；
- **幂等投递**：`dedupe_key`（规则 × 触发窗口 × 方向）以数据库唯一约束强制；事件生产遵循 at-least-once，消费端依赖该约束幂等；
- **轮询纪律**：仅交易时段运行（交易日历判定）；标的批量取价；数据源失败指数退避；非交易时段不发起请求（配额控制）；
- **演示注入**：`POST /internal/demo/events` 允许写入 `source=demo_inject` 的事件进入同一流水线；该端点仅在演示部署档（`BDLH_DEMO_MODE=true`）注册；注入事件在负载、通知、证据链、UI 四处携带「演示注入」标记（C-4）；
- **唤醒**：事件落库成功后创建运行（run），经唤醒态上下文组装进入 Agent 引擎；
- **产出**：结构化事件解读（标题 / 摘要 / 证据引用 / 审计码 / 严重度）写入通知存储；在线用户经 SSE 实时下发，离线用户下次进入时拉取（通知落库为完成语义，SSE 为在线增强）；
- **追问闭环**：通知携带 run 引用与事件摘要；`POST /notifications/{id}/followup` 建立会话并将事件上下文注入首轮，此后完全等同于会话通道。

### 4.9 可靠性与可恢复性

- 运行级 checkpoint：会话与唤醒运行均支持暂停 / 恢复，恢复点语义与运行游标绑定；
- 唤醒运行中途失败：按 checkpoint 恢复重跑，不产生第二条通知（通知写入与 run 结果唯一绑定）；
- 事件源进程崩溃：由进程监督重启；重复产生的事件被 `dedupe_key` 吸收；
- 就绪探针 `/ready` 覆盖 LLM、embedding、数据面、记忆服务：依赖缺失以 `degraded` 显性上报，禁止静默降级。

## 6. 接口规格

### 6.1 HTTP API

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/v1/chat/stream` | 会话通道 SSE 入口 |
| GET / POST / PATCH / DELETE | `/api/v1/watch-rules[/{id}]` | 监视规则管理[^impl-watch-api] |
| GET | `/api/v1/notifications` | 通知中心（分页、未读计数） |
| POST | `/api/v1/notifications/{id}/followup` | 追问入口：创建携带事件上下文的会话 |
| GET | `/api/v1/agent-runs/{id}` | 运行回放（工具调用、Observation、审计记录） |
| POST | `/internal/demo/events` | 演示事件注入（仅 demo 档注册） |
| GET | `/health` · `/ready` | 存活 / 就绪探针 |

### 6.2 SSE 事件契约（会话通道）

| 事件 | 载荷 | 说明 |
|---|---|---|
| `agent_run` | runId / sessionId | 传输层协议帧 |
| `tool.step` | tool / arguments / status | 每轮工具调用实时外显；`search_tools` 检索亦以该事件呈现 |
| `token` | 文本分片 | 真实流式（LLM `astream`），禁止伪流式切片 |
| `response.final` | ChatResult v2 | answer / **blocks[]**（类型化结果块，§7.8）/ tool_trace / evidence_refs / audit_codes / disclosures |
| `done` | status | COMPLETED / NEED_CLARIFICATION / FAILED |
| `notification` | 通知摘要 | 在线推送（看护环触达） |

```text

│ 追问 · 宁德时代 −5.2%         [—][×]│
│ ┌──────────────────────────────┐ │

│ 用户：这对我的换房计划有影响吗？     │
│                                  │
│ ╭ 工具轨迹（tool.step 时间线） ╮   │
│ │ ◈ search_tools "持仓 分析"     │ │   ← search 模式时呈现检索节点
│ │   → 命中 3 个工具（120ms）      │ │
│ │ ● portfolio.get_positions ✓    │ │
│ │ ● market.get_quote 300750 ✓    │ │
│ ╰────────────────────────────────╯ │
│ Agent（流式）：从您的持仓看……▌      │
│ ┌─ 证据链 ──────────────────┐     │
│ │ [1] 行情快照 14:32  深交所   │     │
│ │ [2] 公司公告 …             │     │
│ │ 审计码 RO-OK · DQ-OK        │     │
│ └────────────────────────────┘     │
│ [⏸ 暂停] [▶ 恢复]  ← 运行中显示    │
├──────────────────────────────────┤
│ [ 输入框 …                  发送 ] │
└──────────────────────────────────┘
```

组件与行为：

- **工具轨迹时间线**：每个 `tool.step` 一个节点，含工具名、参数摘要、耗时、结果状态（成功 ✓ / 被拒 ✕ 含审计码）；`search_tools` 节点特殊渲染（检索词 + 命中数），这是 tool search 模式的可视化展示点；节点默认折叠、点击展开 Observation 摘要；
- **流式正文**：`token` 事件增量渲染（打字机效果来自真实流，非前端模拟）；Markdown 子集渲染（段落 / 列表 / 表格）；
- **证据链卡**：`response.final` v2 到达后渲染 `evidence_refs` / `audit_codes` / `disclosures`；这是治理叙事的上屏点；
- **运行控制**：运行中显示暂停；暂停后显示恢复[^impl-resume]；`NEED_CLARIFICATION` 时输入框上方渲染澄清选项卡；
- **状态条**：LLM / 记忆 degraded 时输入框上方常驻提示条（数据源：`/ready` + `agent_run` 帧内 degraded 字段）。

### 7.5 P3–P6 次要视图

- **P3 通知中心**：列表（严重度条 + 标题 + 时间 + 已读态），支持按类型 / 严重度过滤、全部已读；行点击复现事件卡并可发起追问；
- **P4 监视规则管理**：表格视图（类型 / 配置摘要 / 状态 / 最近触发）；新建表单按类型切换字段（价格阈值：标的 / 方向 / 幅度；晨报：时间 / 仅交易日）；启停为开关；删除二次确认；
- **P5 记忆管理**：记忆条目列表（内容 / 来源会话 / 写入时间），支持删除（走数据面，留痕）；空态文案说明记忆如何产生；
- **P6 运行回放**：只读时间线（tool_trace 全程 + Observation + 审计记录），用于演示「可解释性」与面试深挖；不保存模型隐藏思维链。

### 7.6 SSE 事件 → UI 映射

| SSE 事件 | UI 行为 |
|---|---|
| `agent_run` | 抽屉进入运行态：显示控制按钮、记录 runId、呈现 degraded 标记（如有） |
| `tool.step` | 工具轨迹追加 / 更新节点（pending → ✓/✕） |
| `token` | 正文增量渲染并自动滚动 |
| `response.final` | 渲染证据链卡、审计码、披露；工具轨迹定格 |
| `done` | 运行态收尾；`NEED_CLARIFICATION` → 渲染澄清选项卡；`FAILED` → 错误条（含审计码） |
| `notification` | P1 时间线 prepend + 铃铛未读 +1；critical 触发红点与提示音 |
| 连接断开 | 指数退避重连；时间线回退 30s 轮询；状态条提示 |

### 7.7 状态与降级设计

| 状态 | 设计 |
|---|---|
| 加载 | 骨架屏（持仓卡 / 时间线条目），禁止白屏 |
| 空态 | 无规则 → 引导创建；无通知 → 说明监视如何工作；无记忆 → 说明产生方式 |
| 依赖降级 | `/ready` 报 degraded 的依赖（LLM / embedding / 记忆）映射为对应区域的显性提示条，不静默 |
| 演示档标识 | Header 常驻「演示数据」横幅；注入事件三处水印（C-4） |
| 错误 | API 失败 → 区域级错误条 + 重试；SSE 断线 → 重连与轮询回退（§7.6） |

### 7.8 结构化分析结果：Block 渲染体系

分析类工具（评分、多维分析、适合度筛查）的结果以**结果块（ResultBlock）**形式进入响应，前端按类型分发到专用渲染组件，而非混入回答文本。

#### 7.8.1 契约与渲染分发

```text
ResultBlock = ScoreCard | AnalysisReport | SuitabilityDraft | PortfolioHealth | QuoteTable

ChatResult v2 {
  answer: str                # LLM 产出的解读文本（叙事层）
  blocks: ResultBlock[]      # 由工具 Observation 直接投影（事实层，不经 LLM 转述）
  tool_trace / evidence_refs / audit_codes / disclosures
}
```

- 前端维护**渲染器注册表**：`block.type → 组件`；未知类型降级为折叠 JSON 视图（不报错、不丢弃）；
- 图表库选型：**ECharts（CDN 引入，单 script 标签）**——满足雷达图 / 条形 / 环形需求，且不引入构建工具链，与静态站栈一致；
- 叙事与事实分离：用户先读 `answer`（解读），后看 Block（数据本体）；Block 内每个数字可追溯至具体 Observation（来源 / 数据时间）。

#### 7.8.2 ScoreCard（评分卡，个股研究主块）

```text
┌─ 宁德时代 300750 · 综合评分 ──────────────────────┐
│                                                   │
│        ╭─────────╮        综合  72 / 100          │
│        │  雷达图  │        评级带: 中性偏强 ▲       │
│        │ 五维     │        数据时间 2026-08-19     │
│        ╰─────────╯                                │
│                                                   │
│  技术面    ████████░░  78  ▲   [明细]              │
│  基本面    ███████░░░  74  →   [明细]              │
│  估  值    █████░░░░░  52  ▼   [明细]              │
│  资金流    ██████░░░░  65  ▲   [明细]              │
│  情绪面    ███████░░░  71  →   [明细]              │
└───────────────────────────────────────────────────┘
```

- 五维雷达图（ECharts radar）+ 每维 0–100 条形与趋势箭头（环比上次评分）；
- 综合评分为服务端确定性加权（权重配置在服务端，前端不计算）；
- 「明细」展开该维度的 findings 列表：每条结论挂证据编号（点击联动证据浮层）；
- 评分方法论入口：卡片脚注链接至说明页（指标构成、权重、更新频率）——**评分可解释是治理叙事的一部分**。

#### 7.8.3 AnalysisReport（分析明细块）

维度分组的折叠面板：每组含结论列表（finding）、支撑指标（键值对表）、证据编号。默认展开首个维度，其余折叠。财报 / 行情类表格统一 QuoteTable 渲染（列排序、数值千分位、正负着色）。

#### 7.8.4 SuitabilityDraft（适合度筛查卡，受 C-2 约束）

```text
┌─ 风险匹配筛查（DRAFT · 非适当性结论）──────────────┐
│  匹配项  ✓ 风险等级 R3 ↔ 画像稳健型                │
│          ✓ 持仓集中度在容忍带内                     │
│  风险项  ⚠ 单日波动超画像容忍带 1.8σ               │
│          ⚠ 该标的占仓 18%，高于单标的建议区间        │
│ ──────────────────────────────────────────────── │
│  本结果仅为风险匹配筛查草稿，不构成投资建议。          │
│  [查看画像]  [查看计算依据]                          │
└───────────────────────────────────────────────────┘
```

硬性规则：**界面不存在「适合 / 推荐买入」语义的结论位**；匹配项与风险项永远成组呈现；披露文案固定不可关。

#### 7.8.5 PortfolioHealth（组合诊断块）

集中度指标（HHI、前三大占比）条形 + 行业分布环形图 + 风险项清单；事件解读卡（§7.3 时间线条目）可内嵌其迷你版（单条关键指标 + 「查看完整诊断」跳转）。

#### 7.8.6 Block 在各视图的出现位置

| 视图 | Block 形态 |
|---|---|
| P2 会话 / 追问抽屉 | 完整卡片，位于回答文本之后、证据链卡之前 |
| P1 事件时间线 | 迷你版（1 个关键指标 + 跳转） |
| P6 运行回放 | 完整卡片只读态，标注对应 Observation 序号 |

## 11. 质量保障

### 11.1 测试策略

| 层 | 覆盖 |
|---|---|
| 事件源 | 交易日判定、阈值穿越（边沿语义）、`dedupe_key` 幂等 |
| 看护闭环 | FakeChatModel 集成：注入事件 → 通知落库（证据引用、审计码断言）→ 追问首轮上下文 |
| 治理中间件 | G1–G7 逐条拦截与审计记录断言 |
| 工具装载 | `scoped` 映射正确性；`search` 检索命中、缓存、预算、回退 |
| 演示注入 | demo 档开关路由注册；`source` 标记全链路透传；非 demo 档 404 |
| 前端 | SSE 契约 → 时间线 / 徽标 / 水印渲染 |
| 引擎回归 | 既有测试基线全绿，只增不减 |

### 11.2 eval 对照

统一题库（闲聊 / 知识 / 金融研究 / 组合 / 适合度 / 多轮指代 / 误伤 / 看护场景 ≥6 条），对 `scoped` 与 `search` 两种装载策略分别运行，输出任务成功率、检索命中率、平均轮次、token 消耗的对比报告；任何一方任务成功率不得劣于题库基线。

### 11.3 工程纪律

- 门禁：`uv run pytest -q` + `ruff check`；Java `mvn -B -ntp test`；两套 compose `config -q`；[^impl-pytest]
- 被替换路径（正则分派、伪 function calling、伪流式、域插件框架）物理删除，不留兼容层；
- 文档与代码同步：本文件为目标形态真源，实施偏差以工单收敛。

## 12. 设计权衡记录

| # | 决策 | 备选方案 | 采纳理由 |
|---|---|---|---|
| D-1 | 主动式事件驱动作为第一交互面 | 被动问答 Bot | 事件驱动构成与 chatbot 的范式区分；唤醒态上下文组装是个性化的技术支点 |
| D-2 | 裁决逻辑代码化（查表 / 中间件） | LLM 判官 / 阈值拦截 | 权限类决策要求确定性与可审计性；概率判断可被注入话术绕过；红线物理化（工具不注册）优于运行时识别 |
| D-3 | 能力接入统一为 tool，MCP 即插件机制 | 自研 Domain 插件框架 | MCP 已是标准化插件协议；自研框架制造第二套目录与治理接缝 |
| D-4 | 装载策略双模式并存 + eval 对照 | 仅 scoped / 仅 search | 工具规模当前偏小，scoped 为可靠默认；search 面向规模增长与模式验证，选型以对照数据为依据 |
| D-5 | 边沿触发 + 唯一约束幂等 | 水平触发 / 应用层去重 | 轮询模型下水平触发必然重复推送；at-least-once + 幂等消费为标准解法 |
| D-6 | 前端原地扩展 | 引入新前端框架 | 单人维护成本约束；契约测试体系已有 |
| D-7 | 演示注入作为正式机制 | 演示依赖真实行情窗口 | 演示可靠性要求零外部依赖；四处标记保证不污染事实边界（C-4） |
