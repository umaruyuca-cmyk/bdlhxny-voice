### 2.3 前端 API 调用现状

前端所有页面通过 **Nginx `/api/` 反代** 调后端，核心接口：

| 前端调用 | 用途 |
|---|---|
| `POST /api/v1/chat/stream` | SSE 流式对话(核心) |
| `GET /api/v1/agent-runs?limit=20` | 运行列表 |
| `GET /api/v1/agent-runs/{runId}` | 单次运行详情 |
| `GET /api/v1/agent-runs/{runId}/skill-results` | Skill结果回看 |
| `GET /api/v1/conversations?mode=&limit=` | 会话列表 |
| `GET /api/v1/conversations/{id}` | 单会话历史 |
| `GET /api/v1/public/capabilities` | 能力清单(看板用) |
| `skill-dashboard.html` 直调 `:3001` | 绕过Java直连wrapper(调试用) |

**关键点**：前端不直连后端端口，统一走 Nginx `/api/`。这意味着**前端代码几乎不用改**——只要新引擎也对齐这套接口，Nginx 改一下反代目标即可。

### 2.4 融合后前端改动方案（○微调）

前端改动极小，只有两处：

#### 改动1：Nginx 反代增加分流（◎改动 `nginx.conf`）

```nginx
# 方案A:一刀切(迁移期)
location /api/ {
    proxy_pass http://127.0.0.1:8000;   # Python新引擎(替代:8081)
}

# 方案B:按任务分流(并行期，推荐)
location /api/v1/chat/stream {
    # 按header/query或cookie判断走哪个引擎
    # 简单实现:用 map 指令读 $arg_engine
    proxy_pass http://127.0.0.1:$backend_port;
}
```

#### 改动2：新增 Python 引擎专属页面（★新增，可选）

```
public/
├── workspace.html              # ○不动(双引擎共用)
├── stockwise-chat.html         # ○不动
└── analysis-v2.html            # ★新增:Python引擎专属分析页(展示Graph/observation/多子图)
```

**前端其余全部不动**。`workspace-common.js` 的 SSE 消费逻辑、会话管理、run 回放都是通用的——只要 Python 引擎的 SSE 事件格式对齐，现有页面直接复用。

### 3.2 Java 各包的融合处置（逐包定性）

按「新 Python 引擎如何处置」分四档：

#### 第一档：核心编排（被 Python 替代 → 废弃）

| Java 包 | 职责 | Python 对应 | 处置 |
|---|---|---|---|
| `agent/routing/`(19类) | 意图分类+路由+执行计划+付费门禁 | `graphs/root/classify.py` + `runtime/orchestrator.py` | ◎Phase1-2后废弃 |
| `agent/react/`(7类) | 有界ReAct循环 | `agents/base.py` + `graphs/market_research/budget_guard.py` | ◎Phase2后废弃 |
| `agent/context/`(3类) | Token预算+上下文窗口 | `runtime/budget.py` | ◎Phase1后废弃 |
| `agent/`(顶层4类) | Orchestrator/ContextBuilder | `runtime/application_runtime.py` | ◎Phase2后废弃 |
| `llm/`(6类) | DeepSeek/分类/嵌入 | `infrastructure/model_providers/` | ◎Phase2后废弃 |

**这 39 个类是 Java 的「大脑」，新 Python 引擎就是来替代它们的。** 迁移完成后整包删除。

#### 第二档：有价值的业务逻辑（迁移到 Python → 删除原实现）

| Java 包 | 核心逻辑 | 迁移目标 |
|---|---|---|
| `memory/LangChainEpisodicEmbeddingStore` | 情景记忆:pgvector向量检索+recency/semantic加权排序 | `graphs/knowledge/` + `infrastructure/database/`，**共享同一套pgvector表** |
| `memory/SessionStateService` | 会话状态持久化+冲突检测 | `runtime/` + 复用 `conversation_session` 表 |
| `service/EpisodicMemoryService` | 情景记忆检索的业务封装 | `graphs/knowledge/` |
| `service/KnowledgeService` + Extractor + Ingest + Retrieval | 知识RAG四件套(抽取/入库/检索/过滤) | `graphs/knowledge/` + `tools/knowledge_tools.py` |
| `service/GuardrailService` | 输出护栏(事实校验/安全) | 分散到 Python `runtime/errors.py` + 各子图条件边 |
| `skill/`(6类) | Skill注册/定义/上下文框架 | `skills/`(Phase6重设计后) |

**这些是 Java 沉淀的业务知识，不能丢弃，要带着语义迁移到 Python。**

#### 第三档：纯 HTTP 客户端（Python 写更薄的替代 → 废弃）

| Java 包 | 调的什么 | Python 替代 |
|---|---|---|
| `tool/HttpStockAnalysisGateway` | stock-wrapper:3001 | `infrastructure/data_providers/stock_wrapper_client.py`(更薄) |
| `websearch/gateway/HttpWebSearchGateway` | web-search-wrapper:3002 | `infrastructure/data_providers/web_search_client.py`(更薄) |

Java 这层本质就是「HTTP客户端+契约校验」，Python 侧几十行就能复刻，Java 原实现废弃。

#### 第四档：基础设施（共享，不迁移，Python 自己建）

| Java 包 | 内容 | Python 处理 |
|---|---|---|
| `api/`(9 Controller) | HTTP入口 | Python 用 FastAPI 重建，但**接口契约对齐**(见 §5) |
| `entity/mapper/dto` | ORM+MyBatis | Python 用 SQLAlchemy async，**共享同一套PG表** |
| `config/`(4类) | Spring配置 | Python `config.py` |
| `security/`(5类) | JWT+单用户 | Python `auth/`(可复用同一套JWT密钥) |
| `handler/`(3类) | pgvector/JSONB类型处理 | SQLAlchemy自动处理 |

### 3.3 Java 过渡期策略

```
Phase 0-1:  Java 完全不动，正常服务。Python 引擎并行开发。
Phase 2-3:  Java 维护模式(只修P0 bug，不加功能)。
            市场研究/组合分析流量逐步切到 Python。
Phase 4-5:  Java memory/knowledge 逻辑迁移到 Python，共享DB表。
Phase 6:    Java 整体退役，docker-compose 移除 stockwise-backend。
            可能保留 1-2 个 Controller 临时过渡(如 Auth)。
```

## 5. 接口契约对齐（前端零改的关键）

Python 引擎必须实现这套接口（与 Java 现状对齐），否则前端要改：

```
POST /api/v1/chat/stream          → SSE流式对话(事件格式须对齐)
GET  /api/v1/conversations        → 会话列表(?mode=&limit=)
GET  /api/v1/conversations/{id}   → 会话历史
GET  /api/v1/agent-runs?limit=20  → 运行列表
GET  /api/v1/agent-runs/{runId}   → 运行详情
GET  /api/v1/agent-runs/{runId}/skill-results → Skill结果
GET  /api/v1/public/capabilities  → 能力清单
```

SSE 事件类型须与 Java 现有格式对齐（前端 `workspace-common.js` 的 `handleStreamEvent` 解析逻辑不变）。

**这是融合能「前端零改」的核心约束，Python 引擎必须遵守。**

## 9. 迁移路径（对齐设计 §22 Phase）

```
Phase 0  建 Python 骨架 + 接通 stock-wrapper/web-search/PG
         → 此时 Python 能做"单只股票分析"(调 wrapper)，Java 继续服务其余
         → 前端 flag 默认仍指向 Java

Phase 1  Python Query Understanding + Root 路由
         → 前端开始按任务类型分流:简单行情→Python，复杂对话→Java

Phase 2  Python Market Research Graph(含 ReAct + 预算守卫)
         → 市场研究类请求切到 Python，Java 的 agent/react 进入低流量

Phase 3  Python Portfolio Graph
         → 持仓分析切到 Python

Phase 4  Python Strategy + Backtest
         → 评估 skill 计算逻辑是否迁移到 domain/

Phase 5  Python Knowledge/Memory(迁移 Java memory/knowledge 逻辑)
         → 情景记忆、知识检索在 Python 重建，共享 DB 表

Phase 6  Skill 重设计 + Java 后端退役
         → 双引擎对比验证通过 → Java 下线 → docker-compose 移除 stockwise-backend
```

## 11. 给审核 AI 的重点问题

请审核者重点检查以下几点：

1. **前端「零改」是否现实**：Python 的 SSE 事件格式能否 100% 对齐 Java？LangGraph 的事件流和 Java Spring AI 的 SSE 格式差异多大？是否需要一层适配？
2. **双引擎共享 PG 表的并发安全**：Python(SQLAlchemy async)和 Java(MyBatis-Plus)同时读写 `conversation_episode_embedding`、`agent_run` 等表，事务隔离级别、向量索引写冲突如何处理？
3. **Java 39 个编排类被整体废弃的风险**：routing 里的 `PaidModelGate`/`RouteExecutionPolicy` 等门禁逻辑，Python 侧是否需要等价重建？设计文档说「不做复杂门禁」，但 Java 已有付费门禁——是否倒退？
4. **前端是否应该升级工程化**：当前纯静态 HTML(1500行 workspace-common.js)，融合后如果 Python 引擎带来新的交互(Graph 可视化、observation 追溯)，是否到了该引入框架(React/Vue)的时机？
5. **skill 计算层迁移的必要性**：设计要求 Python `domain/` 承担确定性计算，但 stock-analysis-skill(Node)已成熟且带「无未来函数回测」等硬约束——重写风险是否高于永久复用？
6. **Nginx 单点路由 vs API 网关**：前端一个 Nginx 同时反代两个引擎，是否应该引入独立的 API Gateway(如 Kong/Traefik)做统一鉴权、限流、引擎路由？

## 12. 融合核心结论

一句话总结：

> **Python 新引擎替代 Java 的「大脑」(agent 39 类)，通过 HTTP 复用 Node 数据能力层，前端靠 Nginx 切换反代目标实现「零改」过渡，双引擎共享 DB/Redis，最终 Java 退役。**

四个融合要点：

```
替代：  Java agent/ 39个编排类 → Python LangGraph
复用：  stock-wrapper / web-search-wrapper / skill → HTTP 消费，零改动
共享：  PG / Redis / pgvector → 双引擎同库同表
过渡：  Nginx flag 路由 → 逐 Phase 切流量 → Java 退役
```
