# 系统架构与运行流程

## 1. 架构目标

系统围绕“固定条件下可重复运行、运行过程可追溯、公开页面不产生模型费用”设计。一次运行必须能回答：

- 运行了哪个固定用例和数据变体；
- 模型实际收到了哪些上下文和工具；
- 哪些上下文被保留、压缩、引用或省略；
- 模型提出了哪些工具调用，代码如何处理；
- 每个阶段花了多长时间和多少 token；
- 运行是否有效，为什么通过或失败。

## 2. 总体结构

```text
项目所有者登录
        │
        ▼
私有运行页面 ──提交 case_id / variant_id / 运行方式──┐
                                                     ▼
                                              运行控制器
                                                     │
              ┌──────────────────────────────────────┼─────────────────────────┐
              ▼                                      ▼                         ▼
        固定用例目录                           数据快照生成器              上下文构建器
        问题与评测条件                         冻结本次输入数据          选择、压缩、校验
              └──────────────────────────────────────┼─────────────────────────┘
                                                     ▼
                                               Agent 执行器
                                  快路径 / 工具装载 / 模型循环 / 代码拦截
                                                     │
                                                     ▼
                                               运行记录生成器
                                  上下文、模型、工具、耗时、token、判断结果
                                                     │
                         ┌───────────────────────────┴──────────────────────────┐
                         ▼                                                      ▼
                   本地原始工件                                           发布脚本
                   内部调试与复判                               脱敏、校验、生成公开静态数据
                                                                                │
                                                                                ▼
                                                                        /showcase 静态站
```

## 3. 模块职责

### 3.1 固定用例目录

固定用例目录保存问题、场景、权限、工具范围、上下文规则、数据变体和评测条件，是运行页面和评测器的共同数据源。

固定用例由 `data` 保存到 PostgreSQL 的版本表中。运行 API 先按 `case_id` 读取当前版本，再创建批次。评测包中的 Python 定义只用于执行阶段兼容，后续应由数据库用例生成执行输入，不能长期维护第二份题目。

### 3.2 运行控制器

运行控制器负责：

- 验证登录身份；
- 根据编号读取固定用例，拒绝请求中的任意问题正文；
- 创建批次和运行编号；
- 设置总超时、取消标记和并发上限；
- 调用数据快照、上下文构建和 Agent 执行；
- 将基础设施故障与 Agent 能力失败分开记录。

### 3.3 数据快照生成器

同一个对照中的所有运行必须使用相同数据快照。快照至少记录：

```json
{
  "snapshot_id": "snap-20260820-001",
  "case_version": "market-quote-001@3",
  "fixture_version": "financial-fixture@5",
  "profile_version": "demo-profile@2",
  "market_as_of": "2026-08-20T14:32:00+08:00",
  "source_hash": "sha256:..."
}
```

本平台评测的是 agent 执行指标（选择、幻觉、参数、权限、流程、检索），不是工具调用质量；全部工具在任何场景下一律使用冻结 mock 返回，不存在真实调用路径（适配器槽保持未装配，与演示与否无关）。工具可见集是批次级实验变量，经 /lab 勾选或批次配置指定，随 fixed_conditions 落库并在工件中记录。

#### 数据来源

私有运行环境只保留一个 `data` 服务。它保存固定题库、用例版本、冻结数据快照、批次、运行、上下文处理明细、事件和评测结果。长期目标等信息如果是某个长上下文用例的输入，也作为有版本的固定上下文条目保存，不单独引入记忆服务或向量召回。

数据服务只保存事实和记录，不决定模型上下文。上下文构建器读取指定快照，记录来源、时间和 hash，再决定哪些内容保留、压缩、引用或省略。公开展示部署不连接数据服务，也不包含数据库凭证。

具体表关系、版本规则、索引、JSONB 使用范围和数据保留策略见
[`db/docs/01-数据库总体设计.md`](../../db/docs/01-数据库总体设计.md)。

### 3.4 上下文构建器

上下文构建器负责收集候选信息，按场景和 token 预算选择实际发送给模型的内容。详细规则见 [长上下文构建与压缩.md](../context/长上下文构建与压缩.md)。

它输出两部分：

- 模型实际使用的工作上下文；
- 上下文处理报告，包括原始 token、最终 token、选择原因、被省略内容和耗时。

上下文构建失败时，不允许静默改用不受控的完整历史。系统应按用例配置选择“使用最小安全上下文继续”或“本次运行无效”。

### 3.5 Agent 执行器

新正式实验以**实验模板 + 唯一自变量**定义（`experiments/templates.py`），统一在原生 Tool Calling `AgentLoop` 底座上运行（`experiments/template_runner.py`）：执行引擎、工具提供方式（all/search）、治理档位、上下文策略与限制各自成为独立配置（`RunConfig` 快照与 `config_hash`）。历史口径保留为两类诊断，不冒充单变量：

1. **整体实现方案诊断**：baseline 裸循环 / full-system 完整工程模式（同时改变循环、上下文组织、工具装载和治理；LangGraph ReAct 已并入 native 底座，只保留历史只读兼容）；
2. **上下文处理方式交叉诊断**：4×2（四种上下文 × 两种旧整体实现，显式触发）；默认上下文实验是 4×1（同一原生底座只变 `context_strategy`）。

完整工程模式继续使用现有能力：

- 语义快路径；
- 按场景装载工具或检索工具；
- 原生 tool calling 循环；
- 工具执行前的可见性、只读、权限、预算和参数校验；
- 工具执行后的来源、时间、质量和审计记录；
- 最终答案的数字引用与合规检查。

### 3.6 运行记录生成器

运行记录生成器只消费运行过程中产生的事件，不允许根据最终答案反推或补写过程。记录内容包括：

- 用例、版本、数据快照和运行配置；
- 上下文处理报告；
- 模型轮次、工具调用、代码拦截和工具结果摘要；
- 阶段耗时、token、重试和错误；
- 最终答案、引用、审计码和评测结果；
- Git commit、模型、提示词版本、工具目录版本和文件 hash。

### 3.7 评测器

评测器负责判断工具是否正确、关键事实是否保留、数字是否有来源、权限是否泄漏、合规要求是否满足。评测器失败不会把 Agent 运行标记为失败，而是把本次运行标记为“等待评测”或“无效评测”。

### 3.8 发布脚本

发布脚本从本地原始工件生成公开工件：

1. 使用字段白名单投影；
2. 删除或摘要敏感字段；
3. 校验每个引用和 hash；
4. 生成公开索引和批次报告；
5. 写入 `web/public/showcase-data/`；
6. 公开站点只读取这些静态文件。

发布数据是可重复生成的输出，不是第二份人工维护的数据源。

## 4. 一次运行的详细流程

```text
1. 登录用户选择固定用例
2. 后端根据 case_id 读取问题和规则
3. 创建 batch_id、run_id 和超时预算
4. 冻结本次数据快照
5. 收集上下文条目并估算 token
6. 保留强制项，压缩或省略其他项
7. 校验权限、关键约束、引用和 token 上限
8. 按场景装载允许的工具
9. 调用模型
10. 模型如提出工具调用，代码依次执行各项检查
11. 工具结果标准化后进入下一轮模型调用
12. 输出检查器修正或拒绝没有依据的内容
13. 保存运行工件
14. 评测器给出判断
15. 合法批次经发布脚本生成公开数据
```

## 5. API 目标设计

### 5.1 私有运行 API

```http
POST /api/v1/case-runs
Authorization: Bearer <owner-token>
Content-Type: application/json

{
  "case_id": "market-quote-001",
  "variant_id": "long-context",
  "agent_mode": "full-system",
  "context_strategy": "budgeted"
}
```

服务端必须拒绝 `message`、`prompt`、`system_prompt` 或任意工具列表字段。

建议接口：

| 方法 | 路径 | 用途 |
|---|---|---|
| `GET` | `/api/v1/cases` | 登录后读取固定用例目录 |
| `POST` | `/api/v1/case-runs` | 创建单次运行 |
| `POST` | `/api/v1/eval-batches` | 创建一组重复对照运行 |
| `GET` | `/api/v1/batches/{id}` | 查看批次状态和运行列表 |
| `GET` | `/api/v1/runs/{id}` | 查看内部完整运行记录 |
| `POST` | `/api/v1/batches/{id}/publish` | 发布已通过检查的批次 |

### 5.2 公开接口

公开部署不提供运行 API。页面通过静态文件读取：

```text
/showcase-data/index.json
/showcase-data/batches/{batch_id}/report.json
/showcase-data/runs/{run_id}.json
```

## 6. 认证和部署边界

### 6.1 公网展示部署

- 只包含 Nginx 和静态文件；
- 不包含 LLM key、运行服务和数据服务；
- 不代理 `/api/v1/case-runs`；
- 不依赖登录状态；
- 浏览页面不会产生 token 成本。

### 6.2 私有演示部署

- 包含运行服务和登录；
- 只允许项目所有者账号；
- 运行、注入事件、发布和读取内部工件都需要后端鉴权；
- 设置并发上限、单次运行上限和每日 token 上限；
- 演示环境使用单独的模型密钥和模拟数据。

## 7. 运行状态和错误分类

### 7.1 运行状态

```text
CREATED → SNAPSHOTTING → BUILDING_CONTEXT → RUNNING → JUDGING → COMPLETE
                                      └→ CANCELLED
                                      └→ INVALID
                                      └→ FAILED
```

| 状态 | 含义 | 是否进入能力统计 |
|---|---|---|
| `COMPLETE` | Agent 和评测都完成 | 是 |
| `FAILED` | Agent 在有效环境下产生任务失败 | 是，作为失败样本 |
| `INVALID` | 429、余额、服务不可用、评测环境错误 | 否 |
| `CANCELLED` | 人工取消或批次停止 | 否 |
| `PENDING_JUDGMENT` | Agent 完成，评测器未完成 | 暂不进入 |

## 8. 时长与超时

总时长必须拆分记录：

```json
{
  "queue_ms": 12,
  "snapshot_ms": 25,
  "context_collect_ms": 46,
  "context_compress_ms": 138,
  "tool_loading_ms": 8,
  "llm_ms": 8240,
  "tool_ms": 2140,
  "guardrail_ms": 31,
  "judgment_ms": 420,
  "first_output_ms": 1650,
  "duration_ms": 11120
}
```

初始目标区间用于发现异常，不作为脱离真实数据的宣传数字：

| 类型 | 初始总时长目标 | 处理方式 |
|---|---:|---|
| 快路径或拦截 | 1～3 秒 | 超时直接失败，不调用工具 |
| 单工具查询 | 3～8 秒 | 工具超时后给出明确降级 |
| 多工具研究 | 10～30 秒 | 页面持续显示阶段进度 |
| 长上下文或组合分析 | 20～60 秒 | 独立总超时，允许部分工具结果 |

正式报告使用 p50、p95 和最大值，不只显示平均数。

## 9. 可靠性要求

- `case_id + case_version + snapshot_id + run_index + agent_mode + context_strategy` 构成幂等键，重复提交不能意外生成重复计费运行；
- 工具调用有单独超时，不能占满整次运行时长；
- 模型重试次数和退避时间进入运行记录；
- 429、余额不足和模型服务不可用直接标记为无效运行；
- 保存工件失败时不得把运行标记为完成；
- 公开发布失败不影响内部原始工件；
- 运行记录不保存模型隐藏思维过程，只保存可观察的输入、输出、工具调用和代码判断。
