# 匿名测试运行模块设计

> 实验对象、运行次数和多工具用例的最新规则见[《压缩用例与对比用例设计》](./压缩用例与对比用例设计.md)。本文中的“普通 Agent 测试”统一理解为“对比用例测试”，“上下文压缩”和“Session 交叉测试”是压缩用例模块中的两个可拆分阶段。

## 1. 设计结论

新增一级模块“测试运行”，允许未登录访问者选择公开用例、可见工具和测试方式并发起测试。

“用例库”和“测试运行”不合并：

- 用例库负责回答“有哪些用例、每个用例是什么”；
- 测试运行负责回答“这次选择什么条件、怎么运行、运行到哪一步、结果是什么”。

对比用例测试读取用例库，保存 `case_id` 和 `case_version`。压缩用例直接读取上下文压缩模块保存的三个版本化长 Session，不再读取旧的长上下文用例。两类测试都引用工具目录，不复制问题正文、Session 事件、工具说明或评判规则。

未登录访问者可以发起受限制的测试，但不能修改用例、修改工具定义、修改冻结 Mock 返回、发布正式结果或读取内部工件。登录继续保留给维护和发布操作，不再作为普通测试的前置条件。

## 2. 为什么要单独设置“测试运行”

如果直接在用例库页面增加大量运行选项，会出现三个问题：

1. 浏览和运行混在一起。用户只是查看用例时，也会面对模型、工具、上下文、重复次数等配置；
2. 长上下文测试和交叉测试需要队列、进度、取消、耗时和结果区域，用例详情页会越来越复杂；
3. 如果把完整 Session 同时保存成“长上下文用例”和“上下文压缩 Session”，就会维护两份相同数据，版本很容易不一致。

因此采用“目录与执行分离”的方式：

```text
用例库 ── case_id ──────────→ 对比用例：两种整体实现诊断 × 重复 3 次或 5 次

上下文压缩模块 ─ session_id ─┬→ 压缩用例：只生成四份上下文
                              ├→ 压缩用例：运行当前组合
                              └→ 压缩用例：原生 4×1（默认）/ 交叉诊断 4×2（显式），每格 1 次

工具目录 ─ tool_id ─────────→ 上述需要工具的测试
```

## 3. 用户与权限

### 3.1 未登录访问者

允许：

- 查看公开用例和公开工具；
- 选择一套公开用例；
- 在用例允许的公开 Mock 工具中选择本次可见工具；
- 发起一次对比用例测试；
- 为一个压缩用例生成四份上下文；
- 在限额允许时运行当前组合、原生 4×1 或交叉诊断 4×2；
- 查看自己本次测试的排队、运行阶段、结果和公开证据；
- 使用浏览器中的匿名编号查看近期测试记录。

不允许：

- 输入或覆盖问题正文、系统提示词和评判规则；
- 使用未公开工具、真实外部工具或真实用户数据；
- 修改冻结 Mock 返回；
- 修改用例、工具或上下文源文件；
- 指定任意模型地址、密钥或数据库连接；
- 把测试结果发布到公告页或正式指标；
- 查看完整内部提示词、内部错误堆栈、模型密钥和未脱敏工件。

### 3.2 登录维护者

除匿名访问者的能力外，还可以：

- 创建和修改用例版本；
- 创建和修改工具目录及 Mock 数据版本；
- 配置正式实验条件和重复次数；
- 查看内部运行记录和失败原因；
- 将符合条件的批次发布为正式结果；
- 管理匿名测试限额和队列。

## 4. 页面结构

### 4.1 一级导航

建议增加一级模块：

```text
测试运行
├─ 开始测试
├─ 测试进度
└─ 我的测试
```

第一版也可以只实现 `/test/` 一个页面，通过页面内部步骤完成配置、进度和结果展示；等运行记录增多后，再拆分“测试进度”和“我的测试”。

### 4.2 与现有页面的职责关系

| 模块 | 主要职责 | 是否发起运行 |
| --- | --- | --- |
| 公告 | 系统摘要、正式批次指标、代表性实例入口 | 否 |
| 用例库 | 浏览、搜索和查看固定用例定义 | 否 |
| 上下文压缩 | 创建、查看和版本化完整 Session，生成压缩工件 | 只在用户点击压缩按钮后运行 |
| 工具目录 | 浏览工具能力、参数和风险等级 | 否 |
| 测试运行 | 选择条件、创建任务、查看进度和本次结果 | 是 |
| 实例展示 | 展示已经公开的用例详情、调用明细和交叉结果 | 否 |

用例库、上下文压缩模块和工具目录中的“开始测试”按钮只负责携带编号跳转：

```text
/test/?case_id=tool-route-001&tool_id=file.search
/test/?session_id=session-context-engine-debug-01
```

测试运行页面收到编号后，再从服务端读取对应的用例版本或 Session 版本。前端链接中不携带问题正文、Session 正文、工具 Schema、Mock 返回或评判规则。

### 4.3 上下文测试的数据来源

用例库不再保存“长上下文用例”。普通固定问题仍由用例库管理；所有长上下文数据统一由上下文压缩模块管理。

上下文压缩模块保存：

- `session_id` 和 `session_version`；
- 有顺序的用户消息、助手消息、工具调用和工具返回；
- 每个事件的编号、时间和配对关系；
- Session 允许使用的公开 Mock 工具；
- 用于完整测试和交叉测试的评判配置；
- Session 来源、版本哈希和公开状态。

测试运行模块只引用 Session，不复制事件。长上下文库页面如果继续保留，也只是 Session 的浏览入口，不再维护另一套长上下文用例。

### 4.4 最新用户消息作为当前输入

选择一份 Session 发起上下文测试时，以该 Session 最新一条有效的 `user_message` 作为本批次发送给 Agent 的当前输入。

```text
Session 事件 1 ... N-1  → 历史上下文，参与选择、摘要、引用或省略
Session 事件 N          → 最新 user_message，作为当前输入，只发送一次
```

需要注意：

- 当前输入必须是最新一条有效用户消息；
- 当前输入不进入普通历史压缩，避免被摘要或省略；
- 当前输入不能既留在历史中又追加到末尾，否则会重复发送；
- 该消息之前的助手消息、工具调用和工具返回属于历史；
- 如果 Session 末尾是助手消息或工具结果，服务端向前找到最新用户消息，并要求它之后不存在未完成的新一轮；
- 如果最新用户消息之后已经有对应的助手最终回答，该 Session 默认视为“已完成历史”，不能直接把同一消息再次作为当前输入；维护者需要复制为新版本并删除这次回答，或明确指定新的最新用户消息；
- 创建任务时冻结 `current_event_id`，后续 Session 增加新消息不会改变已经创建的批次。

运行任务至少记录：

```text
session_id
session_version
session_hash
current_event_id
current_message_hash
```

四种上下文方式和全部实现都必须使用同一个 `current_event_id`。

## 5. 开始测试页面

页面使用四个连续步骤，不做聊天输入框。

### 5.0 手动触发原则

所有会产生明显耗时或模型费用的操作都必须由用户点击按钮后执行。

以下操作不得自动触发压缩测试或 Session 交叉测试：

- 生成或修改代码；
- 生成静态页面；
- 编译前端资源；
- 启动 engine、data 或 web 服务；
- 初始化或升级数据库；
- 打开“测试运行”“长上下文库”或“Session 交叉验证”页面；
- 部署服务或发布静态文件；
- 读取已有用例和运行结果。

页面首次打开时只读取测试选项和已经存在的结果，不创建任务。后端也不能因为发现“工件缺失”就自动补跑。缺少结果时显示“尚未运行”，由用户决定是否运行。

### 第一步：选择测试方式

| 测试方式 | 用途 | 主要输出 |
| --- | --- | --- |
| 对比用例 | 将一个固定问题交给两种整体实现（诊断对照），每种重复 3 次或 5 次 | 两种实现的结果分布、调用链、Token、时长和评判结果；批次附 `config_hash` 与固定条件 |
| 压缩用例：生成上下文 | 比较一份 Session 在四种上下文处理方式下的输入变化，不运行 Agent | 压缩前后文本、事件处理结果、Token 和构建耗时 |
| 压缩用例：运行当前组合 | 选择一份已经生成的上下文工件和一种 Agent，运行 1 次 | Agent 回答、调用链、评判结果以及完整 Token、时长 |
| 压缩用例：原生 4×1 | 将四种冻结上下文交给同一原生底座（唯一自变量 = 上下文方式） | 4 个单次样本和每格运行证据 |
| 压缩用例：交叉诊断 4×2 | 将四种冻结上下文分别交给两种旧整体实现（非单变量，显式触发） | 8 个单次样本和每格运行证据 |

### 第二步：选择测试对象

根据测试方式显示不同数据：

- 对比用例测试读取公开固定用例；
- 压缩用例的三个操作都读取上下文压缩模块的公开 Session；
- 原生 4×1 与交叉诊断 4×2 只读取同时具备四种上下文配置、公开 Mock 工具和交叉评判配置的 Session。

对比用例展示题号、场景、用例版本和问题摘要。压缩用例展示 Session 标题、Session 版本、事件数量、最新用户消息摘要、预计 Token 和预计时长。问题正文按 `case_id + case_version` 读取；压缩用例的当前输入按 `session_id + session_version + current_event_id` 读取。

### 第三步：选择工具与运行条件

#### 工具选择

未登录访问者可以从该用例允许的公开 Mock 工具中选择“本次对 Agent 可见的工具”。

```text
测试对象允许工具 ∩ 公开工具 ∩ 当前系统可用工具 = 页面可选工具
```

普通测试不能选择不在用例允许范围内的工具；上下文测试不能选择不在 Session 允许范围内的工具。两者都不能更改工具参数定义和 Mock 返回。

工具选择放在“测试运行”模块。用例库和 Session 页面只提供“开始测试”入口，不在目录卡片中展开完整勾选器。

#### 三层工具范围

服务端使用三层范围计算页面最终可选工具：

```text
工具目录中的公开可用 Mock 工具
  ∩ 用例或 Session 允许的工具范围
  ∩ 当前环境已经启用且具有冻结 Mock 返回的工具
  = 本次页面可以勾选的工具
```

三层数据分别承担不同职责：

| 数据 | 含义 | 用户能否修改 |
| --- | --- | --- |
| `allowed_tool_ids` | 当前用例或 Session 允许进入候选范围的工具 | 否 |
| `default_visible_tool_ids` | 页面初始勾选的标准工具集合 | 可以取消或补选允许范围内的工具 |
| `selected_tool_ids` | 用户这一次实际提交给 Agent 的可见工具 | 可以修改，但必须是 `allowed_tool_ids` 的子集 |

评判器使用的正确工具和正确调用顺序单独保存在内部评判配置中，不能通过 `required_tool_ids`、“推荐工具”或高亮样式暴露给公开页面。否则用户可以从页面直接看出标准答案，工具选择率实验失去意义。

`default_visible_tool_ids` 应包含正确工具和合理的相似工具，用于构成标准实验条件，但页面只统一标记为“默认工具范围”，不能说明哪一个是正确工具。

#### 页面交互

工具选择区建议包含：

- 搜索工具名称和说明；
- 按工具方向筛选，例如文件、检索、日历、邮件、代码、数据库；
- “使用默认范围”；
- “选择全部允许工具”；
- “清空选择”；
- 每个工具显示名称、普通说明、只读状态、是否使用冻结 Mock、参数数量；
- 页面底部显示已选择数量、工具 Schema 预计 Token 和服务端最大数量；
- 提交前展示本次工具目录版本和选择结果。

不展示：

- 标准答案中的期望工具；
- 哪些工具属于干扰项；
- Mock 返回的完整内容；
- 内部权限条件和评判规则；
- 未公开或没有 Mock 返回的工具。

可以将不可选工具显示为禁用项并给出普通原因，例如“当前用例不允许”或“没有公开 Mock 数据”，但不能泄漏内部安全规则或评判答案。

#### 标准范围与自定义范围

用户没有修改默认勾选时：

```text
tool_selection_mode = DEFAULT
custom_conditions = false
```

用户增加、移除或清空允许范围内的工具时：

```text
tool_selection_mode = CUSTOM
custom_conditions = true
```

自定义范围可以运行，也可以展示结果，但不能进入标准对照指标。页面应明确提示：“你修改了 Agent 可见工具，本次结果只代表自定义条件，不能与公告中的标准结果直接比较。”

移除正确工具时不能提前提示“你删除了正确工具”，因为这会泄漏答案。系统只提示工具范围已经改变，运行结束后再由评判器如实记录工具不可见造成的结果。

允许选择零个工具，用于观察 Agent 是否诚实说明能力限制；该运行同样属于自定义条件。前端不能为了让任务成功而自动补回工具。

#### 不同测试方式的工具选择

| 测试方式 | 是否显示工具选择 | 规则 |
| --- | --- | --- |
| 对比用例测试 | 显示 | 从用例允许范围选择 |
| 压缩用例：生成上下文 | 不显示 | 不运行 Agent，工具目录不是本阶段变量 |
| 压缩用例：运行 Agent | 显示 | 从 Session 允许范围选择 |
| 运行当前交叉实验单元 | 显示 | 从 Session 允许范围选择 |
| 原生 4×1 / 交叉诊断 4×2 | 显示一次 | 全部实验单元必须使用同一工具集合 |

矩阵测试不能让不同实现分别选择不同工具。工具范围必须在批次级冻结：4×1 的唯一变化是上下文方式；4×2 是上下文方式与整体实现的交叉（诊断口径，不能做单变量归因）。

#### 服务端校验

前端提交示例：

```json
{
  "case_id": "tool-route-001",
  "case_version": 3,
  "selected_tool_ids": ["file.search", "file.read"],
  "tool_selection_mode": "CUSTOM"
}
```

服务端不能相信前端传来的 `tool_selection_mode`，必须重新计算：

1. 按版本读取用例或 Session；
2. 读取当前公开工具目录版本；
3. 确认每个 `selected_tool_id` 都属于允许范围；
4. 确认工具当前启用、允许公开并存在冻结 Mock；
5. 计算选择结果是否与默认范围完全一致；
6. 计算工具 Schema Token 是否超过本次预算；
7. 冻结选择结果、工具目录版本、Schema 哈希和 Mock 数据版本；
8. 再创建运行任务。

任一工具越权、版本失效、缺少 Mock 或总 Schema 超出服务端限制时，拒绝创建任务并返回具体的公开错误，不得静默删除工具后继续运行。

运行任务至少记录：

```text
selected_tool_ids
tool_selection_mode
tool_catalog_version
selected_tool_schema_hash
tool_schema_tokens
fixture_set_id
fixture_set_version
custom_conditions
```

页面应同时展示：

- 用例或 Session 的默认工具；
- 用户本次选择的可见工具；
- 当前测试对象期望的工具是否仍然可见；
- 工具风险等级和是否只读；
- 选择变化会不会使本次运行失去标准对照意义。

如果用户移除了期望工具，仍可允许运行，但必须标记为“自定义条件测试”，不能进入正式指标。

#### 运行条件

对比用例测试固定比较三种 Agent 实现，用户选择重复 3 次或 5 次。压缩用例可以只生成上下文，也可以运行当前组合；完整交叉测试固定为四种上下文方式乘三种 Agent 实现，每格只运行一次，不允许匿名用户改变矩阵定义。

匿名测试的模型、温度、单次超时和最大 Token 由服务端固定。对比用例的 `repeat_count` 只能选择 3 或 5；压缩用例每个实验条件固定为 1。后端必须再次校验，不能只依赖前端选项。

#### Agent 循环轮次

设计和页面必须区分两个容易混淆的数量：

| 名称 | 含义 | 匿名测试规则 |
| --- | --- | --- |
| `repeat_count` | 相同条件下把整个实验独立执行几次 | 对比用例为 3 或 5；压缩用例每个条件为 1 |
| `max_agent_steps` | 单次运行内，Agent 最多进行多少轮模型判断和工具结果回传 | 与重复次数独立；第一版由服务端配置并在页面显示 |

一轮 Agent 循环定义为：模型返回一次判断；如果包含工具调用，系统执行允许的 Mock 工具并把结果加入下一轮输入。模型直接给出最终回答时立即结束，不需要为了达到上限继续调用。

```text
第 1 轮：模型判断 → 可能调用工具
第 2 轮：读取工具结果 → 可能继续调用工具或回答
第 3 轮：继续处理或给出最终回答
```

`max_agent_steps` 是上限，不是必须执行数量。普通简单问题可能第 1 轮就结束。

页面必须分别显示“重复运行 3 次/5 次”和“单次最多 N 步”，不能把二者都写成“运行轮次”。`max_agent_steps` 不提供任意数字输入；服务端按用例级别设置上限并把实际值写入批次。维护者修改上限时必须创建新的正式配置版本。

达到上限仍没有最终回答时，运行记录：

```text
stop_reason = MAX_AGENT_STEPS
```

系统保留已经发生的工具调用和模型输出，并明确显示“达到 Agent 轮次上限”，不能伪装为正常完成。

完整 4×3 交叉测试的 12 个实验单元必须使用同一个 `max_agent_steps`。确认窗口显示理论最大模型调用次数：

```text
12 个实验单元 × 最多 3 轮 = 最多 36 次 Agent 模型调用
12 个实验单元 × 最多 5 轮 = 最多 60 次 Agent 模型调用
```

摘要模型调用单独计算，不计入 Agent 循环轮次。

### 第四步：确认并开始

确认页完整展示本次配置：

- 测试方式；
- 用例编号与版本；
- 工具目录版本和选中工具；
- Agent 实现方式；
- 上下文处理方式；
- 模型名称；
- 最大 Token 和超时；
- 预计运行数量；
- 预计最长等待时间；
- 本次结果属于匿名测试还是正式实验。

用户点击“开始测试”后，前端只提交编号和允许的配置字段。

不同测试方式使用不同按钮，不能用一个含义不清的“全部运行”按钮：

| 按钮 | 实际操作 | 是否调用 Agent |
| --- | --- | --- |
| `运行单个 Agent 测试` | 一个用例 × 一个 Agent 实现 × 一次运行 | 是 |
| `只生成压缩结果` | 为所选 Session 生成一份或多份上下文工件，到此结束 | 否，除非一次摘要明确配置为模型摘要 |
| `用该结果运行完整测试` | 读取用户选中的冻结上下文工件，继续运行 Agent、Mock Tools 和评判 | 是 |
| `运行当前实验单元` | 一个上下文方式 × 一个 Agent 实现 × 一次运行 | 是 |
| `运行完整 4×3 交叉测试` | 四种上下文方式 × 三种 Agent 实现，共 12 个实验单元 | 是 |

默认推荐“只生成压缩结果”。压缩完成后页面停留在压缩结果，不自动运行 Agent。用户确实需要验证任务效果时，再点击“用该结果运行完整测试”或“运行当前实验单元”。完整 4×3 交叉测试是耗时操作，必须使用独立按钮并二次确认。

确认窗口至少展示：

- 将创建多少个实验单元；
- 每个单元重复次数；
- 是否会调用摘要模型；
- 是否会调用 Agent 模型；
- 最大 Token；
- 最大运行时长；
- 当前队列任务数；
- 取消后已经发生的模型费用不会撤销。

## 6. 两个模块的具体设计

### 6.1 对比用例测试

请求示例：

```json
{
  "test_type": "comparison-case",
  "case_id": "tool-route-001",
  "case_version": 3,
  "repeat_count": 3,
  "visible_tool_ids": ["file.search", "file.read"]
}
```

服务端必须忽略并拒绝 `message`、`prompt`、`system_prompt`、`tool_schema`、`mock_result`、`model_base_url` 和 `api_key` 等字段。

结果页展示：

- 固定问题和实际模型输入摘要；
- 三种 Agent 各 3 次或 5 次的结果分布；
- 每次运行的工具选择与逐步调用；
- 冻结 Mock 返回；
- 最终回答；
- 工具选择、参数、权限、引用和数字检查；
- 输入与输出 Token；
- 排队、模型、工具和总时长；
- 运行是否有效。

### 6.2 压缩用例：上下文生成阶段

压缩用例拆成两个独立阶段：

1. 生成并检查四份上下文；
2. 用户选择运行当前组合或完整 4×3。

两个阶段分别创建任务、分别记录状态。第一阶段成功后只返回上下文工件，不得自动创建第二阶段任务。

#### 6.2.1 只做上下文压缩

该任务只读取冻结 Session、执行所选上下文处理方式并生成上下文工件，不进入 Agent 循环。

请求示例：

```json
{
  "test_type": "context-compression",
  "execution_scope": "context-only",
  "session_id": "session-context-engine-debug-01",
  "session_version": 1,
  "current_event_id": "evt-0026",
  "context_variants": [
    "full-session",
    "recent-window",
    "single-summary",
    "budgeted-session"
  ]
}
```

结果必须展示：

- 压缩前完整 Session；
- 每种方式实际生成的模型输入；
- 原始 Token、工作 Token、预算和压缩比例；
- 原文保留、压缩表示、引用保留和省略的事件编号；
- 摘要或压缩构建本身的 Token、时长和模型调用次数；
- Session 哈希、上下文哈希、算法版本和 Token 计数器版本。

该阶段明确不执行：

- Agent 模型调用；
- 工具选择和 Mock Tool 调用；
- Agent 最终回答；
- 工具正确率、任务成功率和回答质量评判；
- 4×3 交叉实验。

一次摘要策略需要单独说明摘要来源：

- 使用确定性摘要时，不调用模型；
- 使用模型摘要时，只调用摘要模型，仍然不运行 Agent；
- 页面必须把摘要模型的 Token、时长和费用记入“上下文构建成本”，不能算作 Agent 执行成本。

压缩测试默认每种策略只构建一次，不做重复轮次。因为输入 Session、策略版本和 Token 计数器相同的时候，确定性构建结果应由工件哈希复用，不需要为了得到同一份文本重复运行。

页面提供两种范围：

1. 只生成当前选中的一种上下文方式；
2. 一次生成四种上下文方式的压缩前后对照。

两种范围都必须点击“只生成压缩结果”后才执行。页面加载和代码生成不能触发。

#### 6.2.2 使用压缩结果运行完整测试

用户在压缩结果页面选择一份已生成的上下文工件，再点击“用该结果运行完整测试”。请求必须引用工件编号和哈希，不能让服务端在完整测试过程中悄悄重新压缩。

请求示例：

```json
{
  "test_type": "context-full-run",
  "execution_scope": "full-pipeline",
  "session_id": "session-context-engine-debug-01",
  "session_version": 1,
  "current_event_id": "evt-0026",
  "context_artifact_id": "ctx-artifact-001",
  "context_artifact_hash": "sha256:...",
  "agent_mode": "full-system",
  "visible_tool_ids": ["code.read", "code.search", "file.read"]
}
```

完整测试从冻结上下文工件开始，继续执行：

```text
读取并校验上下文工件
  → 装载所选 Agent 实现
  → 绑定公开 Mock 工具
  → 运行当前问题
  → 记录工具调用和最终回答
  → 执行评判
  → 保存完整运行工件
```

如果工件哈希、Session 版本、`current_event_id`、当前消息哈希或工具目录版本不匹配，完整测试必须拒绝启动，并提示用户重新生成压缩结果。不能自动生成一份新工件后继续运行。

完整测试结果除了 Agent 调用链和评判结果，还要同时引用第一阶段的压缩工件，使用户能够从最终回答回到压缩前后文本。

#### 6.2.3 两阶段成本分开

页面和数据库必须将两阶段成本分开：

| 成本 | 只做上下文压缩 | 完整测试 |
| --- | ---: | ---: |
| Session 读取与序列化 | 记录 | 不重复计算 |
| 压缩或摘要 Token | 记录 | 引用第一阶段数据 |
| 压缩构建时长 | 记录 | 引用第一阶段数据 |
| Agent 输入 Token | 不产生 | 记录 |
| Agent 输出 Token | 不产生 | 记录 |
| Mock Tool 调用 | 不产生 | 记录 |
| Agent 与评判时长 | 不产生 | 记录 |

页面可以展示“合计成本”，但必须同时保留“上下文构建”和“Agent 完整运行”两部分，不能合并成一个无法解释的总数。

### 6.3 压缩用例：Agent 运行阶段

Session 交叉测试在同一份 Session 上生成四份冻结上下文，再分别交给三种 Agent，实现 12 个实验单元。

访问者一次只能选择一个压缩 Session，每个实验单元固定运行一次。压缩用例不提供增加重复次数的入口。

请求示例：

```json
{
  "test_type": "session-cross",
  "session_id": "session-context-engine-debug-01",
  "session_version": 1,
  "current_event_id": "evt-0026",
  "visible_tool_ids": ["code.read", "code.search", "file.read"]
}
```

处理顺序：

```text
读取上下文压缩模块中的固定版本 Session
  → 分离历史事件和最新用户消息
  → 冻结本次工具目录与 Mock 数据
  → 编译四份上下文输入并计算哈希
  → 创建 4×3 共 12 个运行单元
  → 按并发上限进入队列
  → 每格保存 Agent 执行和评判结果
  → 返回压缩前后与结果矩阵
```

四份上下文必须先生成并冻结。三个 Agent 读取完全相同的对应上下文工件，不能各自重新压缩。

为减少等待时间和费用，交叉测试分成三个操作：

1. `生成四份上下文`：只创建完整 Session、最近窗口、一次摘要和按预算压缩的冻结输入，不运行 Agent；
2. `运行当前实验单元`：只运行用户当前选择的一种上下文方式和一种 Agent 实现；
3. `运行完整 4×3`：使用已冻结的四份上下文运行全部 12 个实验单元。

完整交叉测试每格固定只运行一次。它用于观察四种上下文输入与三种 Agent 实现的交叉结果，不在这个模块增加重复实验。

如果四份上下文工件已经存在，且以下字段的组合哈希完全一致，则直接复用，不重新压缩：

```text
session_hash
+ session_version
+ current_event_id
+ current_message_hash
+ strategy_version
+ token_budget
+ tokenizer_version
+ common_rules_version
+ summary_model_version（使用模型摘要时）
```

任一字段变化时才生成新的上下文工件。运行单个实验单元和完整交叉测试都必须读取同一批冻结工件。

### 6.4 轮次和运行数量

页面必须在按钮旁直接显示将要创建的运行数量：

```text
一个对比用例，重复 3 次：3 种 Agent × 3 = 9 个运行
一个对比用例，重复 5 次：3 种 Agent × 5 = 15 个运行
只做上下文压缩：1 个构建任务，0 个 Agent 运行
当前交叉实验单元：1 个 Agent 运行
完整 4×3：12 个运行
```

对比用例不接受 3 和 5 之外的重复次数。压缩用例的完整 4×3 不接受其他重复次数。页面必须显示乘法结果，避免误把“重复 5 次”理解为总共 5 个运行。

系统不得为了补齐重复次数自动继续运行。一次手动提交只执行确认窗口中列出的运行数量；需要增加样本时，由用户再次手动发起。

## 7. 匿名运行与正式结果分开

允许匿名运行后，最重要的规则是：匿名测试不能自动进入公告页和正式指标。

每次运行增加用途字段：

| 值 | 含义 | 能否进入正式指标 |
| --- | --- | --- |
| `PUBLIC_TRIAL` | 未登录访问者发起的测试 | 否 |
| `OWNER_EXPERIMENT` | 维护者按标准条件发起的实验 | 满足发布条件后可以 |
| `SYSTEM_REGRESSION` | 系统回归任务 | 否，单独统计 |

如果匿名用户改变默认工具可见范围，还要记录 `custom_conditions=true`。这类运行可以展示结果，但不能和标准实验直接比较。

只有维护者能够执行发布操作。公告页只读取已经发布并标记为正式的结果。

## 8. 匿名身份和近期记录

不登录不等于完全没有运行身份。第一次进入测试运行页面时，由服务端签发匿名编号和只读访问凭证：

- 浏览器保存不可读敏感信息的 HttpOnly Cookie；
- 数据库存匿名编号的哈希，不保存用户姓名；
- 匿名用户只能读取自己近期发起的未公开测试；
- 清除浏览器数据后不能恢复匿名记录；
- 公开发布的实例不依赖匿名凭证，任何人都能查看。

不建议仅用 IP 地址作为身份。IP 只用于限流和异常检测，不用于展示给用户。

### 8.1 “我的测试”在哪里查看

测试提交成功后立即返回：

```text
job_id
result_url = /test/jobs/{job_id}
```

页面自动进入当前任务详情。顶部导航“我的测试”指向 `/test/my`，按当前匿名 Cookie 查询近期任务。

“我的测试”列表展示：

- 测试名称和测试方式；
- 用例编号或 Session 标题；
- 创建时间；
- 当前状态；
- 已完成单元数和总单元数；
- 实际耗时；
- 是否使用自定义工具范围；
- 查看结果、继续剩余任务或取消按钮。

匿名 Cookie 丢失后不能通过任务编号枚举或读取结果。任务详情接口必须同时校验 `job_id` 和匿名身份。

### 8.2 与公告页相同的结果展示

匿名测试结果复用公告页和实例展示的组件、字段名称与指标解释，避免同一指标出现两套页面口径。

根据测试方式展示：

- 对比用例：结果摘要卡、用例详情、三种 Agent 的重复结果分布、工具调用明细、Token、时长和评判结果；
- 压缩用例只生成上下文：压缩前后文本、事件处理桶、Token、构建时长和上下文哈希；
- 压缩用例运行当前组合：压缩结果摘要、Agent 回答、工具调用、评判和两阶段成本；
- 压缩用例完整 4×3：与公告实例相同的矩阵、压缩前后和单元格下钻。

视觉结构可以相同，但数据归属必须清晰区分：

| 页面 | 数据范围 | 是否正式 |
| --- | --- | --- |
| 公告 | 维护者发布的正式批次 | 是 |
| 实例展示 | 维护者发布的代表性运行 | 是 |
| 我的测试 | 当前匿名身份发起的测试 | 否 |

匿名结果页顶部固定显示：

> 匿名测试结果：只代表本次选择的用例、工具和运行条件，不进入公告指标，也不会自动公开。

如果用户选择了自定义工具范围，还要展示“自定义条件”标签。匿名结果不能因为页面样式与公告相同就被描述为正式实验。

## 9. 费用、并发和滥用控制

开放匿名运行会直接产生模型费用，必须由后端限制，不能只隐藏前端按钮。

第一版建议限制：

| 项目 | 对比用例测试 | 压缩用例：只生成上下文 | 压缩用例：完整 4×3 |
| --- | ---: | ---: | ---: |
| 重复规则 | 三种 Agent 各 3 次或 5 次 | 每种上下文生成 1 份工件 | 每格 1 次 |
| 同一匿名用户并发 | 1 | 1 | 1 |
| 同一匿名用户每日次数 | 10 | 5 | 1 |
| 单任务最大排队时间 | 2 分钟 | 2 分钟 | 5 分钟 |
| 单任务最大运行时间 | 60 秒 | 60 秒 | 15 分钟 |
| 自定义问题 | 不允许 | 不允许 | 不允许 |
| 真实外部工具 | 不允许 | 不允许 | 不允许 |

具体数字做成服务端配置，不写死在前端。

还需要：

- 全局每日 Token 上限；
- 单 IP 和单匿名编号的速率限制；
- 全局并发队列；
- 任务幂等键，防止重复点击重复计费；
- 超限时给出明确的下次可用时间；
- 服务异常、429、余额不足和模型不可用标记为无效运行，不进入能力指标；
- 必要时在达到异常阈值后增加验证码，而不是第一版默认增加复杂交互。

## 10. 运行状态和长任务处理

匿名测试使用后台异步任务。创建接口只负责校验配置、创建任务并返回 `job_id`，前端不能保持一个请求等待 15 分钟。

```text
QUEUED
  → PREPARING
  → BUILDING_CONTEXT
  → RUNNING_AGENT
  → JUDGING
  → COMPLETE

任意阶段还可能进入 INVALID、FAILED、CANCELLED 或 EXPIRED。
```

页面通过任务编号读取状态。进度展示当前阶段、已完成实验单元、总实验单元、排队位置、已用时间和最大时间。Session 交叉测试显示 `3 / 12` 这类真实完成数量，不使用虚构百分比。

匿名用户可以取消自己仍在排队或运行中的任务。取消只停止尚未开始的单元，已经产生的模型费用和运行工件仍然记录。

任务完成后只保存结果和状态，不自动发起下一轮、不自动补跑无效单元，也不自动转为正式实验。无效单元是否重跑由用户查看原因后再次点击按钮决定。

### 10.1 浏览器或网络中断

浏览器关闭、刷新页面、电脑休眠或用户网络断开时，后台任务继续执行，不因前端连接中断而停止。

前端可以优先使用服务器事件或 WebSocket 显示实时进度，但必须提供普通状态查询作为恢复方式。页面重新打开后，通过匿名 Cookie 和 `job_id` 从服务端读取当前状态。

```text
浏览器断开
  → 后台任务继续
  → 运行事件和结果持续写入数据库
  → 用户重新打开“我的测试”
  → 恢复显示真实进度或最终结果
```

前端断开不是取消操作。只有用户点击“取消测试”，后端收到并记录取消请求后，任务才进入取消流程。

### 10.2 后台服务中断

任务、实验单元和阶段状态必须写入 PostgreSQL，不能只保存在进程内存。Worker 领取任务时记录租约和心跳。

如果 engine 或 Worker 中断：

1. 尚未开始的单元保持 `QUEUED`；
2. 正在执行的单元在租约超时后标记为 `INTERRUPTED`；
3. 已经完成的单元和工件保持不变；
4. 整个任务标记为 `PARTIAL`，展示已完成数量；
5. 系统不自动重跑中断单元，避免重复模型费用和重复工具调用；
6. 用户恢复访问后可以点击“继续剩余任务”。

“继续剩余任务”只创建尚未完成单元的新执行记录，并引用原任务：

```text
parent_job_id = 原任务编号
resume_from_job_id = 原任务编号
```

已经 `COMPLETE` 的单元不会重复运行；`INTERRUPTED` 单元是否重跑由确认窗口单独列出，让用户选择。

如果只是 Web 页面或 Nginx 重启，但 engine Worker 仍在运行，任务不受影响。

### 10.3 取消和停止边界

用户点击取消后：

- 队列中尚未开始的单元直接取消；
- 正在等待模型或 Mock Tool 返回的单元发出协作取消信号；
- 无法立即取消的外部模型请求等待当前请求返回，但不开始下一轮；
- 已产生的 Token、耗时和结果照常记录；
- 任务最终显示 `CANCELLED` 或 `PARTIAL`，不能显示为完整成功。

## 11. 接口设计

建议新增公开受限接口，不把现有维护者接口直接取消鉴权。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/api/v1/public/test-options` | 获取公开测试方式、用例、工具和服务端固定条件 |
| `POST` | `/api/v1/public/test-jobs` | 创建匿名测试任务 |
| `GET` | `/api/v1/public/test-jobs/{job_id}` | 查看自己任务的状态和摘要 |
| `GET` | `/api/v1/public/test-jobs/{job_id}/results` | 查看自己任务的公开字段结果 |
| `POST` | `/api/v1/public/test-jobs/{job_id}/cancel` | 取消自己的任务 |
| `GET` | `/api/v1/public/test-jobs` | 查看本匿名编号的近期任务 |

在内部处理上应区分两类任务，即使第一版继续使用统一的 `test-jobs` 路径：

- `context-only`：只生成上下文工件；
- `full-pipeline`：必须引用已有上下文工件，再运行 Agent 和评判。

不建议让一个长请求先压缩再自动执行完整流程，因为用户无法在中间检查压缩结果，也无法控制是否继续产生模型费用。

维护者接口继续保留鉴权：

- 创建或修改用例和工具；
- 创建正式多次实验；
- 查看内部工件；
- 发布正式结果；
- 管理队列和限额。

## 12. 数据库记录

可以复用现有批次、运行和上下文工件表，在任务或批次记录中增加以下字段：

| 字段 | 说明 |
| --- | --- |
| `requester_type` | `ANONYMOUS`、`OWNER` 或 `SYSTEM` |
| `anonymous_id_hash` | 匿名编号哈希；维护者运行为空 |
| `run_purpose` | `PUBLIC_TRIAL`、`OWNER_EXPERIMENT` 或 `SYSTEM_REGRESSION` |
| `test_type` | `COMPARISON_CASE` 或 `COMPRESSION_CASE` |
| `target_type` | `CASE` 或 `SESSION` |
| `case_id` / `case_version` | 对比用例测试使用；压缩用例为空 |
| `session_id` / `session_version` | 压缩用例使用；对比用例为空 |
| `current_event_id` | 本批次作为当前输入的最新用户消息事件编号 |
| `current_message_hash` | 当前输入正文哈希，防止 Session 修改后继续复用旧工件 |
| `execution_scope` | `CONTEXT_ONLY` 或 `FULL_PIPELINE` |
| `context_artifact_id` | 完整测试引用的冻结上下文工件；只压缩任务为空 |
| `parent_job_id` | 完整测试对应的压缩任务编号，用于两阶段追溯 |
| `repeat_count` | 整个实验重复次数；对比用例为 3 或 5，压缩用例每格为 1 |
| `max_agent_steps` | 单次 Agent 最大循环步数；与 `repeat_count` 独立，由服务端配置版本确定 |
| `actual_agent_steps` | 单元实际执行的 Agent 轮次 |
| `stop_reason` | 正常完成、达到轮次上限、取消、中断或错误 |
| `custom_conditions` | 是否改变了标准工具范围等条件 |
| `requested_tool_ids` | 本次用户选择的公开工具编号 |
| `quota_snapshot` | 创建任务时使用的限额版本 |
| `expires_at` | 匿名内部结果的过期时间 |
| `publishable` | 是否具备进入正式发布流程的资格；匿名测试固定为 false |

普通测试的问题正文、允许工具和评判条件从版本化用例读取。上下文测试的历史、当前输入、允许工具和评判配置从版本化 Session 读取。两类正文都不复制到测试任务表，运行工件只保存引用、版本和哈希用于追溯。

## 13. 部署方案变化

当前“公开站只有静态文件”的部署方式不能支持匿名测试。新方案需要区分两个地址：

```text
浏览器
  ├─ 静态页面                    Nginx / CDN
  └─ /api/v1/public/test-*       公共运行入口
                                      │
                                      ▼
                               限流与任务队列
                                      │
                      ┌───────────────┴───────────────┐
                      ▼                               ▼
                  engine                          data / PostgreSQL
```

公共运行入口只开放明确列出的测试接口。维护者接口、data 内部接口、发布接口和管理接口仍然要求登录或内部令牌。

模型密钥只保存在 engine 服务端。浏览器不能看到模型密钥、数据库凭据和 data 内部令牌。

## 14. 页面结果的去向

测试完成后有三个去向：

1. “测试运行”显示本次任务的即时结果；
2. “我的测试”在保留期内显示匿名用户自己的近期结果；
3. 维护者选择有代表性的正式实验发布后，“实例展示”和公告页才出现公开实例。

匿名测试不会自动出现在实例展示中。这样可以避免访客测试污染公开案例，也能保持公告页数据稳定。

## 15. 第一版建议范围

第一版先做：

1. 新增“测试运行”单页；
2. 未登录可选择公开用例和用例允许的 Mock 工具；
3. 支持三种 Agent × 重复 3 次或 5 次的对比用例测试，以及只生成上下文的压缩用例测试；
4. 支持用户从压缩结果手动发起一次完整测试；
5. Session 交叉测试先限制为一套 Session、每格一次；
6. 异步任务、进度查询、取消和匿名限额；
7. 匿名测试结果不进入正式指标；
8. 登录仅用于维护、内部工件和发布；
9. 压缩和交叉测试全部手动触发，任何构建、启动和页面访问都不会自动运行；
10. 支持单个实验单元运行，完整 4×3 使用独立确认按钮；
11. 同配置的冻结上下文工件按哈希复用，避免重复压缩。

第一版暂不做：

- 自由输入问题；
- 用户上传文件或 Session；
- 用户提供模型密钥；
- 真实第三方工具；
- 对比用例 3 次或 5 次之外的任意重复次数；
- 匿名结果自动公开；
- 匿名用户之间共享未发布任务。

## 16. 后续需要同步修改的旧设计

本设计确认后，以下旧口径需要统一更新：

- “公开访问者不能发起运行”改为“公开访问者可以发起受限制的匿名测试”；
- “所有创建运行都必须登录”改为“维护、正式实验和发布必须登录，匿名测试使用独立公共接口和限额”；
- “公网只部署静态页面”改为“静态页面与受限公共运行入口分离部署”；
- “访客不能选择工具”改为“访客只能从用例允许的公开 Mock 工具中选择可见工具”；
- 正式批次、公告指标和实例发布仍保持维护者控制。

涉及文档至少包括：

- `docs/product/产品目标与使用方式.md`；
- `docs/architecture/系统架构与运行流程.md`；
- API、权限、部署和数据库设计；
- 页面导航与“测试运行”模块说明。

## 17. 验收标准

设计落地后应满足：

1. 未登录访问者能从公开用例或公开 Session 进入测试运行页面；
2. 用例库只维护普通固定用例，长上下文统一由上下文压缩模块维护；
3. 测试运行不复制用例正文、Session 事件和评判规则；
4. 访客只能选择当前用例或 Session 允许的公开 Mock 工具；
5. 对比用例和压缩用例使用统一任务基础能力，但保持各自的数据来源和运行规则；
6. 匿名测试和正式实验在数据库、指标和发布流程中明确分开；
7. 匿名测试不会自动进入公告页；
8. 限流、并发、Token、时长和每日费用由后端执行；
9. 公共接口不接受任意问题、系统提示词、工具定义、Mock 返回、模型地址和密钥；
10. 长任务能显示真实阶段和完成单元数量；
11. 登录仍然保护用例维护、Session 维护、工具维护、内部工件和正式发布；
12. 代码生成、页面生成、服务启动和页面访问不会创建测试任务；
13. 完整 4×3 按钮在提交前明确显示 12 个实验单元、重复次数、最大时长和 Token 上限；
14. 用户可以只生成压缩前后工件，或只运行当前选中的一个交叉实验单元；
15. 系统不会自动补跑无效单元或自动增加重复轮次；
16. “只做上下文压缩”和“使用压缩结果运行完整测试”是两个独立任务；
17. 压缩任务完成后不会自动调用 Agent、Mock Tools 或评判器；
18. 完整测试必须引用用户确认过的上下文工件编号和哈希；
19. 上下文构建成本与 Agent 完整运行成本分别记录和展示；
20. 同一批次以 Session 最新一条有效用户消息为当前输入，并冻结 `current_event_id`；
21. 当前输入不参与历史压缩，也不会重复发送。
22. 对比用例固定比较三种 Agent，每种只允许重复 3 次或 5 次；
23. 压缩用例固定 4×3 且每格 1 次，不能与对比用例的重复规则混用；
24. 页面和接口明确区分 `repeat_count` 与 `max_agent_steps`。
