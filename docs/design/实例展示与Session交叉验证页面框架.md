# 实例展示与 Session 交叉验证页面框架

## 1. 本阶段目标

本阶段只设计公开页面的信息结构，不运行 Agent、不执行上下文验证，也不生成实验数字。

公告页继续负责展示系统摘要、最新批次汇总和少量代表性用例。实例展示不再重复这些内容，只承接公告页中某个具体实例的证据下钻。

## 2. 实例展示的三个页面

| 页面 | 地址 | 只负责展示 |
| --- | --- | --- |
| 用例详情 | `/showcase/` | 题号、版本、场景、问题原文、固定实验条件、应调用工具、禁止调用工具和回答约束 |
| 用例调用明细 | `/showcase/tools` | 某个实例、Agent 模式和运行编号对应的逐步工具调用、参数、冻结 Mock 返回、状态与证据位置 |
| Session 交叉验证 | `/session-cross/` | 同一 Session 的四种上下文输入、压缩前后内容、事件处理结果和 4×3 交叉实验结果 |

原来的“批次概览”和“对照结果”属于公告页的汇总信息，不再作为实例展示的独立入口。原来的“单次运行”拆入“用例详情”和“用例调用明细”。旧地址只保留跳转，避免已有链接失效。

## 3. 页面之间的关系

公告页中的普通用例卡片携带 `case_id`；Session 交叉验证卡片携带 `session_id`。如果已经有公开运行，还可以携带 `run_id`。

用例详情页使用 `case_id` 展示普通固定输入和约束，用户需要查看执行过程时进入用例调用明细。上下文压缩和交叉验证不读取长上下文用例，直接使用上下文压缩模块中的版本化 Session。

公开页面只能读取发布后的静态工件，不能发起模型调用、工具调用、压缩任务或数据库操作。

## 4. Session 交叉验证页面结构

Session 交叉验证合并为一个页面，避免在“原始 Session”“四种模型输入”“实验结果”三个页面之间来回切换。

### 4.1 实验对象

展示以下字段：

- `session_id`、`session_version`；
- Session 标题和用途；
- 作为本批次当前输入的最新 `user_message` 及其 `current_event_id`；
- 原始 Session 哈希；
- 事件数、用户消息数、助手消息数、工具调用对数量；
- 原始 Token 数和计数器版本。

### 4.2 固定交叉条件

四种上下文方式：

1. 完整 Session：不压缩的原文基准；
2. 最近窗口：只保留预算范围内的最近事件；
3. 一次摘要：把较早历史整理成一份摘要；
4. 按预算选择和压缩：使用项目算法选择原文、摘要、引用或省略。

三种 Agent 实现：

1. 裸 Tool Calling；
2. LangGraph ReAct；
3. 完整工程模式。

同一轮交叉实验必须固定 Session 版本、`current_event_id`、模型、温度、工具目录、冻结 Mock 数据和评判标准，每个实验单元固定运行 1 次。`current_event_id` 之前的事件作为历史，最新用户消息作为当前输入并且只发送一次。四种上下文方式先各生成一份冻结输入，再分别交给三种 Agent，形成 12 个实验单元。

### 4.3 压缩前后展示

这一部分不能只显示压缩率，必须同时展示文本和事件变化。

左侧固定展示压缩前的完整 Session：

- 用户和助手消息；
- 工具调用与工具返回；
- 事件编号和时间顺序；
- 失败、纠正和被后续决定替换的内容。

右侧展示所选上下文方式实际发送给模型的内容：

- 最终消息顺序；
- 原文保留内容；
- 结构化摘要或文本摘要；
- 引用；
- 省略说明；
- 公共规则与当前问题。

顶部展示原始 Token、模型输入 Token、压缩比例、预算、构建耗时和上下文哈希。底部按“原文保留、压缩表示、引用保留、省略”四类列出事件编号，使每个变化都能回到原始 Session 定位。

### 4.4 交叉结果矩阵

矩阵行为四种上下文方式，列为三种 Agent 实现。每个单元格在正式发布后展示：

- 有效运行数和无效运行数；
- 任务成功情况；
- 工具选择与参数是否正确；
- 当前约束和关键事实是否保留；
- 输入 Token、输出 Token、总时长；
- `run_id` 与公开工件入口。

压缩构建成本和 Agent 执行成本必须分开记录，不能把摘要或压缩消耗隐藏在 Agent 输入指标里。

## 5. 空数据规则

当前阶段没有正式交叉验证数据，所有数据区域统一显示“暂无已发布数据”或“尚未运行”。

- 不读取旧的 Session 交叉验证示例填充新框架；
- 不展示 `0%`、`0 ms`、`0 token` 等容易被误解为实测的数字；
- 不生成虚构的工具调用、模型回答或结果矩阵；
- 不在公开页面提供运行按钮；
- 只有正式发布工件存在时才替换空状态。

## 6. 后续数据接入顺序

1. 先接入公开用例详情；
2. 再接入该用例的逐步调用工件；
3. 接入原始 Session 和四份冻结上下文输入；
4. 最后接入 12 个实验单元的正式结果；
5. 数据接入完成后再进行页面验证，本阶段不运行验证。
