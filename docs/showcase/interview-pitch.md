## 1. 三十秒电梯介绍

> 我做了一个 LLM Agent 的对照评测平台。核心问题是:换一个上下文策略、换一个
> 温度、少给一个工具,Agent 的行为到底变不变?平台把"实验"做成一等公民——
> 模板定义唯一自变量、冻结其余条件、逐运行记账,跑完正式规模的真实验后,经
> 校验发布成公开结果站。目前 **7 类实验、15 个正式批次、198 次运行
> (158 有效 + 40 无效,无效也如实展示)**,得出了几个可复述的结论。

三个钩子:对照实验方法学、真实规模、诚实的数据口径。

## 2. 系统架构(一页讲完)

```
engine(FastAPI, :8090)          ← 实验编排:模板计划、单运行执行、统计重算
   │  逐运行登记 + 事件流
   ▼
data(Java/Spring, :18081)       ← 唯一事实真源:运行/事件/判定落 PostgreSQL
   │
   ▼
PostgreSQL(touchstone)
   │  统计快照工件(artifacts)
   ▼
publisher(Node)                 ← 发布投影:schema 校验 + 敏感字段扫描 + 哈希核对
   │                            │  门槛不达标 / 校验失败 → 拒绝发布,不部分发布
   ▼
web(静态站)                     ← 五段结构,零后端调用,只消费 showcase-data
```

一句话概括:**评测链路里每个数字都可下钻、可对账、可被拒绝发布**。

## 3. 方法学(和"跑个 demo"的差距)

1. **单一变量控制**:每个实验模板只动一个变量,其余全部冻结——
   - 工具返回用 fixture 固定(0 毫秒、内容不变);
   - 模型配置写入运行快照并计算 `config_hash`,同配置必同哈希;
   - 统计时哈希不一致的样本直接排除(排除原因落表)。
2. **有效性分层**:每次运行先判 VALID / INVALID。基础设施失败(限流、服务
   卡死、余额)不冒充任务失败,单列不计入分母;每组有效样本达到正式门槛
   (每变体 ≥3 次,压缩单元 ≥1 次)才允许发布。
3. **发布即校验**:schema 校验 + 禁止字段扫描 + 逐运行哈希核对 + 引用完整性
   (report 引用的 run 必须已发布),任何一条不过整批拒绝。
4. **证据链**:每个指标下钻到组成它的单次运行,运行有 11 段证据链
   (固定输入 → 上下文构建 → 工具结果 → 输出检查 → 判定)。

## 4. 实验数据故事(挑 2~3 个讲,别念全表)

### 故事 1:步数上限有硬边界(最推荐)

> 最大步数实验(多工具数据用例):**3 步上限下 3/3 全部触顶未收尾,放宽到
> 4 步起 3/3 全部正常收尾**——该用例的最小可行上限就是 4。生产含义直接:
> 上限配 3 看着省 token,但任务全废。

### 故事 2:工具发现有真实成本

> 把"全量给工具"换成"只给搜索入口"(基础单工具用例):平均**多走 1 轮
> (3 vs 2 步)、输入 token +35%(2153 → 2911)、中位时长 2.9 倍
> (4.4s → 12.9s)**。搜索式工具提供不是免费的,它自己吃轮次和上下文。

### 故事 3:上下文可以压到 1/4 而不掉底线

> 上下文策略对照(3 个 Session 用例 × 3 策略 × 5 次,43/45 有效):抽取式
> 压缩把工作上下文压到**原始的 26.4%**,同时全部变体四项质量断言
> (强制项保留 / 关键事实出现 / 注入隔离 / 禁用事实泄漏)**100% 达标**。
> 压缩预算化可行,且有质量底线证明。

### 备选:温度不敏感(证伪同样是结论)

> 温度 0.0 → 0.7:各档轮次一致(多工具用例 3 步)、全部正常收尾、中位时长
> 14.6s ~ 32.2s 与温度无单调关系。冻结数据 + 该类用例下,温度不是敏感因子。
> ——对照实验的价值之一就是**证伪**。

### 全部 7 类实验的真实结论速览

| 实验 | 变体 | 核心数字 | 结论 |
|---|---|---|---|
| 上下文策略对照 | 完整/抽取/混合 | 26.4% 工作上下文;质量断言 4/4 | 压缩可行不掉底线 |
| 压缩方法对照 | 抽取式/混合式 | 1 步 vs 3~4 步收尾 | 同预算下执行画像不同 |
| 最大步数稳定性 | 3/4/5 步 | steps-3 触顶 3/3,steps-4 起全正常 | 最小可行上限 = 4 |
| 工具提供方式 | 全量/搜索 | +1 轮、token +35%、时长 ×2.9 | 工具发现有成本 |
| 工具可用性降级 | 完整/移首选/移首选+替代 | 三档全部收尾;无效集中在最严变体 | 能收尾但无效率是代价 |
| 温度稳定性 | t0.0~t0.7 | 轮次一致、无单调趋势 | 该场景下温度不敏感 |
| 治理开关对照 | 关/标准 | 轮次与输入 token 一致 | 行为面无差异(合规判定未发布) |

## 5. Debug 故事(面试官最爱,留足时间)

### 故事 A:供应商"温水悬挂"的完整诊断(最亮眼)

**现象**:约 20~30% 的运行被 600 秒熔断;但事件流显示同一次运行里,模型前
4 次调用 3~12 秒就返回——服务商明明很快。

**定位**:逐事件对账,卡死的永远是多轮工具调用后、上下文最长的那一拍:
`model.requested` 发出后彻底静默,直到 600s 总闸强杀。

**对照实验**(本地假服务商 + 引擎同款客户端链路,timeout=30s):

| 假服务商行为 | 客户端行为 |
|---|---|
| 连接后一个字节不发 | **30.1 秒准时 ReadTimeout**(超时配置本身正确) |
| 每 2 秒发一次 SSE 心跳,永不给正文 | **永不超时**,挂到外层 120s 看门狗才断 |

**根因**:httpx 读超时度量"两次收到字节的间隔",SSE 心跳也是字节,把计时器
无限重置。服务商对个别长请求"接单不干活":连接活着、心跳在发、正文永远
不来。我们的超时只防"彻底沉默",防不了"光说稍等不干活"。

**修法**:内容级空闲看门狗——心跳不算数,90 秒无真实内容即断开重拨
(`EVAL_LLM_IDLE_TIMEOUT_S`);600s 总闸保留兜底。

**讲点**:现象 → 数据 → 对照实验 → 根因 → 方案,完整排查闭环。

### 故事 B:跨语言哈希与统计口径

- **跨语言哈希**:发布链 Python 产工件、Node 校验。Python `json.dumps(1.0)`
  输出 `1.0`,JS `JSON.stringify(1)` 输出 `1`——浮点序列化差异导致哈希
  校验全挂。统一整数化解决,并迁移存量工件。
- **无效双计**:无效运行 = excluded + failed,被熔断的运行两张表都进,
  页面显示 56 次、数据库实际 34 次。对账发现后改为"物理尝试 − 有效",
  修正到 32,与运行库完全一致。
- **预算记账**:压缩用例观察结果未预留 token,工作上下文 8389 > 预算 8192,
  确定性 INVALID。给 turn 预算加 2048 观察预留后复跑 VALID。

**讲点**:不信任中间层数字,习惯做端到端对账。

## 7. 追问速答

| 追问 | 一句话答案 |
|---|---|
| 为什么无效也要展示? | 方法学诚实:无效是基础设施失败,不冒充失败样本也不藏,分母口径才可信 |
| 样本量够吗? | 每变体 ≥3 是"最小正式样本"门槛,统计里标了样本等级,不冒充大样本 |
| 怎么保证可复现? | 冻结 fixture + config_hash 一致性 + 配置快照与随机种子随运行存档 |
| 最大技术挑战? | 评测链路的"真":每个数字可下钻、可对账、可拒绝发布 |
| 供应商挂了怎么办? | 两级硬熔断(600s+15s)保证只损失一次样本不拖死批次;看门狗是下一步 |
| 为什么自己造不用现成? | 需要对照实验的一等公民抽象(模板/变体/冻结条件),现有 eval 框架面向单次打分 |
