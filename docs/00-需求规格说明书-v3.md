## 当前实现基线（2026-07-29）

以下能力已经实现，后续开发必须在此基线上增量演进，不得退回仅靠 Prompt 的软约束：

1. **显式 Route 边界**：代码先生成不可变 `RouteDecision`，再从 `RouteExecutionPolicyRegistry` 读取允许的真实 Skill Command、WebSearch 权限和模型等级；不再把工具交给付费模型自主选择。
2. **上下文与记忆**：Redis 保存强类型当前会话短期状态，PostgreSQL 保存完整归档；LangChain4j 按用户、标的、语义和时间检索跨会话摘要，再按消息数和保守 Token 预算生成每请求隔离的只读窗口，不无限拼接历史，也不覆盖 Redis/PG 原始记忆。
3. **CLI 契约硬规则**：stock-analysis-skill JSON 必须通过 Schema、`asOf`、数据质量和追高限制校验；不允许用自然语言绕过行情时效和方向性结论规则。
4. **RAG 质量底线**：向量检索最低相似度为 `0.55`；注入模型的知识携带 score、来源、置信度、有效期和 Embedding 版本等证据。
5. **运行审计**：一次 Skill 推理对应一个 Agent Run，持久化工具 Action、Observation、策略拒绝、耗时、错误和最终回答；SSE 返回 `runId`，支持最近运行查询和按步骤回放。审计三表 DDL 已于 2026-07-28 在 PostgreSQL 执行完成。
6. **安全配置**：API Key 和数据库密码只从环境变量读取，不允许提交真实密钥。
7. **付费模型硬门禁**：业务层只能通过要求 `PaidModelPermit` 的 `PaidAnalysisClient` 调用 DeepSeek；原始 `DeepSeekClient` 为包内实现。
8. **共享外部搜索**：Java 只调用 `web-search-wrapper` 固定契约，Wrapper 负责逐 Agent 鉴权、限流、缓存、熔断和 SearXNG 结果标准化；SearXNG 不承担 Intent、Route 或答案生成。

当前仍使用单表 `knowledge_chunks`。`public_knowledge`/`private_knowledge` 双表和游客模式属于后续目标设计，未完成迁移前不得把目标结构描述为已上线能力。

### 1.1 Route-Intent-Skill 固定映射

映射由 `RouteExecutionPolicyRegistry` 在代码中维护，Prompt 和模型不得扩大权限。

| RequestRoute | 兼容 Intent | 真实能力 | WebSearch | ModelPolicy |
|---|---|---|---|---|
| `GENERAL_CHAT` | `GENERAL_CHAT` | 无 | 禁止 | `LOCAL_ONLY` |
| `KNOWLEDGE_QA` | `INVESTMENT_QA` | PgVector | 禁止 | `LOCAL_ONLY` |
| `EXTERNAL_RESEARCH` | `INVESTMENT_QA` | 无 | 必须 | `LOCAL_ONLY` |
| `MARKET_FACT` | `STOCK_ANALYSIS` | `stock-analysis-skill: stock` | 禁止 | `TEMPLATE_ONLY` |
| `SECTOR_FACT` | `STOCK_ANALYSIS` | `stock-analysis-skill: sector` | 禁止 | `TEMPLATE_ONLY` |
| `SECTOR_ATTENTION` | `STOCK_ANALYSIS` | `stock-analysis-skill: sector` | 必须 | `LOCAL_ONLY` |
| `STOCK_DECISION` | `STOCK_ANALYSIS` | `stock-analysis-skill: stock` | 默认禁止 | `PAID_AFTER_VALIDATED_SKILL` |
| `PORTFOLIO_DECISION` | `PORTFOLIO_ANALYSIS` | `stock-analysis-skill: portfolio`，必要时受控补充 `stock` | 默认禁止 | `PAID_AFTER_VALIDATED_SKILL` |
| `QUANT_DECISION` | `PORTFOLIO_ANALYSIS` | `stock-analysis-skill: quant/sector` | 默认禁止 | `PAID_AFTER_VALIDATED_SKILL` |
| `SECTOR_ANALYSIS` | `PORTFOLIO_ANALYSIS` | `stock-analysis-skill: sector` | 默认禁止 | `PAID_AFTER_VALIDATED_SKILL` |
| `MARKET_CAUSAL_ANALYSIS` | `STOCK_ANALYSIS` | `stock-analysis-skill: stock` | 必须 | `PAID_AFTER_VALIDATED_SKILL` |
| `NEED_CLARIFICATION` | 任意兼容 Intent | 无 | 禁止 | `TEMPLATE_ONLY` |

项目只有一个真实行情分析 Skill：`stock-analysis-skill`。`stock`、`portfolio`、`quant`、`sector` 是它的 Command，不得虚构 Quote Skill、Kline Skill 等不存在的 Skill。

### 1.2 路由判定规则

1. 确定性规则优先；命中后本地模型不得改写 Route。
2. “分析”一词本身不是付费依据。“分析一下 MACD”走 `KNOWLEDGE_QA`；“600519 的 MACD 是多少”走 `MARKET_FACT`。
3. 当前价格、涨跌幅、K 线和技术指标事实不调用 WebSearch，也不调用付费模型。
4. 板块热度、排名、资金流和换手事实走 `SECTOR_FACT`；互联网讨论、关注和零售关键词代理走 `SECTOR_ATTENTION`，两者不得混合计算。
5. 买卖、加减仓、止盈止损、组合调整、ETF轮动和板块方向判断等明确决策目标才进入深度分析候选 Route。
6. “为什么上涨/下跌”进入 `MARKET_CAUSAL_ANALYSIS`，必须同时取得行情 Skill Observation 和外部证据。
7. 本地 Intent 兜底无法确认股票目标时必须进入 `NEED_CLARIFICATION`，不能默认升级为付费分析。
8. 付费 DeepSeek 语义路由默认关闭；规则未命中时使用本地 Ollama Intent 兜底。显式开启 DeepSeek 候选分类时必须单独记录路由成本，不能算作最终分析模型调用。

Stock Agent 固定的是“当前分析对象”而不是强制股票代码。股票决策仍要求显式选择单标的；板块和市场问题允许在未选择股票时进入 `SECTOR_FACT`、`SECTOR_ATTENTION` 或 `SECTOR_ANALYSIS`。

### 1.3 付费模型硬门禁

业务层调用链固定为：

```text
RouteDecision
→ 显式执行允许的 Skill Command
→ StockSkillContractValidator
→ EvidenceValidator（仅要求外部证据的 Route）
→ PaidModelGate
→ PaidModelPermit
→ 游客 Redis 次数原子扣减（仅游客真实付费调用）
→ PaidAnalysisClient
→ DeepSeekClient
```

只有以下条件全部成立才允许付费：

```text
Route.modelPolicy = PAID_AFTER_VALIDATED_SKILL
∧ Skill 执行成功
∧ JSON 契约通过
∧ Command 与 Route 匹配
∧ 标的匹配
∧ 数据时效允许方向性结论
∧ 要求 WebSearch 时证据充分
```

原始 `DeepSeekClient` 必须保持包内可见，任何业务组件不得直接注入。知识抽取、普通问答、RAG 回答和外部资料总结不得产生隐藏的 DeepSeek 调用。

游客次数不得在 Route 后提前扣减。Skill 失败、契约失败、时效不通过、外部证据不足、`SECTOR_FACT` 和 `SECTOR_ATTENTION` 都不消耗次数；只有 `PaidModelPermit.allowed=true` 且即将订阅付费模型流时执行 Redis Lua 原子扣减。

### 1.3.1 有界多轮 ReAct

当前实现采用“确定性 Route 规划 Action、通用循环执行 Action/Observation”的方式，不允许模型直接生成未授权工具调用。`BoundedReactLoop` 每轮复用首次生成的 `RouteDecision`，并执行以下硬限制：

- 全局最大 5 轮，Skill 只能收紧，不能放宽；
- 全局总截止时间 180 秒；
- 单工具默认超时 60 秒；
- 相同工具与规范化参数默认只允许执行 1 次；
- Observation 注入工作记忆默认最多 8000 字符，完整结果仅用于本轮契约校验；
- 工具总量同时受 ReAct 预算、Skill `maxToolCalls` 和 `AgentRunContext` 约束；
- Action 指纹采用工具名与规范化参数的 SHA-256，不记录模型隐藏思维链。

统一终止原因包括：

`FINAL_ANSWER`、`ASK_USER`、`MAX_STEPS_REACHED`、`TOOL_BUDGET_EXCEEDED`、`DEADLINE_EXCEEDED`、`DUPLICATE_ACTION_BLOCKED`、`TOOL_TIMEOUT`、`TOOL_FAILED`、`POLICY_REJECTED`、`EVIDENCE_INSUFFICIENT`、`MODEL_GATE_BLOCKED`。

每轮写入 `REACT_DECISION`，结束写入 `REACT_TERMINATION`；SSE `done` 事件返回 `reactTerminationReason`、`reactRounds` 和 `reactToolCalls`。`MARKET_CAUSAL_ANALYSIS` 当前是两轮确定性计划：先取得并校验行情，再获取固定 `List<SearchResult>`，两类证据均满足后才能进入付费门禁。

### 1.4 WebSearch 固定链路

```text
LocalSearchPlanner
→ 最多3个 SearchTask
→ SearchPolicyValidator
→ HttpWebSearchGateway
→ WEB_SEARCH_ENDPOINT_URL
→ 临时 http://118.25.178.86:3002/api/search / 正式 HTTPS 入口
→ web-search-wrapper
→ Docker/VPC 内网 SearXNG
→ 百度、360
→ 固定 List<SearchResult>
→ EvidenceValidator
```

各 Agent 自己负责 Intent、Route、隐私清理和最小搜索词生成。Wrapper 不接收完整对话，不接入大模型，不理解股票业务，只负责：

- `X-Agent-Id` + `X-Search-Token` 鉴权；
- 请求契约和任务预算校验；
- 逐 Agent 限流、短期缓存、超时与熔断；
- SearXNG Provider 调用；
- URL 清洗、去重、来源类型和固定错误信封。

公网端点固定为 `/api/search`，协议版本由 `schemaVersion` 管理，不在 URL 中增加 `v1`。SearXNG 原始 `/search`、`/config` 和 UI 不作为 Agent 公网接口。

请求示例：

```json
{
  "schemaVersion": "1.0",
  "tasks": [
    {
      "taskId": "search-1",
      "purposeCode": "NEWS_CATALYST",
      "mode": "NEWS",
      "query": "600519 近期 下跌 原因 新闻 公告",
      "language": "zh-CN",
      "freshnessDays": 30,
      "includeDomains": [],
      "excludeDomains": [],
      "maxResults": 5
    }
  ]
}
```

业务层只消费固定字段：`resultId`、`taskId`、`purposeCode`、`title`、`url`、`domain`、`snippet`、`sourceType`、`provider`、`publishedAt`、`retrievedAt`、`relevanceScore`。

### 1.5 失败与降级

- Skill 超时、契约错误、Command 不匹配、标的不匹配或数据过期：禁止付费，返回可审计原因。
- 搜索鉴权失败、超时、无结果或证据不足：普通外部查询明确说明资料不足；涨跌归因禁止付费。
- `NEED_CLARIFICATION` 对 Skill、WebSearch 和 DeepSeek 的调用次数必须为零。
- Agent Run 必须记录 `ROUTE_DECISION`、工具 Action/Observation、`MODEL_GATE`、`MODEL_CALL` 和最终回答，不保存隐藏思维链或 Token。

## 5. Skill 抽象层设计

### 5.1 概念

Skill = 一套完整的领域规则、真实 Command、输入输出契约和约束。`RouteExecutionPolicyRegistry` 先决定允许的 Command，Java 再显式执行；模型只能消费 Observation，不能自主扩大工具权限。

### 5.2 Skill 定义结构

```java
public record SkillDefinition(
    String name,                    // "investment-knowledge-qa"
    String version,                 // 行为版本，写入 Agent Run 支持复现
    String description,
    String systemPrompt,            // 系统指令（核心规则）
    List<String> availableTools,    // 可用工具列表
    Map<String, Object> constraints,// 约束（maxTokens, temperature...）
    List<String> guardrailRules     // 该 Skill 特有的护栏规则
) {}
```

`availableTools` 仅作为兼容角色定义，最终权限以 Route 的 `allowedSkillCommands` 为准。`constraints` 至少支持 `maxTokens`、`temperature` 和 `maxToolCalls`；每个 Agent Run 必须创建独立预算，禁止跨请求共享调用计数。

### 5.3 真实 Skill 与兼容角色

真实可执行 Skill 只有 `stock-analysis-skill`，由 `stock-wrapper` 暴露 `stock`、`portfolio`、`quant`、`sector` Command。`investment-knowledge-qa`、`portfolio-analysis`、`stock-deep-analysis`、`general-chat` 是 Java 侧兼容角色规则，不是可独立部署或调用的 Skill。

WebSearch 是独立共享基础服务，不属于 `stock-analysis-skill`，也不得伪装成 Quote Skill、Kline Skill 或搜索 Skill。

### 5.4 Skill NPM 包与透明 JSON 契约

`stock-analysis-skill` 使用独立 NPM 包名、语义化版本和 CLI `bin` 入口。构建镜像时先执行 `npm pack`，再从生成的 `.tgz` 安装到 stock-wrapper 镜像；禁止依赖源码目录偶然存在。发布包只能包含运行代码、`SKILL.md`、必要 references 和模板，不得包含 `node_modules`、历史分析结果、IDE 文件或真实用户配置。

`stock`、`portfolio`、`quant`、`sector` 在 `--json` 模式下必须只向 stdout 写入一个 JSON 文档，固定包含：

```json
{
  "schemaVersion": "1.1",
  "command": "portfolio",
  "timezone": "Asia/Shanghai",
  "asOf": "2026-07-29 10:00:00",
  "request": {},
  "dataQuality": {},
  "data": {},
  "sources": {}
}
```

约束：

- `portfolio` 和 `sector` 必须返回原生结构化数据，不允许 Wrapper 把中文看板包装成 `data.format=text`。
- JSON stdout 不得混入表格、日志、颜色控制符或进度提示；诊断信息只写 stderr。
- 失败必须使用结构化错误 JSON，并以非零退出码结束；错误至少包含 `schemaVersion`、`command`、`error.code` 和 `error.message`。
- `asOf` 必须来自已核验行情、K线、净值或板块数据时间，不能使用模型回答时间伪造。
- Wrapper 只校验 Schema、Command 和上限后透传 Skill JSON；非法 JSON、版本错误和 Command 不匹配必须明确失败，不允许补字段或猜测成功。
- CLI 文本模式仅供人工终端查看，不能进入 Java Agent 的 Observation。
- 每次结果必须携带方法论版本、命中的 Rule ID、硬门禁、关键观测值、阈值、结论和适用限制；最终模型不得隐藏或改写 Skill 声明的局限性。

### 5.5 stock-wrapper 服务边界

`stock-wrapper` 是独立的 Node.js 内部服务，与 `stock-analysis-skill` 打包到同一 Docker 镜像；`stockwise-backend` 单独构建 Java 镜像。两者可以由同一套 Docker Compose 部署在同一台服务器，但运行环境、进程和扩容边界必须分离。

```text
StockTools
  → StockAnalysisGateway
  → HttpStockAnalysisGateway
  → stock-wrapper HTTP API
  → stock-analysis-skill
```

约束：

- Java 业务代码禁止直接依赖 Node.js 路径或使用 `ProcessBuilder` 调用 Skill。
- Wrapper 的 `3001` 端口只在容器内部网络暴露，不直接开放公网。
- Wrapper 必须提供健康检查、请求 ID、内部 Token、请求参数校验、执行超时和并发上限。
- Wrapper 返回版本化响应信封；其中 `data` 必须是 Skill 原生 JSON 契约，Java 解包后继续执行 `StockSkillContractValidator` 金融硬规则。
- Wrapper 在 Node 服务内部安全启动由 NPM 包安装的 Skill CLI。Java 无需感知包安装路径，也不保留 CLI 调用后备。

### 5.6 Skill 上下文组装

```java
public SkillContext assembleContext(
        SkillDefinition skill,
        String userId,
        String userQuestion,
        boolean retrievalHit,
        List<KnowledgeChunk> retrievalResults,
        List<Message> conversationHistory) {

    return SkillContext.builder()
        .userQuestion(userQuestion)
        .conversationHistory(conversationHistory)
        .projectEnvironment(getProjectEnv(userId))     // 用户持仓/偏好
        .skillInstruction(skill.systemPrompt())
        .availableTools(skill.availableTools())
        .retrievalHit(retrievalHit)
        .retrievalResults(retrievalResults)             // 可能为空
        .constraints(skill.constraints())
        .build();
}
```

当前实现的上下文边界：

- `ConversationMessage` 是 Redis 工作记忆中的强类型消息，兼容旧版 `role/content` JSON。
- `LangChainContextWindow` 每次请求创建独立 `TokenWindowChatMemory`，先限制最近消息数，再限制 Token，不使用全局 ChatMemory。
- 本地模型与付费分析模型使用不同记忆预算；单条历史消息和跨会话摘要分别设上限，当前用户问题始终单独保留。
- LangChain4j 窗口不挂接 `ChatMemoryStore`。完整消息继续由 Redis CAS 保存，并在用户确认收档后写入 `conversation_history`。
- LangChain4j `EmbeddingStore<TextSegment>` 只用于跨会话摘要检索。适配器写入独立的 `conversation_episode_embeddings`，不得复用 `knowledge_chunks`。
- 新会话必须先完成 Route 并确认 `symbol`，再按 `user_id` 强隔离召回；有标的时只召回相同标的，最后按语义相似度与时间衰减综合排序。
- `conversation_history` 必须先写成功，摘要向量索引随后尽力写入；索引失败保留完整归档，检索失败或旧归档尚无索引时降级为最近摘要。

### 6.1 知识状态模型

                           │
                    问题被解决 (Step 10)
                           │
                           ▼
                    ┌──────────────┐
                    │  候选知识     │  ← 从对话中提取，待确认
                    └──────┬───────┘

                    └──────┬───────┘
                           │ 通过
                           ▼
                    ┌──────────────┐
                    │  生成正式向量  │  ← Ollama Embedding
                    └──────┬───────┘
                           │
                           ▼
                    ┌──────────────┐
                    │  active(生效) │  ← 正常使用中
                    └──┬───┬───┬──┘
                       │   │   │

### 6.2 知识质量过滤 (Step 5 详细逻辑)

```java
public List<KnowledgeChunk> filterKnowledge(List<KnowledgeChunk> rawResults) {
    List<KnowledgeChunk> filtered = new ArrayList<>();
    List<String> conflicts = new ArrayList<>();

    for (KnowledgeChunk chunk : rawResults) {

        // ── 检查1: 过期 ──
        if (chunk.getMetadata().containsKey("expires_at")) {
            Instant expiresAt = Instant.parse(chunk.getMetadata().get("expires_at"));
            if (Instant.now().isAfter(expiresAt)) {
                chunk.setStatus("expired");
                continue; // 跳过过期知识
            }
        }

        // ── 检查2: 冲突 ──
        for (KnowledgeChunk kept : filtered) {
            if (detectConflict(chunk, kept)) {
                conflicts.add(chunk.getContent() + " ↔ " + kept.getContent());
                // 保留置信度更高的
                if (chunk.getConfidence() <= kept.getConfidence()) {
                    chunk.setStatus("conflicted");
                } else {
                    kept.setStatus("conflicted");
                    filtered.remove(kept);
                }
            }
        }

        // ── 检查3: 可信度 ──
        if (chunk.getConfidence() < 50) {
            chunk.setStatus("low_credibility");
            continue; // 跳过低可信知识
        }

        filtered.add(chunk);
    }

    // 如果有冲突，在结果中标注
    if (!conflicts.isEmpty()) {
        log.warn("知识冲突检测: {}", conflicts);
    }

    return filtered;
}
```

## 8. 数据库设计

### 8.1 知识库（双表分离：客观背景 vs 个人偏好）

> **目标状态**：本节描述后续双表方案。当前已实现并正在使用 `knowledge_chunks` 单表，字段与索引以 `db/schema.sql` 为准；迁移到双表前继续保持现有接口兼容。
>
> **设计理念**：同一只股票的分析背景知识是客观的，谁看都一样；只有持仓和偏好因人而异。故拆为两张表——`public_knowledge` 全局共享（含游客），`private_knowledge` 按 `user_id` 隔离。分离后可实现游客模式 + RAG 缓存共享。

#### public_knowledge（公共背景知识 / RAG 缓存层）

存公司基本面、行业知识、财报摘要、投资概念；候选知识由本地模型提取并经过质量过滤，按产品规则确认后写入，后续问答可直接复用。**实时数据（股价/涨跌）绝不缓存**，每次实时拉取。

```sql
CREATE TABLE public_knowledge (
    id            BIGSERIAL PRIMARY KEY,
    stock_code    VARCHAR(10),                -- 关联股票代码，检索第一过滤条件
    content       TEXT NOT NULL,
    embedding     VECTOR(1024),               -- qwen3-embedding:0.6b
    metadata      JSONB DEFAULT '{}',         -- {source, problem, confidence, expires_at, tags, category}
    status        VARCHAR(20) DEFAULT 'active' CHECK (status IN ('active','expired')),
    created_at    TIMESTAMPTZ DEFAULT NOW(),
    updated_at    TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX idx_pubk_stock ON public_knowledge(stock_code);
CREATE INDEX idx_pubk_status ON public_knowledge(status);
CREATE INDEX ON public_knowledge USING ivfflat (embedding vector_cosine_ops) WITH (lists = 100);
```

检索 SQL（先按 stock_code 过滤，再向量排序命中索引）：
```sql
SELECT content, metadata, 1 - (embedding <=> :vec::vector) AS score
FROM public_knowledge
WHERE status = 'active' AND stock_code = :stockCode
  AND (metadata->>'expires_at')::timestamptz > now()
ORDER BY embedding <=> :vec::vector LIMIT 5;
```

#### private_knowledge（个人偏好 / 按 user_id 隔离）

存用户偏好、自定义规则、投资经验；Step 11 用户确认后从 `temporary` 变 `active`。

```sql
CREATE TABLE private_knowledge (
    id            BIGSERIAL PRIMARY KEY,
    user_id       BIGINT NOT NULL,            -- 按用户隔离
    content       TEXT NOT NULL,
    embedding     VECTOR(1024),
    metadata      JSONB DEFAULT '{}',
    status        VARCHAR(20) DEFAULT 'active'
                  CHECK (status IN ('temporary','active','expired','conflicted','deprecated')),
    version       INT DEFAULT 1,
    replaces_id   BIGINT REFERENCES private_knowledge(id),
    created_at    TIMESTAMPTZ DEFAULT NOW(),
    updated_at    TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX idx_pk_user ON private_knowledge(user_id);
CREATE INDEX idx_pk_status ON private_knowledge(status);
CREATE INDEX idx_pk_fts ON private_knowledge USING GIN (to_tsvector('simple', content));
CREATE INDEX idx_pk_metadata ON private_knowledge USING GIN (metadata);
CREATE INDEX ON private_knowledge USING ivfflat (embedding vector_cosine_ops) WITH (lists = 100);
```

检索 SQL（必须带 user_id 隔离）：
```sql
SELECT id, content, metadata, 1 - (embedding <=> :vec::vector) AS score
FROM private_knowledge
WHERE status = 'active' AND user_id = :userId
  AND (metadata->>'expires_at' IS NULL OR (metadata->>'expires_at')::timestamptz > now())
ORDER BY embedding <=> :vec::vector LIMIT 5;
```

> `temporary` 状态是 Step 10 提取但用户尚未确认的候选知识——**不参与检索**，只在确认页可见。
>
> **双源检索**：注册用户同时查 public + private（合并后进 Step 5 过滤）；游客只查 public（无 user_id，无从查 private）。

### 8.3 Agent 运行审计

运行审计采用三张结构化表，完整 DDL 以 `db/schema.sql` 为准：

| 表 | 职责 | 核心字段 |
|----|------|----------|
| `agent_runs` | 一次 Skill 推理的生命周期 | `run_id`、用户/会话、intent、Skill 名称与版本、状态、工具预算、最终回答、错误、起止时间 |
| `agent_steps` | 按 `step_no` 保存可回放事件 | `ROUTE_DECISION`、`REACT_DECISION`、`TOOL_CALL`、`TOOL_OBSERVATION`、`REACT_TERMINATION`、`MODEL_GATE`、`MODEL_CALL`、`POLICY_REJECTION`、`FINAL_ANSWER`、`ERROR` |
| `tool_executions` | 关联工具 Action 与 Observation | 工具参数、结构化返回、状态、耗时、错误码和起止时间 |

要求：

- 只保存业务输入输出、工具动作和简短决策摘要，不保存模型隐藏思维链。
- `run_id + step_no` 必须唯一，保证回放顺序稳定。
- 允许执行的工具调用计入预算；被策略拒绝的调用单独记录，但不增加已执行工具计数。
- 工具异常既要更新 `tool_executions`，也要把 Agent Run 标记为 `failed`。
- PostgreSQL 初始化 DDL 必须使用 `IF NOT EXISTS`，允许在相同结构上重复执行；字段变更必须使用版本化迁移，不能依赖 `IF NOT EXISTS` 自动升级旧表。

### 8.4 Redis 结构

| Key | 类型 | 内容 | TTL |
|-----|------|------|-----|
| `session:{id}:state` | String(JSON) | 当前暂停点、Route、模型上限、标的、最近消息、待确认候选、最后 Run ID 与 `version` | 30min |
| `guest:analysis:{subjectHash}` | String | 当前游客已获准发起的分析请求数，上限默认 10 | 无自动过期 |

`session:{id}:state` 禁止无条件覆盖。保存和清除必须通过 Redis Lua CAS 比较 `version`；版本不一致时返回会话冲突，不允许后到请求覆盖先到请求。进入异步 ReAct 前先把状态改为 `react_running` 并占用新版本；同一会话在该状态下拒绝并发执行。

游客分析次数必须使用 Redis Lua 原子执行“读取当前值 → 判断上限 → 递增”，不能先 `GET` 再 `INCR`。游客主体由服务端签发的 HttpOnly Cookie 生成，Redis Key 只使用主体的 SHA-256 哈希，不保存原始 Cookie、IP 或 User-Agent。Cookie 被清除后可获得新的游客主体，因此该能力属于轻量产品配额；需要强身份防刷时必须要求登录并叠加网关限流。

计数时点固定在 `RouteDecision` 形成之后、任何 Skill/WebSearch/付费模型执行之前。一次分析只要通过闸门并获得执行资格即计为一次；下游失败不自动返还，避免并发重试绕过上限。Redis 不可用时分析限额必须失败关闭，普通免费问答仍可继续。

### 8.5 MemoryRouter 与四类记忆

| 记忆类型 | 存储 | 内容 | 禁止内容 |
|---|---|---|---|
| 工作记忆 | Redis | 当前会话、暂停点、Route、ReAct 运行状态、最近消息、待确认候选 | 无限历史、完整长期工具数据 |
| 情景记忆 | PostgreSQL + PgVector | 完整会话归档、可重建摘要向量索引、Agent Run、结构化用户反馈 | 模型隐藏思维链、把摘要索引当原始历史 |
| 语义记忆 | PgVector | 用户确认后的可复用知识 | 行情价格、临时指标、未确认候选 |
| 业务事实 | PostgreSQL 业务表 | 用户持仓、成本、份额、资金预算、现金缓冲 | 依靠向量召回推测持仓 |

业务层不得直接猜测存储位置，统一通过 `MemoryRouter` 调用对应能力。组合分析必须按 `user_id` 加载 `portfolio_positions.active=true` 和 `user_configs`，转换为固定 `PortfolioAnalysisInput` 后发送给 `stock-wrapper`。缺少真实持仓或资金配置时进入 `ASK_USER`，不得让 Skill 回退到示例 `portfolio.json`。

长期情景记忆采用双层结构：

- `conversation_history`：完整消息与摘要的真相源，归档失败时不得清除 Redis 工作记忆。
- `conversation_episode_embeddings`：LangChain4j `TextSegment` 的派生向量索引，可删除、重建或停用，不影响完整归档。
- 查询向量由现有 Spring AI `EmbeddingService` 生成；不得再创建第二套 Ollama Embedding 客户端。
- 历史摘要只能帮助理解用户延续问题，不得覆盖当前 Skill、行情工具或 WebSearch 返回的最新事实。

结构化反馈写入 `user_feedback`：

- `RESOLVED`：用户明确表示已解决；
- `UNRESOLVED`：用户明确表示未解决；
- `CORRECTION`：用户提供补充或修正；
- `KNOWLEDGE_CONFIRMED`：确认候选知识入库；
- `KNOWLEDGE_REJECTED`：拒绝候选知识入库。

## 9. API 设计

### 9.0 认证与 RBAC 权限

认证接口公开，登录和注册成功返回 JWT。JWT 只携带用户身份，具体权限由 MySQL RBAC 关系实时查询，避免角色变更必须等待 JWT 过期。

| 权限码 | 允许能力 | 默认 USER | ADMIN |
|---|---|---:|---:|
| `AGENT_RUN_READ` | 查询自己的 Agent Run 与回放 | 是 | 是 |
| `KNOWLEDGE_READ` | 读取公开知识 | 是 | 是 |
| `KNOWLEDGE_WRITE` | 修改或软删除知识 | 是 | 是 |
| `SYSTEM_USER_READ` | 查询系统用户 | 否 | 是 |

游客只能访问明确公开的聊天、配额查询、健康探针和知识读取接口。客户端提交的 `userId`、`role`、`permission` 和 `isGuest` 一律不作为授权依据。管理员角色不得在注册流程自动授予，必须由运维执行幂等授权 SQL。

### 9.1 对话接口（SSE 流式）

```http
POST /api/v1/chat/stream
Content-Type: application/json
Accept: text/event-stream
```

```json
{
  "sessionId": "sess_abc",
  "message": "现在适合买入吗",
  "instrument": {
    "symbol": "600519",
    "assetType": "stock"
  }
}
```

当前是单用户部署模式，用户身份固定从服务端 `stockwise.single-user.id` 读取；请求体和查询参数不得接收 `userId`。以后接入认证时由认证主体替换该配置入口。`instrument` 是结构化当前标的：问题中存在新代码时以问题为准，否则沿用该字段；知识问答不要求标的，组合分析只读取数据库真实持仓。

前端使用 `fetch + ReadableStream` 发起 POST 并解析 SSE，不再使用只能发送 GET 的 `EventSource`。用户完整问题不得进入 URL、Nginx access log 或代理查询日志。

SSE 事件类型：

```text
data: {"type":"status","step":"classifying"}
data: {"type":"quota","quotaType":"guest_analysis","limit":10,"used":3,"remaining":7}
data: {"type":"status","step":"skill_executing","skill":"investment-knowledge-qa"}
data: {"type":"agent_run","runId":"019fa2b5-..."}
data: {"type":"token","content":"因子投资"}
data: {"type":"token","content":"是通过..."}
...
data: {"type":"suggest","items":["知识①","知识②"]}  ← 候选知识
...
data: {"type":"ask","prompt":"以上回答是否解决了你的问题？","runId":"019fa2b5-..."}
data: {"type":"done","runId":"019fa2b5-...","skill":"investment-knowledge-qa","status":"RESOLVED"}
```

每个连接必须以 `done` 或 `error` 终止。发送到前端的回答片段必须先通过输出护栏；禁止“先发送全部 token、最后仅补发告警”。模型输出可以按完整句子缓冲后校验并发送，以保留近实时体验。

当游客分析次数耗尽时，连接直接返回 `done`：`status=GUEST_ANALYSIS_LIMIT_REACHED`，并携带 `quotaType`、`limit`、`used`、`remaining` 和登录提示。前端必须展示“游客分析 0/10”，不得继续调用 Skill、WebSearch 或付费模型。

工具 Action/Observation 当前写入 Agent Run 审计表，通过 9.4 回放接口查询；后续前端需要实时工具状态时，再增加不含敏感参数的 `tool_call` SSE 事件。

## 10. 护栏与合规

### 10.1 分层护栏

| 层级 | 检查点 | 规则 |
|------|--------|------|
| Step 1 (输入) | 用户消息 | Prompt注入检测 + 违规关键词 |
| Step 5 (检索) | 检索结果 | 过期/冲突/低可信过滤 |
| Step 8 (输出) | Skill 结构化结果 | 禁止"保证收益"等措辞 |
| Step 11 (入库) | 候选知识 | 合规审查 + 敏感内容过滤 |

### 10.2 知识入库审查

| 检查项 | 方式 | 动作 |
|--------|------|------|
| 包含禁止措辞 | 关键词匹配 | 拒绝入库 |
| 向量相似度 > 0.92 | PgVector 检索 | 标记重复，跳过 |
| 内容 < 20 字 | 长度检查 | 拒绝 |
| 与已有知识冲突 | 语义比较 | 用户二选一 |
| 置信度 < 50 | 元数据检查 | 拒绝 (只有解决问题后才入库) |

### 11.2 搜索服务云端边界

本地开发允许只启动 Java Agent，通过环境变量访问云端搜索服务：

```env
WEB_SEARCH_ENDPOINT_URL=http://118.25.178.86:3002/api/search
WEB_SEARCH_AGENT_ID=stockwise
WEB_SEARCH_AGENT_TOKEN=与云端Wrapper一致的独立Token
```

上述 IP 地址只用于未备案域名受限期间的临时联调。3002 必须限制可信来源 IP，SearXNG 的8080端口始终不得暴露公网；正式 HTTPS 入口恢复后必须关闭公网3002。

### 与 v2.0 的核心差异

| 维度 | v2.0 | v3.0 |
|------|------|------|
| 向量管理 | 搜和存混用 | 临时向量(搜) + 正式向量(存) 分离 |

| 知识沉淀 | 搜索结果直接入库 | 问题被解决后才提取候选知识 |
| 结构化返回 | 纯文本 | SkillResult (status + confidence + candidates) |
| Agent 判断 | 硬编码 | RouteDecision + 执行策略 + 可审计终止结果 |
