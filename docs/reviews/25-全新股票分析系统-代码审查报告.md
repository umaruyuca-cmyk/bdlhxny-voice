## 二、设计亮点（这些写得好）

### 2.1 动态 WorkflowPlan 调度（root_graph.py）

不是写死的线性流程，而是 `dispatch_workflow` 读 `workflow_plan` 的 `next_stage` 做条件路由，每个任务完成后回到调度节点继续——这是比 v1 设计文档的固定子图更灵活的实现，且没有牺牲确定性（路由由代码函数决定，非 LLM）。

### 2.2 执行矩阵（market_data_graph.py + research_agent.py）

按 `analysis_type` 分流：
- `market_snapshot`：快路径，不启动 ReAct，直接 finish
- `technical/fundamental`：规则版 agent，按 DataRequirement 顺序（确定性）
- `comprehensive`：LLM 版 agent，自主决策

这个设计精巧——既满足了"简单查询省 token"，又保留了"复杂研究可自主"，且规则版完全可测。

### 2.3 记忆降级策略（memory/noop.py + base.py）

Mem0 不可用时自动降级到 NoOpMemoryStore，主流程不受影响。记忆被定位为"增强项非关键路径"——这和架构 v2 §5 的"黑箱关在记忆层"完全一致。

### 2.4 MCP 服务端吞错识别（adapter.py + normalizer.py）

不止识别协议层错误（工具抛异常），还识别"服务端返回 200 但 body 里藏 `{"error":true}`"的吞错——这是真实 MCP 服务常见坑，代码处理得很到位，且吞错也触发 fallback。

### 2.5 子图输出 schema 受限（market_data_graph.py `_MarketDataOutput`）

子图刻意不输出 `workflow_plan`，防止子图入口快照覆盖主图调度进度。注释说明这是"冒烟发现的 bug"的修复——说明开发者真的跑过、踩过坑、修对了。

## 三、发现的问题

### 🟡 问题 1（建议改）：`runtime/` 与 `runtimes/` 命名混淆

**现象**：

```
runtime/    （单数）= 应用承载层（application/budgets/checkpointers/recovery）
runtimes/   （复数）= 编排引擎层（langgraph/letta/shared）
```

两者职责不同（前者是架构 §2.3 Application Runtime，后者是 §3.2 可替换引擎），但名字只差一个 `s`。更绕的是 `runtime/application.py` 里 import `runtimes.langgraph`，出现"runtime 调 runtimes"的交叉引用。

**影响**：新人接手必踩坑；阅读代码时需要反复确认是哪个。

**建议**：`runtime/`（单数）重命名为语义更明确的 `app/` 或 `boot/`。
- 改动量：1 个目录 + 约 10 处 import
- 风险：纯机械重构，但需跑测试验证无遗漏

**为什么没改**：本次审查环境无 Python，无法验证 rename 后测试仍通过。建议在有 Python 环境时执行。

### 🟢 问题 2（信息，非问题）：Letta 版完全空

`runtimes/letta/` 只有空 `__init__.py`。这是计划内的（README + 架构 v2 §4.1 均说明"主版本稳定后启动"），不算缺陷。

### 🟢 问题 3（信息）：测试覆盖面广但未验证

存在大量测试文件（domain/graphs/mcp/memory/observations/runtime/runtimes），覆盖 ReAct 回归、MCP fallback、记忆降级、回测无未来函数等。但因运行环境无 Python，本次审查**未执行任何测试**，测试是否全绿未知。
