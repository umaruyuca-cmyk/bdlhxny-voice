> 复核对象：[21-全新股票分析系统-Agent需求与开发设计.md](../architecture/21-全新股票分析系统-Agent需求与开发设计.md)（v1.0）

> 复核依据：原文 §24「给其他 AI 的复核任务」，按 §24.6 要求的格式输出。
>
> 复核立场：不默认原文档正确，重点检查流程边界、状态流转、Agent 使用方式、条件边和确定性计算职责。

## 总体结论

**合理（偏上），但有关键一致性缺口。**

骨架（分层、Agent 模式、Observation、条件边原则）是扎实的，可以照着落地。扣分集中在两类问题：

1. **文档内部前后矛盾**（最影响复核可信度）；
2. **核心动态组件的安全守卫缺失**。

没有到「推倒重来」的 P0，但有 1 个逼近 P0 的安全缺口和若干必须澄清的边界。

**建议评分：8 / 10**

## P0 必须修改

### P0-1　Research Agent 内部循环缺少显式预算守卫

**位置**：§8.4 内部子图 vs §2.4 / §2.5 / §8.5

**问题**

§8.4 把 Research Agent 画成一个内部自循环：

```
select_next_action → execute_tool → normalize_tool_result → append_observation → select_next_action
```

但这个**内层循环里没有任何 CODE 节点检查 `max_rounds` / `tool_call_count`**。而文档自己在：

- §2.4：「Agent ……不能无限循环」
- §2.5：把「防止无限循环」列为硬约束
- §8.5：「最终是否结束由 `evaluate_research_state` 决定」

问题在于：`evaluate_research_state` 在 §8.2 是**外层 Market Research Graph 的节点**，它只能在**内层子图返回之后**才运行。那么内层子图本身的迭代次数由谁兜底？现状只有两种读法，都有问题：

- **读法 A**：内层每次只做**一步**就返回、真正的循环在外层 → 那 §8.4 里「append_observation → select_next_action」的回边就是**错的 / 误导**的；
- **读法 B**：内层**自由多步循环** → 那它**缺自己的硬停**，违反 §2.4 / §2.5。

**影响**

系统最核心的动态组件存在死循环风险，且与文档明令禁止的行为直接冲突；复核者会立刻盯住这里。

**修改建议**：二选一并写死。

- **方案 A（推荐）**：内层子图**每次调用只执行一个 action**；删掉 §8.4 里「append_observation → select_next_action」的回边，把循环收敛到外层 `evaluate_research_state → research_agent_subgraph`，并在外层显式做预算扣减。
- **方案 B**：保留内层多步，但在 `append_observation` 之后插入一个 CODE 守卫节点 `check_agent_budget`，命中上限强制走 `STOP_LIMITED`，并在文档中标注内层 `max_inner_rounds` 与外层预算的关系。

### P0-2　Root Graph「单选路由」与「一个或多个子图」自相矛盾

**位置**：§5.1 vs §5.2 vs §5.3 vs §5.4

**问题**

四处描述互相打架：

| 章节 | 表述 | 语义 |
|---|---|---|
| §5.1 | 「调用**一个或多个**子图」「合并子图结果」 | 多选 |
| §5.3 | `invoke_child_graph` 输出 `child_result`（单数）、`merge_child_result`（合并） | 暧昧 |
| §5.4 | 条件边写成**互斥 if/else**（单选：「→ market_research_graph」「→ portfolio_analysis_graph」） | 单选 |

这是直接矛盾。现实里大量请求是跨域的：

- 「分析茅台走势**并**和我持仓对比」→ market_research + portfolio
- 「设计策略**并**回测」→ strategy + backtest

按 §5.4 的单选路由**无法服务这类请求**；而 §5.1 / §5.2 又承诺可以多子图。

**影响**

整个系统最顶层的编排语义未定。复核时无法判断 `merge_child_result` 合并的是 1 个还是 N 个结果，也无法判断跨域请求会不会被错误地丢进单一子图。

**修改建议**

1. 把 `classify_workflow` 的输出从「单一 workflowType」改为「**目标子图列表 + 执行计划（并行 / 串行 / 依赖）**」，例如：
   ```json
   { "targets": ["market_research", "portfolio"], "plan": "sequential" }
   ```
2. §5.2 在 `route_workflow` 后明确：**fan-out →（并行或按依赖串行）执行 → fan-in 合并**；`merge_child_result` 改名 `merge_child_results` 并定义多结果合并规则。
3. §5.4 条件边重写成「返回目标集合」而非互斥分支。

## P1 建议修改

### P1-1　Root 与 Query Understanding Graph 职责重叠，实体解析归属不明

**位置**：§5.3 vs §7.3

`resolve_entities` **同时出现在 Root（§5.3）和 Query Understanding Graph（§7.3）**；且 Root 的 `normalize_request`（STRUCTURED_LLM）与 Query Graph 的 `extract_intent + normalize_time_scope` 功能高度重叠。§5.4 又写「分类不确定 → query_understanding_graph」，暗示 Query Graph 是 Root 的「兜底重判」——但这个**两层关系全文没有定义**。

**修改建议**：明确二选一。

- 方案 A：Root 只做「轻量 normalize + classify」，实体解析 / 缺失检测**全部下沉到 Query Graph**（Root 不再 resolve_entities）；
- 方案 B：Query Graph 只在「分类不确定」时被调用，且**不重复** Root 已做的步骤。

当前两处都写等于没有权威定义。

---

### P1-2　Observation 标准化是「普适原则」，却只在 Market Research 实现

**位置**：§16 vs §9 / §10 / §11

§16：「**所有** Tool、Service、MCP 和 Skill 的外部结果都应转换为 Observation」。

但实际只有 Market Research 有 `normalize_observation`（§8.2）和 `normalize_tool_result`（§8.4）：

- Portfolio 的 `load_market_snapshot`（TOOL_ONLY）直接喂给 `calculate_portfolio_metrics`（§9.3）；
- Strategy、Backtest 同样**没有 normalize 节点**，外部数据直进计算。

回测尤其需要——历史价的复权方式、数据源版本若不进 Observation，`as_of` / `provenance` 就丢了。

**影响**

要么原则是空的（只有研究数据需要溯源，组合 / 回测数据不需要 → §16 措辞要收窄），要么组合 / 回测也该标准化（那它们缺节点）。

**修改建议**

统一口径。建议保留普适原则，在 Portfolio / Strategy / Backtest 各加一个轻量 `normalize_*_observation` 节点，至少落 `asOf / source / 复权方式 / dataQuality`。

---

### P1-3　Knowledge Graph 路由语义混淆（「事实查询」vs「记忆检索」）

**位置**：§5.4 vs §12

§5.4：「单纯事实查询 → knowledge_graph 或直接回答」。

但 §12 的 Knowledge Graph 职责是**检索已沉淀的知识 / 历史研究**，不是回答市场事实。

「茅台市盈率多少」是**市场数据事实**，应进 market_research 或直接数据 Tool，而不是 knowledge_graph。把「事实查询」路由到「记忆检索」是概念错配。

**修改建议**

把 §5.4 那条改为「单纯事实查询 → 直接 Tool 调用或 market_research 的快照路径」；knowledge_graph 仅在「回忆之前的研究 / 用户曾沉淀的偏好」类请求时进入。

---

### P1-4　Strategy → Backtest 的链路在 Root 平面路由下断裂

**位置**：§5.4 vs §10 vs §11

Backtest（§11）以 `load_strategy_spec` 起步，依赖一个**已结构化策略**。但 Root 是平面单选路由（§5.4）。那么「回测这个策略」时，策略从哪来？

- 是同 thread 里 strategy_graph 先跑过（隐式依赖）？
- 还是用户直接传入 StrategySpec？

`StrategyState` 里有个 `backtest_request` 字段（§17.3）暗示 strategy 能触发 backtest——这又和「Root 平面路由」冲突。

**修改建议**

明确 Backtest 的入口契约：

- (a) 允许接收外部 StrategySpec（用户 / 上游传入）；
- (b) 允许引用同 run 内 strategy_graph 的产物（依赖 P0-2 的多子图编排支持这种依赖串行）。

把「策略 → 回测」作为一种**编排计划**在 Root 层表达，而不是藏在状态字段里。

---

### P1-5　Portfolio Graph 流程图缺 `portfolio_analysis_model`，且可选研究子图过重

**位置**：§9.2 vs §9.3

**问题 1**：§9.2 的主流程箭头从 `evaluate_portfolio_completeness` 直接指向 `build_rebalance_recommendation`，但 §9.3 表格里 `portfolio_analysis_model`（STRUCTURED_LLM）和 `build_rebalance_recommendation` 是两个独立 Model 节点——**流程图漏画了 `portfolio_analysis_model`**。

**问题 2**：把一整个多轮 ReAct 的 Market Research Graph 当「补充市场背景」嵌进 Portfolio（§9.2 `optional_market_research_subgraph`），代价过重：

- 容易把组合分析的预算打爆；
- 「需要补充市场背景」判定条件没定义。

**修改建议**

- 补全流程图节点；
- `optional_market_research_subgraph` 改为**受控的快照式**市场背景获取（单次 Tool 调用），或明确它有独立的更小预算上限。

## P2 可选优化

### P2-1　缺少快路径

简单问题（「茅台代码多少」）也要走 normalize → classify → resolve 全流程（≥2 次模型调用）。建议在 `classify_workflow` 后加一条「trivial fact → 直接 Tool / 直接回答」的早退边，跳过 `build_research_goal`。

### P2-2　单步 ReAct 的延迟成本

§8.4 每步一次模型往返，5 个工具 ≥5 次模型调用。§13.7 已经定义了「批量并行 Tool 调用」模式——建议对**已知模式的固定取数**（如组合快照）绕过 ReAct 走并行，把 ReAct 留给真正需要动态决策的研究。

### P2-3　状态命名不对齐

`RootState.status` / `ResearchState.research_status` / 终态（§18.4 SUCCEEDED…）/ 控制信号（§18.1 CONTINUE / SYNTHESIZE / VERIFY…）两套集合都有 NEED_USER / LIMITED / FAILED，但语义不同（一个是控制信号，一个是结果终态）。建议：

- 明确「research_status 是控制信号、终态是结果枚举」；
- 给一张映射表。

### P2-4　回测偏差清单没有对应验证节点

§11 末尾的前视偏差 / 生存者偏差 / T+1 / 涨跌停等是一段 reminder，没有节点或属性测试去断言。建议在 `validate_backtest_data` 里：

- 可检项（生存者偏差 = 标的池来源、复权方式 = 显式字段）做成硬校验；
- 不可检项（前视偏差）用属性测试兜底。

### P2-5　Phase 与定义错位

§12 Knowledge Graph 在 Phase 5 才建，但 Root 从 Phase 0 / 1 就能路由到它（P1-3）；`load_session_context` 也是 Phase 0 就在 Root 里，但记忆要等 Phase 5。建议注明 Phase 0–4 期间这些是 stub。

## 缺失模块

1. **缓存层**：行情 / 基本面是读密集 + 外部 API 限速，全文无缓存设计。Observation 有 `as_of` 暗示时效，但没有 TTL / 失效策略。对限速数据源这是硬缺口。
2. **限流**：外部数据源（尤其免费档）有 RPM / 日配额，Tool / Domain Service 层无限流器设计。
3. **认证与多租户隔离**：`get_user_positions_readonly` 意味着有按用户隔离的隐私数据，但 §20 API 无任何鉴权，也无 user → portfolio 的归属校验模型。组合分析上线前必须补。
4. **错误分类与重试策略**：`errors: list[dict]` 散落在各 State，但没有错误分类（瞬时 vs 永久 / 数据源宕机 vs 标的非法）和对应的重试 / 降级策略。
5. **长任务的执行模型**：§20.1 是 SSE chat，§23.4 要求「长时间研究不阻塞 API 线程」。但一次 5 分钟研究挂在 SSE 上很脆弱——缺「后台 run + 轮询 / 断线续传」的回退设计。
6. **模型降级链**：§2.2 提到「重试和降级」，但没有模型选型 / 成本分级 / 回退链的设计（用哪个模型做 classify、哪个做研究、失败回退到谁）。

## 不必要复杂度

- **两层理解管线**（Root normalize/classify + Query Understanding Graph）对多数请求是双重计税。若按 P1-1 收敛为一层，能省一次模型调用。
- **Tool Adapter → Domain Service → Data Provider** 三层，对简单的只读行情快照可能过度；建议区分「薄透传 Tool」（直接包 Domain Service 方法）与「复合 Tool」，前者免 Adapter 仪式。
- **Portfolio 里 `portfolio_analysis_model` + `build_rebalance_recommendation` 连续两个 STRUCTURED_LLM**：可考虑合并为一个结构化输出节点，减少一次模型往返。

## 建议保留的设计

以下设计经复核认为正确，修订时不应改动：

- **§1.2 非目标清单**（不下单 / 无 Broker / 无订单状态机）——边界纪律极佳，是整份文档最稳的部分。
- **§3 Agent 使用模式分类**（CODE / DIRECT_LLM / STRUCTURED_LLM / BOUNDED_REACT / AGENT_AS_SUBGRAPH / TOOL_ONLY / INTERRUPT）——清晰、可执行，每个节点能在表里对号入座。
- **§2.4「固定边界、动态路径」**——正确哲学。
- **§8.4 单步 ReAct**（每步一个结构化动作）——可调试、可审计，优于把循环藏进一次模型调用（配合 P0-1 修完守卫后）。
- **§13.4 组合 Tool 用 `readonly` 命名**——防御性命名，防未来误扩成写操作。
- **§16 Observation 统一结构**（含 `asOf / observedAt / provenance / dataQuality`）——可溯源，方向正确（配合 P1-2 落到所有子图即可）。
- **§18.3 条件边由 CODE 判定、Agent 不得直接返回节点名跳转**——正确，杜绝模型劫持控制流。
- **§13.8 Domain Service 不依赖 LangChain**——保证计算 / 回测逻辑可跨框架复用。

## 复核结论与建议次序

一句话总结：这是一份**结构合格、原则正确**的设计。真正要紧的只有两件事——

1. **把 Research Agent 循环的守卫补上**（P0-1）；
2. **把 Root 路由从「单选」改成「可编排多子图」并消除与 §5.1 的矛盾**（P0-2）。

其余 P1 多是「文档前后口径对齐」和「普适原则要落到每个子图」，改起来不重。

**修订次序建议**：

```
P0-1 / P0-2  →  P1-1（与 P0-2 联动）→  P1-2 / P1-3 / P1-4  →  P1-5  →  P2  →  缺失模块
```

建议完成 P0、P1 修订后再进入 Phase 0 开发。
