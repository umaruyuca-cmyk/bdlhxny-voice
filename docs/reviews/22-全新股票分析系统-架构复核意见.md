# StockWise 全新股票分析系统 Agent 架构复核意见

> 复核对象：`21-全新股票分析系统-Agent需求与开发设计.md`（v1.0）
>
> 复核结论：**合理（接近优秀，实现前需先解决 2 个架构歧义）**
>
> 建议评分：**8 / 10**

---

## 总体评价

这是一份完整、克制的架构设计，核心哲学"**固定边界、动态路径**"、单步结构化 ReAct、MCP Adapter 启动期转 Tool、Observation 统一结构、Skill 推迟到 Phase 6——都是正确的决策。

没有 god agent，没有多余的运行时，职责分层清晰，非目标边界明确（不交易、无 Broker、无订单审批）。

---

## P0 必须修改

### P0-1｜工具执行归属自相矛盾（架构级）

- 问题：§8.2 的流程是 `research_agent_subgraph → normalize_observation → evaluate_research_state`，工具执行在**子图外部**（子图只产出动作）；而 §8.4 的流程是 `select_next_action → execute_tool → normalize_tool_result → append_observation → select_next_action`，工具执行在**子图内部**。
- 影响：实现时"Observation 由谁标准化、工具预算在哪统计、审计事件在哪发"全部有歧义，直接决定整个执行模型。
- 修改建议：统一为"**子图只产出单步结构化动作，父图执行 Tool、标准化 Observation、统计预算**"，与 §8.4"单步 ReAct"的声明一致，也让审计和条件边能介入每一步。

### P0-2｜单 workflow 与"调用一个或多个子图"矛盾 + query_understanding 后无重路由

- 问题：§5.1 说 root"调用一个或多个子图"，但 `route` 是单值字符串，`invoke_child_graph` 一次只进一个图。同时 §5.4 说"分类不确定 → query_understanding_graph"，但 query_understanding 输出 `workflowType` 后**流程没有回到 route_workflow 的回路**。
- 影响："分析持仓并设计策略再回测"这类跨域请求会被截断成单域，或实现时各自发明二段路由，行为不一致。
- 修改建议：Phase 0/1 明确"仅单 workflow 一次运行"；要支持多域就把 `route: str` 改成 `workflow_plan: list[str]` 并设计 fan-out/join。同时补一条从 query_understanding 回到 route_workflow 的条件边。

## P1 建议修改

### P1-1｜Root 与 Query Understanding 职责重复

- 问题：Root 有 `normalize_request` + `classify_workflow` + `resolve_entities`（三次模型调用），Query Understanding 又做 `extract_intent` + `resolve_entities`。
- 影响：模型调用重复、实体解析两次、结果一致性难保证。
- 修改建议：合并成一次 `STRUCTURED_LLM` 联合输出（意图 + 实体 + 时间范围），Query Understanding 退化为只处理"缺失信息 / 无法解析"分支。

### P1-2｜缺少最终回答的 token 级流式事件

- 问题：API 是 SSE，但 §19.2 事件清单里没有流式 token 事件，`compose_response` 输出 `response` 字段暗示一次性返回。
- 影响：前端无法打字机效果，长报告体验差；若 compose_response 一次性生成长输出还有超时风险。
- 修改建议：增加 `ANSWER_STREAM` / `TOKEN` 事件，或明确"结论先行 + 结构化结果异步展示"的分段推送规则。

### P1-3｜`research_goal_satisfied()` 缺少具体机制

- 问题：§8.6 只给布尔式条件，没说"必需数据类别"如何映射到 SYNTHESIZE / LIMITED。
- 影响：研究完成判定不可复现，Agent 的 FINAL_CANDIDATE 无法被真正校验。
- 修改建议：让 `build_research_goal` 输出 `requiredDimensions: list[str]`，evaluate 对照 observations 计算 `coveredDimensions`，核心维度未覆盖一律 LIMITED 并披露 `missing_dimensions`。

### P1-4｜Strategy → Backtest 无显式衔接

- 问题：`StrategyState` 有 `backtest_request`，但 Strategy Graph 流程和 Root 路由都没定义"策略完成后进入回测"的边。
- 影响：用户说"设计策略并回测"会掉进单域限制。
- 修改建议：在 Root 增加 `STRATEGY_BACKTEST` 组合路由，或明确 Phase 4 前两者必须拆成两次对话。

### P1-5｜`load_strategy_data` 与 `compile_strategy_rules` 顺序存疑

- 问题：当前顺序是 `validate → load_strategy_data → compile_strategy_rules`，但标的池、时间频率应由编译后的规则决定。
- 影响：先加载的数据可能与最终编译规则不匹配。
- 修改建议：改成 `validate → compile_strategy_rules → load_strategy_data`。

## P2 可选优化

1. **`compose_response` 缺 grounding 约束**：明确只能基于 `structuredResult + observations` 组织语言，禁止引入未观察事实（可平移旧 Java 版的 GuardedOutput）。
2. **provider 分层**：§2.5 放弃付费门禁，但建议保留轻量的模型分层（分类/意图走便宜模型，研究合成走主力模型），避免全量走贵模型。
3. **会话上下文机制未定义**：`load_session_context` 只写了概念，未定义"谁写摘要、上下文预算 / 裁剪策略"（旧版 `ContextBudgetPolicy` 可直接平移）。
4. **并发控制**：同一 thread 的并发运行 / 恢复未定义（旧版有 SESSION_BUSY / CAS 版本号），建议 runtime 加 thread 级锁。
5. **数据时效策略**：Observation 有 `asOf` 但无"过期数据处置"策略，分析型系统可降级为标记，但应显式说明。
6. **`evaluate_research_state` 标"Code + optional Model"**：建议 Phase 2 一律确定性 CODE 实现，避免含糊。

## 缺失模块

- SSE 完整事件 payload Schema 表（§20 只有请求示例，没有事件契约）。
- 错误码与降级矩阵：模型超时 → 本地回退？MCP 失败 → LIMITED 的判定标准？
- 数据源 Provider 接口契约（行情 / 历史价格 / 基本面），Phase 2 依赖它却未给 schema。
- §23.3 要求固定测试数据，但数据来源未说明。
- 与现有 `stockwise-backend`（Java）和 `stock-analysis-skill` 的迁移 / 共存关系——Skill 推迟到 Phase 6，旧资产如何过渡没有交代。

---

## 职责冲突

1. Root 的 `normalize_request / resolve_entities` 与 Query Understanding 的 `extract_intent / resolve_entities` 重叠（对应 P1-1）。
2. "Agent 只提出动作、Graph 执行"与 §8.4 子图内 `execute_tool` 表述矛盾（对应 P0-1）。
3. `evaluate_research_state` 既是完成判定又"可选模型"，职责含糊（对应 P2-6）。

---

## 不必要复杂度

整体没有明显冗余。唯一要警惕的是：如果 P0-1 不解决，"单步 ReAct + 子图内循环"两套循环控制并存，那就是不必要的复杂度。

---

## 建议保留的设计

- "固定边界、动态路径"的执行哲学
- 单步结构化 ReAct 动作 + `AGENT_ACTION` 可审计事件
- Agent 只能提议、条件边由代码裁决
- MCP Adapter 启动期统一转 Tool
- Observation 统一结构（source / asOf / dataQuality / limitations / provenance）
- 明确不交易、无 Broker、无 god agent
- 统一终态集合（SUCCEEDED / LIMITED / NEED_USER / FAILED / INTERRUPTED）
- Skill 延迟到 Graph / Tool / Domain 稳定后再设计
- 不保存思维链、审计内容边界
- §23 的测试验收矩阵

---

## 一句话总结

方向对、职责清晰、纪律性强；把 P0-1（工具执行归属）和 P0-2（多子图路由 + 重路由回路）在写代码前定死，这套骨架就是可落地的。
