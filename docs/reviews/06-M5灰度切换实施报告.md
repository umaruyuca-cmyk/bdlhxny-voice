## 3. 当前发布门禁

真实灰度仍被阻断，原因如下：

- Run Registry 仍是进程内实现；
- Cognitive 实体上下文仍是进程内实现，尚无独立 Checkpoint namespace；
- M0 的 History/Checkpoint/多副本幂等故障注入尚未全部关闭；
- 未配置生产监控、告警 owner、审批引用和真实回滚演练证明；
- 未执行真实用户影子或灰度流量。

代码将 `production_storage_ready` 明确保持为 `False`，避免仅配置 PostgreSQL
Checkpointer 就误判为全部持久化门禁完成。

## 4. API、事件和数据库变化

- `/api/v1/chat/stream` 与 `/api/v1/agent-runs` 保持原路径和请求契约；
- 新路径 SSE 增加 `schema_version`、`runtimePath`、`routingReason`，不删除既有字段；
- `RunLocation` 增加 `runtime_path`，用于查询和恢复时保持路径粘性；
- `bdlh_runtime_chat_session` 增加可空字段 `pending_runtime_path VARCHAR(64)`；
- Cognitive clarification 保持同一 `run_id` 和运行路径，不转交旧 LangGraph resume。

## 5. 回滚方式

立即将 `BDLH_COGNITIVE_ROLLOUT_MODE=off` 并滚动重启服务。路由器会把全部新请求
导向旧 Root Graph；已在新路径发出 Domain Request 的运行不会自动重跑，必须保留原路径
结构化失败，避免重复外部调用。

## 6. 灰度顺序

门禁关闭后严格按以下顺序操作：

1. `internal`：只配置内部用户 ID；
2. `percentage`：从小比例开始并保持稳定观察窗口；
3. 逐步扩大比例；
4. `all`：owner 批准后将新路径作为默认；
5. 稳定观察期内保留旧 Root Graph。
