# StockWise 生产审查规范

> **文档角色：当前唯一有效的审查方法、严重级别和发布判定规范**  
> **版本：v1.0**  
> **生效日期：2026-08-10**  
> **上位架构：[00-StockWise统一生产架构.md](../architecture/00-StockWise统一生产架构.md)**  
> **实施入口：[00-StockWise生产开发实施Prompt.md](../prompts/00-StockWise生产开发实施Prompt.md)**

## 1. 目的

本规范解决三个问题：

1. 评审结论必须绑定代码版本、范围和证据，不能永久使用“当前代码”一类浮动表述；
2. 单元测试通过、阶段功能完成和生产可发布是三个不同结论；
3. 每个问题必须能直接转成开发任务，并带有明确验收方式。

本目录不再为每次讨论复制一份完整架构。架构事实以上位架构为准，开发阶段和契约以实施 Prompt 为准，审查报告只记录差异、证据和发布结论。

## 2. 权威顺序

发生冲突时按以下顺序处理：

1. 已生效的安全、合规和只读边界；
2. `docs/architecture/00-StockWise统一生产架构.md`；
3. 已批准的 API、数据和事件契约；
4. `docs/prompts/00-StockWise生产开发实施Prompt.md` 当前阶段要求；
5. 本规范；
6. 带提交号的当前审查报告；
7. Git 中的历史审查文档。

历史报告只能解释决策来源，不得覆盖当前架构和验收标准。

## 3. 审查快照必须包含的信息

每份审查报告必须在开头记录：

| 字段 | 要求 |
|---|---|
| 审查日期 | 使用绝对日期 |
| 代码基线 | 完整或可唯一定位的 Git 提交 |
| 工作区状态 | clean / dirty；dirty 时说明未提交内容是否进入范围 |
| 审查范围 | 服务、目录、接口和部署环境 |
| 排除范围 | 未执行的外部联调、压测、安全扫描等 |
| 目标阶段 | M0～M6 或明确的发布批次 |
| 验证环境 | OS、关键运行时及外部依赖方式 |
| 最终判定 | `GO`、`CONDITIONAL GO` 或 `NO-GO` |

没有提交号、证据或范围的结论只能标记为“待验证”，不能作为发布依据。

## 4. 状态与严重级别

### 4.1 验证状态

| 状态 | 含义 |
|---|---|
| `PASS` | 已有可重复证据证明满足验收标准 |
| `PARTIAL` | 部分实现或仅覆盖部分运行路径 |
| `FAIL` | 已验证不满足当前标准 |
| `NOT IMPLEMENTED` | 尚未实现，不得写成缺陷已修复 |
| `NOT VERIFIED` | 可能已经实现，但本次没有足够证据 |
| `NOT APPLICABLE` | 本阶段明确不适用，并说明原因 |

### 4.2 问题级别

| 级别 | 定义 | 发布规则 |
|---|---|---|
| `P0` | 数据越权、虚构金融事实、不可恢复状态丢失、核心链路不可用或缺少生产必需证据 | 必须关闭后才能发布 |
| `P1` | 可靠性、可观测性、回滚或主要功能存在明显风险 | 原则上关闭；例外必须有责任人、期限和降级方案 |
| `P2` | 可维护性、效率或非关键体验问题 | 可进入后续迭代 |

严重级别按影响评定，不按修改难度评定。

## 5. 生产审查门禁

### G0：范围与基线

- 审查提交可定位，工作区改动已说明；
- 本批次只覆盖一个明确阶段；
- 架构、Prompt、代码和部署配置没有互相冲突的“唯一真源”；
- 旧运行路径的保留、切流和删除策略已说明。

### G1：架构与边界

- Python、Java、前端、Gateway、MCP/Wrapper 的职责符合生产架构；
- `DomainRequest`、`DomainOutcome`、`Observation`、事件及 API 契约稳定；
- 客观研究与用户适配性结论分离；
- 确定性计算不交给 LLM，LLM 不直接访问基础设施；
- 新旧 Graph 不出现不受控的双写和双真源。

### G2：身份、安全与金融边界

- 所有用户数据请求从可信 JWT 推导 `user_id`，拒绝客户端覆盖；
- 跨服务内部调用有独立认证，日志不输出密钥、Token 和完整敏感数据；
- 生产环境禁止 Mock 冒充真实行情、持仓或搜索结果；
- 默认只读，不具备真实交易、转账或调仓执行能力；
- Prompt injection、Tool 参数、能力白名单和响应内容均有可执行 Guardrail。

### G3：状态、数据与恢复

- 会话、Checkpointer、运行注册、事件、分析历史和任务状态的持久化策略明确；
- 多实例、重启、超时、重复请求和断线重连行为可预测；
- 写入具备幂等键、唯一约束或等价防重机制；
- 数据携带来源、时间、质量、降级和 Mock 标识；
- 恢复接口不会跨用户访问运行状态。

### G4：功能与契约

- 主路径、降级路径、拒绝路径和恢复路径都有测试；
- SSE 事件类型、顺序、终态和错误语义稳定；
- API 前缀、Gateway 路由和前端调用保持一致；
- 阶段能力必须实际进入运行路径，不能只以类型或接口骨架宣称完成。

### G5：可靠性与依赖治理

- liveness 与 readiness 分离；readiness 检查生产必需依赖；
- 外部依赖设置连接/读取超时、重试上限、熔断或明确失败策略；
- 无静默异常、无限重试和无法取消的后台任务；
- 容器启动顺序、健康检查、优雅停机和资源限制已定义。

### G6：可观测性与审计

- 日志至少关联 `request_id`、`run_id`、`session_id`、可信 `user_id`；
- 关键节点、外部工具、Guardrail 决策和降级产生结构化事件；
- 有错误率、延迟、外部依赖、队列/任务和数据质量指标；
- 告警阈值、仪表板和审计数据保留策略可执行。

### G7：测试与质量

- Python、Java、前端相关测试全部通过；
- 契约、认证隔离、持久化恢复、SSE、生产禁 Mock 和迁移均有覆盖；
- 关键外部服务至少完成一次受控集成验证；
- 格式、静态检查、依赖和安全扫描结果可追溯；
- 测试数量只作为快照信息，不能替代测试覆盖说明。

### G8：部署、灰度与回滚

- 镜像可重复构建，配置模板完整且仓库无生产密钥；
- 数据库迁移可向前执行，破坏性变更有备份与恢复方案；
- Gateway 路由、SSE buffering、超时和请求体限制符合契约；
- 灰度指标、自动停止条件、回滚步骤和责任人已定义；
- 发布后有最小冒烟测试和观察窗口。

## 6. 组件重点检查

| 组件 | 必查项 |
|---|---|
| Python Analysis | Graph 接线、Checkpointer、运行/历史持久化、SSE、数据质量、生产禁 Mock |
| Java Backend | 用户与账户真源、内部认证、事务/迁移、遗留 Agent 开关、Python 数据接口 |
| Frontend | JWT、用户隔离、SSE 解析、终态处理、断线恢复、错误呈现 |
| Nginx / Gateway | 明确路由、身份头处理、SSE buffering、超时、健康入口、限流 |
| MCP / Wrapper | 能力白名单、协议差异、超时、来源与质量、降级语义 |
| PostgreSQL / Redis | 数据模型、唯一约束、连接池、备份、迁移、故障恢复 |
| LLM / Memory | 模型配置、成本预算、超时、记忆隔离、失败不阻断策略 |

## 7. 单个问题的标准格式

```markdown
### SW-R-XXX：问题标题

- 级别：P0 / P1 / P2
- 状态：OPEN / FIXED / ACCEPTED / NOT VERIFIED
- 影响范围：服务、接口或阶段
- 证据：文件:行号、测试、日志或命令结果
- 风险：真实故障场景和影响
- 根因：设计或实现原因
- 修复要求：只描述必须达到的结果
- 验收：可重复的测试或操作步骤
- 责任人 / 目标版本：发布任务中填写
```

不得只写“建议优化”“加强测试”或“注意安全”。每个问题都必须描述可观察的失败和关闭条件。

## 8. 发布判定

### GO

- 所有适用门禁为 `PASS`；
- 没有开放 P0；
- P1 已关闭，或已批准风险接受并具备期限、监控和降级方案；
- 回滚与生产冒烟证据齐全。

### CONDITIONAL GO

- 没有开放 P0；
- 只存在不会破坏本次范围的 P1；
- 每个例外都有明确责任人、到期日、监控和自动停止条件。

### NO-GO

满足任一条件即为 `NO-GO`：

- 存在开放 P0；
- 关键结论仅有代码推断，没有生产或等价环境证据；
- 生产状态不可恢复、身份边界不可证明或金融数据可能被 Mock 冒充；
- 无法可靠回滚。

## 9. 文档生命周期

- `00-StockWise生产审查规范.md`：长期维护的审查规则；
- `01-StockWise当前生产就绪审查报告.md`：仅保存最新一次全局审查快照，每次更新必须修改基线提交和验证日期；
- `历史审查索引.md`：记录被取代报告的来源和仍有效结论；
- 单批次审计优先写进对应 Issue、PR 或发布记录，不在本目录长期堆叠；
- 被替代的报告从工作树清理，通过 Git 历史恢复。
