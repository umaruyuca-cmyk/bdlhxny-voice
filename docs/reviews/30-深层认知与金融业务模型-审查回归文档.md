## 0. 总体结论

**评分：9 / 10（作为架构愿景）/ 4 / 10（作为近期开发任务）**

28/29 号是整个项目迄今为止架构水平最高的设计。它们把 StockWise 从"对话式股票分析 Agent"提升到了**"认知-领域分层的事件驱动金融管家"**——这是正确的产品演进方向。

但这两份文档与当前代码（v2.1）存在**架构级差距**（预估 2-3 月工作量），且复杂度对个人项目偏高。**结论：当"北极星"指引方向，不当"下一阶段"立即执行。**

## 1. 两份文档的关系

28 号（认知内核）和 29 号（金融领域）是**上下游分层**关系，不是并列：

```
28号 深层认知内核（通用，不碰金融逻辑）
  ├─ 情境理解 / 信念维护 / 目标识别 / 不确定性评估
  ├─ 决策"下一步做什么"（7种行动，不只回答）
  ├─ 调用领域模型（DomainRequest）
  ├─ 吸收领域结果（DomainOutcome）
  └─ 管理任务 / 承诺 / 记忆 / 沟通
      │ DomainRequest
      ▼
29号 金融业务模型（专业，不碰对话理解）
  ├─ 接收明确的金融目标（不是原始用户消息）
  ├─ 选 Skill（stock-research / portfolio-health / ...）
  ├─ 调统一能力取数（经 Tool Gateway）
  ├─ 确定性计算（domain/）
  ├─ 适配性判断（SuitabilityEngine）
  ├─ Critic 四类复核
  └─ 返回 FinancialDomainOutcome
      │ FinancialDomainOutcome
      ▼
28号 吸收结果 → 决定表达/追问/建任务/等待
```

**核心设计哲学：对话理解和金融专业能力彻底分离。** 这是对当前"一个 Root Graph 全干"的根本性重构。

## 2. 设计亮点（5 个真正有价值的创新）

### 亮点 1：信念系统（28号 §5.3）—— 全文档最深刻的设计

```python
class Belief:
    status: Literal["CONFIRMED", "SUPPORTED", "INFERRED", "DISPUTED", "UNKNOWN"]
```

当前系统（v2.1）的痛点：LLM 说出来的话没有"可信度标签"——它可能把"推断"说成"事实"。信念系统强制每条信息标注来源等级，且**推断不能静默升级为事实**。

**直接价值**：这是从系统层面根治 LLM 幻觉的机制，不靠 prompt 求模型"别编"。

### 亮点 2：下一行动不等于回答（28号 §3.4）

```python
NextAction: RESPOND | ASK_USER | INVOKE_DOMAIN | CREATE_TASK | WAIT | NOTIFY | DO_NOTHING
```

当前系统对每个输入的默认动作都是"回答"。28 号的核心洞察：**用户的每句话首先是一次状态更新，"回答"只是 7 种可能行动之一。** 例："茅台贵了先帮我看着" → 正确动作是 `CREATE_TASK`（建观察任务），不是 `RESPOND`（回答"好的"）。

### 亮点 3：领域适配性引擎（29号 §13）—— 金融专业性的核心

```python
class SuitabilityAssessment:
    result: Literal["SUITABLE", "CONDITIONALLY_SUITABLE", "CURRENTLY_NOT_SUITABLE", "INSUFFICIENT_INFORMATION"]
```

**"这是好资产吗" vs "这适合当前用户吗"是两个完全不同的问题。**

当前系统把两者混在一起（LLM 直接说"建议买入"）。29 号强制分开：
- `stock-research` Skill 只回答"资产本身好不好"（客观研究）
- `SuitabilityEngine` 结合用户持仓/目标/流动性回答"适不适合你"（主观适配）

### 亮点 4：事件驱动 + 持续任务（28号 §3.1/3.5）—— 产品差异化的关键

```python
InputEvent: USER_MESSAGE | SCHEDULED_WAKEUP | MARKET_EVENT | GOAL_DEADLINE | TASK_RESUMED
```

当前系统是纯"请求-响应"（用户不问就不动）。28 号引入事件驱动——**系统可以因市场变化、目标到期、任务唤醒而主动行动。** 配合 Commitment（系统答应过用户什么）和 Scheduler，实现真正的"持续性"。

这是"随身管家"和"问答工具"的本质区别。

### 亮点 5：Critic 四类复核（29号 §15）

```
数据复核 / 计算复核 / 适配性复核 / 输出复核
```

v2.1 的 Guardrails 是"格式/权限校验"，29 号的 Critic 更深一层——复核**结论的逻辑正确性**（如"是否把优质资产等同于适合买入"、"是否隐藏重大限制"）。

## 3. 与当前代码（v2.1）的差距

| 维度 | v2.1（当前代码 `42b0722`） | 28/29 号目标 | 差距 |
|---|---|---|---|
| 顶层架构 | 一个 Root Graph 全干 | 认知内核 + 领域运行时分层 | 🔴 架构级重构 |
| State | 一个 RootState | CognitiveState + FinancialBusinessState 拆分 | 🔴 拆分 |
| 对话理解 | QueryIntent（意图+实体） | Belief / Goal / Uncertainty / SpeechAct 信念系统 | 🔴 全新概念 |
| 行动选择 | dispatch_workflow（固定任务链） | NextAction 7 选 1（含 CREATE_TASK / WAIT） | 🔴 全新机制 |
| 股票分析 | 顶层流程 | 下沉为 stock-research Skill（子图） | 🟡 重构 |
| 适配性 | 无（LLM 直接说） | SuitabilityEngine（独立模块） | 🔴 新建 |
| 持续任务 | 无 | Task / Commitment / Scheduler | 🔴 新建 |
| 事件驱动 | 只有 HTTP 请求 | 7 种事件类型 | 🔴 新建 |
| 沟通层 | compose_response（一个节点） | CommunicationPlan + Response Verification（两阶段） | 🟡 增强 |

**工作量预估**：28 号列了 8 步实施顺序，29 号列了 5 个阶段——合计约 13 个里程碑，预估 **2-3 个月全职工作量**。

## 4. 三个真实的风险

### 风险 1：过度设计（P1）

28/29 号的复杂度接近商业银行投顾系统水平（信念系统、目标管理、不确定性分类、承诺追踪、适配性引擎、Critic……）。**对于个人项目/求职作品，很多模块（如 Commitment 追踪）在单人使用场景下价值很低，但开发成本高。**

### 风险 2：与 v2.1 的断裂（P1）

当前代码的 Root Graph / dispatch_workflow / build_data_requirements 都是"对话+金融"耦合的。28 号 §19 的迁移清单很诚实，但实际拆分"认知内核+领域运行时"意味着**几乎重写整个编排层**——不是"重构"，是"重建"。

### 风险 3：信念系统的 LLM 可靠性（P2）

Belief 系统设计很美，但**让 LLM 稳定输出 `CONFIRMED vs INFERRED vs UNKNOWN` 判断有失败率**。LLM 可能把不确定信息标成 CONFIRMED。虽然系统有"信念不能静默升级"规则，但初始标注错了规则也救不回来。需要大量 prompt 调试。

## 5. 渐进回归路径（从 v2.1 到 28/29 目标）

**核心策略：不一步到位，分三波渐进引入 28/29 的核心概念。**

### 第一波（近期，~2 周）：完成 v2.1 阶段一/二（不动 28/29）

```
v2.1 §17 阶段一：执行模式选择 + 语义修正
  · IntentRoute（direct_response / single_capability / agent_loop）
  · 删除"缺股票代码就中断"
  · direct_response 快路径

v2.1 §17 阶段二：planner-executor + Guardrails
  · TaskPlan 动态生成（替代固定 WorkflowPlan）
  · 四时点 Guardrails
  · 重规划机制（≤2 次）

→ 完成后系统已是"对话式 Agent"，能处理无代码/市场/宏观问题
→ 这一步不引入 28/29 任何概念，先把 v2.1 做完
```

### 第二波（中期，1-2 月）：选择性引入 28/29 的 3 个核心概念

从 28/29 里挑**性价比最高**的 3 个概念，渐进融入 v2.1（不搞全套认知内核）：

| 引入的概念 | 来源 | 融入方式 | 价值 |
|---|---|---|---|
| **Belief 状态标注** | 28号 §5.3 | 给 Observation/Finding 加 `confirmed/inferred/unknown` 标签，Response Composer prompt 强制区分 | 根治幻觉，最小代价 |
| **NextAction 扩展** | 28号 §5.7 | dispatch 的候选从"任务节点"扩展到含 `CREATE_TASK / WAIT` | 支持"先帮我看着"类请求 |
| **SuitabilityEngine** | 29号 §13 | 股票研究后加一步"适配性判断"（结合 user_profile + portfolio） | 区分"好资产"vs"适合你" |

**不引入**（成本高/单人场景价值低）：
- Commitment 追踪（28号 §5.6）—— 单人场景下过度
- 完整事件驱动 + Scheduler（28号 §3.1）—— 先靠用户主动触发
- CognitiveState / FinancialBusinessState 拆分 —— 等 v2.1 稳定后再考虑

### 第三波（远期，3 月+）：如果验证成功，做完整分层

等 v2.1 + 第二波增强稳定后，再评估：
- 拆分 CognitiveState / FinancialBusinessState
- 引入完整事件驱动 + Scheduler
- 完整 Task / Commitment 系统
- 多领域扩展（非金融领域）

## 6. 立即可吸收的一个思想（最小代价，最大收益）

即使不实现完整 SuitabilityEngine，**29 号 §13 的这句话应该立刻体现在 Response Composer 的 prompt 里**：

> **必须区分："这是不是一个质量较好的资产？" vs "这是不是当前适合这个用户的资产？"**

当前 compose_response 节点的 prompt 没有这个区分——LLM 可能直接说"茅台基本面良好，建议关注"，但没结合用户持仓。**在 prompt 里加一句约束**（"客观研究和用户适配性分开表述"），是提升金融建议质量的最小代价改动。
