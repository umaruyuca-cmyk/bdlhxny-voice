# StockWise 历史版本档案 02：V1 新旧系统融合架构

> 版本性质：历史迁移方案，部分原则已被 V2.x 替代  
> 形成日期：2026-08-04  
> 代表提交：`8676bea`  
> 原始版本：融合架构设计 v1.0

## 1. 版本定位

本版本解决的是新 Python 分析引擎如何与现有多模块系统融合，而不是重新定义股票分析业务本身。

当时的现有系统由以下部分组成：

- Java 后端；
- Node Wrapper 和数据能力；
- 静态前端；
- Nginx；
- DB、Redis 等共享基础设施。

## 2. 迁移目标

- 用 Python 新引擎替代 Java 中的 Agent 编排与分析大脑；
- 尽量保持前端 API 契约不变；
- 通过 Nginx 分流实现新旧链路平滑切换；
- 在过渡期允许 Java 与 Python 双引擎并行；
- 复用仍有价值的数据、用户和基础设施能力；
- 最终退役 Java Agent 编排部分。

## 3. 目标调用关系

```text
前端
  → Nginx / API Gateway
      ├─ 旧 Java Agent 链路
      └─ Python 新分析链路
          ├─ Node 数据能力
          ├─ Java 用户数据
          ├─ DB
          └─ Redis
```

## 4. 前端需求

- 保持现有页面和交互尽量不变；
- 保持主要 API 请求与响应兼容；
- 通过 Nginx 调整反向代理目标；
- 迁移期可以按任务类型将请求分别路由到 Java 或 Python；
- 可选新增 Python 引擎专属页面用于测试和灰度。

## 5. Java 后端处置

### 5.1 计划废弃

- Java Agent 编排；
- Java 中重复的 LLM 流程；
- 被 Python Graph 取代的动态分析流程。

### 5.2 计划迁移

- 有价值的确定性业务逻辑；
- 适合放入 Python Domain 层的指标和分析逻辑；
- 与股票分析强相关但不应继续由 Java Agent 承担的能力。

### 5.3 计划保留

- 用户、持仓、账户相关能力；
- 权限和认证相关服务；
- 共享数据库与基础设施；
- 迁移期不可立即替换的业务 API。

## 6. Node 层处置

本版本最初计划在过渡期继续通过 HTTP 复用 Node 数据能力，以降低一次性迁移成本。

主要要求：

- Python 通过薄 Adapter 调用 Node；
- Node 不参与 Python Agent 编排；
- 接口保持结构化；
- 后续再判断能力保留、迁移或退役。

## 7. 部署要求

- Python、Java 在迁移期独立部署；
- 共享 DB 和 Redis；
- Docker Compose 增加 Python 服务；
- Nginx 负责新旧路径分流；
- 支持单独健康检查和故障回退；
- 迁移过程不能一次性破坏旧链路。

## 8. 迁移步骤

1. 建立 Python 项目骨架；
2. 通过兼容 API 接入现有前端；
3. 接入现有数据能力；
4. 分阶段迁移研究、组合、策略和回测能力；
5. 新旧链路并行对照；
6. 逐步将流量切换到 Python；
7. 验收后退役 Java Agent 编排。

## 9. 后续版本修正

V2.x 对本方案作出以下重要调整：

- 市场数据改由 MCP 统一提供；
- Java 明确只保留用户和账户数据 API；
- `stock-wrapper` 降级为仅用于离线回归；
- 确定性分析优先迁移到 Python Analysis Engine；
- 新生产链路不再依赖 Node Wrapper 作为数据备份源。

## 10. 版本遗产

本版本保留下来的核心迁移原则包括：

- Python 新架构与旧系统渐进式切换；
- 前端和 API 优先兼容；
- 新旧路径并行验证；
- 复用用户数据和基础设施，而不是重写全部系统；
- 新路径稳定前不删除旧路径。
