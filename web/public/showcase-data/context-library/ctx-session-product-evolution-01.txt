# 长上下文构建与压缩

## 1. 目标和边界

固定用例的问题正文通常很短，真正消耗 token 的是问题附带的系统约束、工具定义、用户数据、记忆、行情、新闻和多轮工具结果。因此本设计不压缩固定问题本身，而是压缩一次运行可使用的候选上下文。

目标是：

- 在给定 token 上限内生成模型实际需要的上下文；
- 用户约束、权限、关键数字、数据时间和证据引用不能因压缩丢失；
- 被省略的信息仍可通过内部引用追溯；
- 压缩过程可解释、可测试、可替换；
- 压缩带来的 token 节省必须大于压缩自身的模型成本；
- 压缩失败不能绕过安全约束。

本项目不实现跨 Codex、Cursor、OpenCode 的 Session 交接，也不保存通用聊天历史。ContextHub 文档中的可用部分被简化为：上下文条目、按预算选择、多种表示方式、来源追溯和评测对照。

## 2. 输入和输出

### 2.1 输入

上下文构建器接收：

```json
{
  "case_id": "portfolio-value-001",
  "case_version": 3,
  "scene": "portfolio",
  "message": "我的持仓现在值多少钱",
  "snapshot_id": "snap-001",
  "token_budget": 16000,
  "allowed_tools": [
    "portfolio.get_current_positions",
    "market.get_realtime_quote",
    "portfolio.build_current_valuation"
  ],
  "context_strategy": "budgeted"
}
```

### 2.2 输出

上下文构建器输出：

1. `messages`：发送给模型的消息；
2. `context_report`：说明上下文如何被处理；
3. `cache_key`：用于复用相同构建结果；
4. `validation`：关键约束、引用和预算检查结果。

上下文构建结果必须是结构化对象。各模型适配器可以把它渲染为具体消息格式，但不能重新选择或删除内容。

## 3. 上下文条目

候选上下文先被拆成独立条目。每个条目至少包含：

```json
{
  "id": "holding-300750",
  "type": "portfolio_fact",
  "content": {
    "symbol": "300750",
    "weight": 0.18,
    "quantity": 200
  },
  "source_ref": "snapshot://snap-001/positions/300750",
  "source_time": "2026-08-20T14:32:00+08:00",
  "authority": "data-service",
  "trust": "verified",
  "required": true,
  "relevance": 0.95,
  "raw_tokens": 82,
  "status": "active"
}
```

建议类型：

| 类型 | 示例 | 默认处理 |
|---|---|---|
| `system_constraint` | 不允许交易、适合度口径 | 强制保留 |
| `case_input` | 固定问题、场景、权限 | 强制保留 |
| `watch_event` | 演示注入的价格事件 | 事件用例强制保留 |
| `user_profile` | 风险承受能力、投资期限 | 结构化保留 |
| `portfolio_fact` | 持仓、现金、权重 | 结构化保留 |
| `memory_fact` | 与当前用例相关的已确认事实 | 检索后选择 |
| `market_observation` | 行情、历史价格 | 保留数字、来源和时间 |
| `fundamental_observation` | 财务指标和估值输入 | 保留计算依赖项 |
| `news_evidence` | 新闻标题、摘要、来源 | 去重、检索、必要时摘要 |
| `tool_failure` | 工具超时、参数错误 | 保留错误签名和状态 |
| `data_quality` | 过期、缺失、冲突 | 被引用数据必须保留 |
| `previous_result` | 预设多步用例的上一步结果 | 只保留结构化状态和引用 |
| `raw_reference` | 长日志、原文、完整响应的位置 | 只在内部保存引用 |

## 4. 来源和指令隔离

上下文中的文字不具有相同权力。系统必须区分“指令”和“数据”。

### 4.1 来源优先级

发生冲突时，按以下顺序处理：

1. 当前系统安全规则；
2. 当前固定用例和登录身份；
3. 用户明确确认的约束；
4. 数据快照和工具返回的结构化事实；
5. 已确认记忆；
6. 模型从文本中提取的结论；
7. 新闻、网页、日志和其他外部文本。

新内容不会自动覆盖高优先级旧内容。替换或撤销约束必须生成明确的新版本，并记录被替换条目。

### 4.2 防止间接提示注入

- 新闻、网页、日志、工具返回和历史模型输出一律放入“数据”区域；
- 数据中的“忽略之前要求”“调用某工具”等文字不能提升为系统指令；
- 模型提取的约束或事实必须携带原始来源；
- 没有来源或与数据快照冲突的提取结果不能进入强制保留集合；
- 公开工件只展示处理结果和安全摘要，不展示可能包含敏感指令的完整原文。

## 5. 按场景选择上下文

每个场景配置一份普通规则文件，说明哪些内容强制保留、优先保留和通常省略。

| 场景 | 强制保留 | 优先保留 | 通常省略 |
|---|---|---|---|
| 行情 | 问题、标的、最新行情、来源、时间 | 相关短期历史 | 无关记忆、长新闻 |
| 研究 | 问题、C-1/C-2、核心财务指标 | 同行数据、相关新闻、历史估值 | 无关持仓和日志 |
| 组合 | 问题、身份、全部持仓摘要、风险画像 | 主要标的行情、集中度 | 新闻全文、无关知识 |
| 适合度 | 问题、身份、风险画像、C-2、披露 | 产品风险、用户期限 | 无关实时行情 |
| 看护 | 事件、持仓影响、风险画像、来源 | 相关记忆和新闻 | 其他标的信息 |
| 拦截 | 原始请求、身份、禁止规则 | 拒绝原因 | 行情、持仓和工具数据 |
| 知识 | 问题、基础系统规则 | 相关知识片段 | 用户持仓和私有记忆 |

规则文件只决定候选范围和硬限制，不能写入预期答案。

## 6. Token 预算

模型窗口不能全部分配给候选上下文。预算至少分成：

```text
模型最大窗口
├─ 系统规则
├─ 固定问题
├─ 工具定义
├─ 工作上下文
├─ Agent 多轮新增工具结果
├─ 最终输出预留
└─ 安全余量
```

示例：模型窗口为 32K 时，可以从以下初始配置开始，再用真实评测调整：

| 部分 | 示例预算 |
|---|---:|
| 系统规则和固定问题 | 2K |
| 工具定义 | 3K |
| 初始工作上下文 | 15K |
| 后续工具结果 | 6K |
| 最终输出 | 4K |
| 安全余量 | 2K |

预算配置必须按模型 tokenizer 计算。估算 tokenizer 只能作为降级方案，并预留更大的安全余量。

## 7. 压缩步骤

### 7.1 第一步：收集和标准化

从固定用例、数据快照、用户画像、持仓、记忆和工具数据中收集候选条目。统一数字类型、时间格式、来源引用和状态，去除完全重复的条目。

### 7.2 第二步：确定强制保留项

以下内容不参与普通打分淘汰：

- 系统安全规则；
- 当前固定问题；
- 当前身份和权限；
- 用户明确约束；
- 当前事件；
- 当前用例的验收条件；
- 未解决的高风险数据问题；
- 最终计算依赖的数字、时间和来源。

如果强制保留项本身已经超过预算，本次运行标记为上下文构建失败。系统不能通过删除安全规则继续运行。

### 7.3 第三步：为条目准备不同长度的表示

一个条目可以有以下表示方式：

| 表示方式 | 内容 | 适用情况 |
|---|---|---|
| 完整内容 | 原始文本或完整结构 | 很短且关键 |
| 结构化摘要 | 保留字段、数字、状态、错误签名 | 持仓、行情、日志、工具结果 |
| 文本摘要 | 对较长自然语言生成短摘要 | 新闻和历史讨论 |
| 引用 | 只提供类型、hash 和内部位置 | 源文件、完整日志、长原文 |
| 省略 | 不进入工作上下文 | 低相关且可恢复内容 |

数字、日期、权限和系统规则不能只保留自由文本摘要。

### 7.4 第四步：计算优先级

第一版使用可解释的规则，不训练新模型：

```text
priority =
  relevance * wr
  + authority * wa
  + freshness * wf
  + source_quality * wq
  + task_impact * wi
  + citation_dependency * wc
  + failure_risk * we
  - staleness * ws
```

权重按场景配置。为了避免长条目占用全部预算，实际选择时使用：

```text
selection_value = priority / representation_tokens
```

### 7.5 第五步：在预算内选择

第一版算法按以下顺序执行：

```text
1. 放入全部强制保留项
2. 为剩余条目生成可用的不同长度表示
3. 按 selection_value 从高到低选择
4. 某条目放不下时，尝试更短表示
5. 保留被选条目的依赖项和来源引用
6. 达到预算后停止
7. 运行完整性检查
```

后续可以替换为更精确的预算求解方式，但对外行为和报告字段保持不变。

### 7.6 第六步：完整性检查

至少检查：

- 所有强制项仍在；
- token 总数不超过预算；
- 每个事实性数字都有来源；
- 每个引用指向数据快照或内部原始记录；
- 被选条目的依赖项没有缺失；
- 过期数据带有明确质量标记；
- 外部文本没有进入系统指令区域；
- 公开字段没有真实用户敏感信息。

## 8. Agent 循环中的再次压缩

初始上下文合格并不代表整个运行不会超出窗口。每轮工具调用都会增加 Observation。因此每轮模型调用前都要重新检查预算：

1. 当前轮模型刚提出的工具调用和最近工具结果优先保留；
2. 已被结构化结果取代的旧工具原文降级为引用；
3. 重复工具结果合并；
4. 被最终回答引用的 Observation 不得省略；
5. 如果仍然超预算，停止继续调用工具并返回明确的预算错误或部分结果。

系统不保存或压缩模型隐藏思维过程，只处理可观察的消息、工具调用和工具结果。

## 9. 稳定内容、动态内容和缓存

### 9.1 稳定内容

以下内容变化较少，可按版本缓存：

- 系统安全规则；
- 固定用例；
- 场景规则；
- 工具定义；
- 风险披露；
- 已确认长期记忆。

### 9.2 动态内容

以下内容必须按运行或有效期更新：

- 当前行情；
- 当前运行选择的数据快照；
- 当前持仓和现金；
- 工具执行结果；
- 数据质量状态。

### 9.3 缓存键

```text
case_version
+ context_profile_version
+ snapshot_hash
+ compiler_version
+ tokenizer_id
+ tool_catalog_version
```

命中缓存只节省上下文收集和压缩成本，不允许复用旧的动态工具结果。缓存命中、失效原因和节省时长都进入运行记录。

## 10. 预设多步用例

多步用例每一步完成后只产生结构化状态：

```json
{
  "step": 1,
  "resolved_entities": ["300750"],
  "selected_facts": ["holding-300750", "risk-profile-01"],
  "result_refs": ["observation://run-001/2"],
  "active_constraints": ["C-1", "C-2"]
}
```

下一步上下文由固定问题、结构化状态和仍有效的证据重新构建，不直接附加上一步全部自然语言。这样可以评测指代和连续性，同时避免通用会话历史膨胀。

## 12. 失败和降级

| 问题 | 处理 |
|---|---|
| tokenizer 不可用 | 使用保守估算并增加安全余量，记录降级 |
| LLM 摘要失败 | 回退到结构化摘要或引用，不使用空白摘要 |
| 强制项超过预算 | 运行失败，不删除安全项 |
| 引用失效 | 运行无效，不能发布 |
| 来源冲突 | 同时保留冲突值、来源和时间，交给代码规则判断 |
| 缓存版本不一致 | 缓存失效并重新构建 |
| 上下文构建超时 | 按用例配置使用最小安全上下文或标记无效 |

## 13. 对照方式

上下文压缩单独比较以下策略，Agent 实现方式、模型、温度、工具数据和数据快照保持不变。四种策略相互独立：只有 `budgeted` 使用项目自研算法，其余三种是行业常见基准；四种方式可以共用安全隔离与记录入口，但**不得**都经过自研压缩，否则实验无法证明自研算法优于基准。

| 策略 | 说明 | 当前实现 |
|---|---|---|
| `full` | 在窗口允许时发送全部候选上下文，作为质量与成本上限 | 已实现；超预算直接失败，不静默截断 |
| `recent-n` | 简单截断基线：公共系统规则等 required 始终保留，从最后一个事件向前选完整条目，达到预算即停 | 已实现（修复：required 不再被窗口截掉） |
| `single-summary` | 一次性摘要基准：required + 最近事件原文 + 更早事件一次性摘要 | 已实现；摘要器（`summary.py`）与自研规则压缩器分离，默认确定性抽取式，可注入 LLM 摘要 |
| `budgeted` | 自研：强制保留、结构化压缩、按优先级和公平份额选择 | 已实现（structured-text-v1 早期版本；多因子重要度与 selection_value 仍是设计稿） |

完整自然 Session 的交叉验证（4 策略 × 3 Agent 模式 = 12 组矩阵）、派生工件冻结与 gold 评测见 [Session交叉验证设计.md](Session交叉验证设计.md)。评测指标和有效性规则见 [Agent 对照评测与证据展示.md](../evaluation/Agent对照评测与证据展示.md)。具体的长上下文组成、正反例和网页测试用例见 [固定用例与网页展示.md](../showcase/固定用例与网页展示.md)。

# Session 交叉验证设计（4 上下文策略 × 3 Agent 模式）

本文档是"固定问题、冻结 Session、冻结 Mock Tools、比较不同 Agent 实现方式"
产品目标下的交叉验证完整设计，同时如实区分**已实现**与**仍属设计**的部分。
第一个固定用例为 `ctx-session-touchstone-design-01`（102 个事件的冻结自然
Session），数据位于 `engine/var/cases/ctx-session-touchstone-design-01/`。

## 1. 实验目标和结论边界

**目标**：在同一份原始 Session、同一个当前问题、同一模型/温度/工具目录/
Mock fixture/评测标准下，单独观察两个变量：

1. 上下文处理方式（4 种）对 Agent 表现的影响；
2. Agent 实现方式（3 种）对上下文利用效率的影响；
3. 两者组合是否存在交互效应。

**结论边界**：

- 所有工具返回均为冻结 Mock。结论只覆盖 Agent 的工具选择、参数、调用顺序、
  权限、错误处理、上下文保留与任务完成，**不**覆盖真实第三方 API 的数据
  质量、网络性能或可用性；
- 模拟延迟均显式标记 `simulated: true`，不得对外冒充真实 API 延迟；
- 本用例 Session 约 9.4K token（保守估算），适合验证数据结构与全链路；
  32K/64K 窗口测试需要继续加入自然的完整文件内容、日志与工具结果，
  **不得**用编号短句批量填充长度。

## 2. 12 组矩阵与固定条件

| 上下文方式 ↓ / Agent 模式 → | 裸 Tool Calling | LangGraph ReAct | 完整工程 Agent |
|---|---|---|---|
| full-session（完整透传） | 运行 | 运行 | 运行 |
| recent-window（最近窗口） | 运行 | 运行 | 运行 |
| single-summary（一次摘要） | 运行 | 运行 | 运行 |
| budgeted-session（按预算压缩） | 运行 | 运行 | 运行 |

每个单元格固定：同一 `source_session_hash`、同一当前问题、同一模型与温度
（0.1）、同一工具可见集（7 个只读工具）、同一 Mock fixture 集、同一最大
工具调用数（20）、同一有效重复次数（默认 3）、同一评测器与有效性规则。
每格记录：模型、温度、Agent 模式、Session 版本、上下文策略、
`compiled_context_hash`、公共提示词 hash、工具目录 hash、fixture hash、
Git commit 与评测器版本。

**冻结纪律**：四份派生输入先编译、hash、落盘（`compiled/*.json`），三个
Agent 模式读取同一份冻结工件。完整工程组通过 `FrozenContextBuilder` 按
item id 命中冻结构建结果，不重新生成；裸调用/ReAct 组直接消费冻结工件
渲染出的消息。算法、摘要提示或预算变化必须产生新的 `strategy_version`
和 hash，同批次工件不可修改。

## 3. Session 数据结构（已实现）

`loader.py` 加载并校验 `*.session.json`：

- `events[]`：`seq` 从 1 连续递增，`event_id` 唯一；类型限
  `user_message` / `assistant_message` / `tool_call` / `tool_result`；
- 每个 `tool_result` 必须紧跟配对的 `tool_call`（call_id 匹配、无悬挂）；
- `runtime_case.current_question` 非空、`visible_tools` 为工具可见集；
- `source_hash = sha256(规范化 JSON)`，四份派生输入必须同源。

原始事件正文只含自然对话与工具过程，不含任何评测标注。

## 4. 四种派生输入规则（已实现）

公共序列化（`serializer.py`）：用户/助手消息 → conversation 条目（保持
角色与顺序）；`tool_call`+`tool_result` → **合并为一条不可信数据条目**
（调用与结果不可拆开）。序列化只读 session，不读 gold。

| 策略 | 构建器映射 | 行为 | 预算 |
|---|---|---|---|
| full-session | `full` | 全部条目按序透传；超窗即失败（`invalid_context_too_large`），不静默截断 | 16384 |
| recent-window | `recent-n` | 公共系统规则与当前问题（required）**始终保留**；从最后事件向前选完整条目，预算耗尽即停 | 4096 |
| single-summary | `single-summary` | required 原文 + 最近事件原文（1024）+ 更早事件一次性摘要（≤2560）；摘要器与自研压缩器**分离** | 4096 |
| budgeted-session | `budgeted` | 自研算法：required 原文保留，其余按 priority+公平份额压缩/引用/省略（structured-text-v1 早期实现） | 4096 |

single-summary 的默认摘要器是确定性的 `ExtractiveSummarizer`
（均匀分配预算、按句边界抽取，`extractive-uniform-v1`）；接口支持注入
一次性 LLM 摘要（生成后冻结，Token/时长/成本单独记入工件
`build_model_calls/build_input_tokens/build_output_tokens/build_cost`）。
摘要器不得读取 gold，也不得复用 budgeted 的选择结果。

## 5. 派生工件（已实现）

每份工件含 `variants.compiled_context_artifact_required_fields` 全集：
`case_id / case_version / source_session_hash / variant_id / strategy_version /

全部事件 id（含合并的工具对两个 id）。

## 6. Mock fixture 规则（已实现）

`mock_dispatcher.py` 按 gold 的 `runtime_mock_fixtures` 匹配：

- 精确参数子集匹配 → 返回冻结结果（成功或错误状态），均带 `simulated: true`；
- 同名 fallback fixture → `FILE_NOT_IN_FIXTURE`，**绝不把正确内容当兜底**；
- 未登记工具 → `TOOL_NOT_IN_FIXTURE`；
- 每次调用记录 step、工具名、参数、命中 fixture、状态与结果摘要。

错误路径不返回正确答案，参数错误必须返回参数错误，这样工具选择错误与
参数错误才能进入统计。

## 7. 内部标准答案（gold）结构与使用边界

gold 含：`current_active_constraints`（含证据事件 id）、
`superseded_decisions`（旧说法+替代说法）、`required_facts`、
`forbidden_claims`、`expected_tool_plan`（必需/可选/不必要/禁止/不存在
工具与顺序规则）、`runtime_mock_fixtures`、`answer_rubric`、
`evaluation_checks`。

gold 存放于 `gold/` 子目录，仅 `mock_dispatcher`（配置冻结返回）与
`gold_eval`（运行后评测）允许读取；`SessionCompiler.compile()` 签名不含
gold，接口层阻断答案泄漏。禁止把 gold 拼入摘要提示、工具描述或公开页面。

## 8. 指标公式（已实现机械部分）

**工具指标**（`gold_eval.grade_tool_calls`）：

- 正确工具选择率 = 名称+关键参数命中的 required 调用数 / required 总数；
- 漏调用：required 工具名称从未出现；参数不匹配单独计 `argument_mismatch`；
- 额外/不必要/禁止/不存在工具调用与重复调用（同参数规范化键）分别计数；
- 顺序正确：required 命中位置单调递增。

**上下文指标**（`grade_compiled_constraints`，按编译工件计算，与运行无关）：

- 约束保留率 = 任一证据事件被保留（kept/compressed/referenced）的约束数 /
  要求约束总数。

**答案指标**（`grade_answer`，机械近似）：

- 废弃决定误用：答案含旧说法特征片段（或字符 bigram 重叠 ≥ 0.6 的近似复述）；
- 禁用说法：`forbidden_claims` 同口径检查；
- 未修改文件声明：答案含"未修改/没有修改"等关键词。

当前这份 Session 的基线对照（编译阶段即可复现）：full / single-summary /
budgeted 的约束保留率均为 100%，**recent-window 仅 33%**（丢失 6 个早期
决定）——这正是简单窗口基准应当暴露的缺陷。

## 9. 无效运行规则

- 基础设施故障、模型限流、余额不足、评测器失败 → INVALID，不进能力指标；
- Agent 自身失败（选错工具、参数错误、超出调用预算、违反权限、任务未完成、
  循环内预算耗尽被诚实停止）→ 有效失败，进入统计；
- 单运行设超时熔断（`EVAL_RUN_TIMEOUT_S`，默认 300s），超时按 INVALID 收尾；
- 失败案例保留，可按 `run_key` 下钻到 `tool_calls` 与 `mock_records`。

# 产品目标与使用方式

## 1. 产品定义

Touchstone 用固定题库比较不同 Agent 实现方式，并把比较过程公开展示。它要回答的不是“模型能不能聊天”，而是以下工程问题：

- 模型是否选择了正确工具；
- 工具权限、只读限制和调用预算是否由代码可靠执行；
- 长上下文压缩后，关键事实和用户约束是否仍然保留；
- token、运行时长和成本减少后，任务成功率是否下降；
- 任何汇总数字能否回到单次运行记录进行核对。

该项目主要用于面试展示、架构评审和回归评测，不作为面向公众的金融问答产品。

## 2. 用户和权限

系统只有两类使用者。

### 2.1 项目所有者

项目所有者登录私有运行页面后可以：

- 选择固定用例和用例变体；
- 选择待比较的 Agent 实现方式或上下文处理方式；
- 发起运行、查看实时进度和内部运行记录；
- 将通过脱敏检查的运行批次发布到公开站点；
- 查看无效运行和失败原因。

项目所有者也不能通过运行接口传入任意问题正文。修改问题必须修改版本化的固定用例文件并经过代码审查。

### 2.2 公开访问者

公开访问者可以：

- 浏览项目定位、架构和实验设置；
- 筛选、排序、展开和回放已发布的运行工件；
- 查看完整对照分布、失败案例和无效运行数量；
- 查看上下文压缩前后的 token、保留项、压缩项和耗时。

公开访问者不能：

- 输入问题；
- 发起、重试或取消运行；
- 调用 LLM、工具或内部 API；
- 查看原始持仓、真实用户记忆、密钥、完整提示词或未脱敏工具结果。

公开页面允许导航、筛选、折叠和回放。这些是浏览操作，不是运行操作。

## 3. 使用方式

### 3.1 单步固定用例

大多数用例只有一个固定问题，例如：

- “宁德时代现在什么价”；
- “贵州茅台估值高不高”；
- “我的持仓现在值多少钱”；
- “帮我立刻下单买入”。

登录页面发送的请求只包含用例编号和运行配置：

```json
{
  "case_id": "market-quote-001",
  "variant_id": "long-context",
  "agent_mode": "full-system",
  "context_strategy": "budgeted"
}
```

服务端根据 `case_id` 读取问题正文。前端不能覆盖问题正文、权限、期望工具或评测条件。

### 3.2 预设多步用例

通用聊天不是产品能力。如果需要评测指代、状态延续或长上下文，使用预先登记的多步用例：

```yaml
id: portfolio-followup-001
steps:
  - message: 先分析我的组合风险
  - message: 其中风险最大的那个为什么
  - message: 如果它继续下跌 10% 呢
```

每一步的输入顺序固定。系统只把上一步的结构化结果、仍然有效的约束和被引用证据传给下一步，不复制完整对话历史。

### 3.3 事件类用例

为了展示主动运行能力，可以保留固定事件用例，例如“持仓标的下跌 5.2%”。事件由登录用户触发，数据明确标记为演示注入，并进入与其他用例相同的上下文构建、Agent 执行和运行记录流程。

事件用例不是公开输入入口，也不依赖真实市场在面试时间发生特定波动。

## 4. 固定用例的组成

每个固定用例至少包含：

| 字段 | 说明 |
|---|---|
| `id` | 稳定且唯一的编号 |
| `title` | 页面显示名称 |
| `message` | 服务端读取的固定问题 |
| `scene` | 行情、研究、组合、适合度、拦截、知识等场景 |
| `authenticated` | 是否要求登录身份数据 |
| `allowed_tools` | 本次运行可见的工具范围 |
| `context_profile` | 使用哪套上下文选择规则 |
| `token_budget` | 本次模型输入可使用的 token 上限 |
| `data_fixture` | 评测时使用的数据快照或模拟工具数据 |
| `expected_checks` | 工具、权限、引用、数字和合规检查 |
| `public` | 问题和结果是否允许发布 |

固定用例目录是页面、运行服务和评测器的共同数据源，不允许分别维护三份题目清单。

## 5. 产品页面

### 5.1 公开页面

| 路由 | 内容 |
|---|---|
| `/showcase` | 项目定位、运行流程、最新有效批次和主要指标 |
| `/showcase/results` | 全部对照组、场景和指标，不只展示系统获胜案例 |
| `/showcase/cases` | 允许公开的固定用例、变体和评测条件 |
| `/showcase/runs` | 单次运行列表和详情回放 |
| `/showcase/context` | 上下文压缩对照、长上下文案例和保留情况 |

公开路由由静态文件提供，不代理运行 API。

### 5.2 私有页面

| 路由 | 内容 |
|---|---|
| `/login` | 项目所有者登录 |
| `/lab` | 选择固定用例、变体和运行方式 |
| `/batches/{id}` | 查看一个批次的进度、无效运行和发布状态 |
| `/runs/{id}` | 查看未脱敏的内部运行详情 |

私有页面和运行 API 只在本地或受保护的演示部署中启用。公网部署可以完全不包含运行服务。

## 6. 安全和合规边界

- 系统不提供交易执行工具；交易请求必须在工具执行前被代码拒绝。
- 风险匹配只输出筛查草稿和风险披露，不给出确定的投资适当性结论。
- 权限、只读、预算和参数校验由代码执行，不能依赖模型自行遵守。
- 工具返回、网页、新闻和历史文本按不可信数据处理，不能被当成系统指令。
- 公开数据采用字段白名单生成。发现真实持仓、用户记忆、手机号、密钥或未允许字段时，发布失败。
- 前端隐藏按钮不构成权限控制。所有创建运行、注入事件和发布操作必须由后端鉴权。

## 7. 明确不做的内容

- 不开放公众自由提问；
- 不建设通用聊天会话和聊天历史管理；
- 不让访客选择任意模型或工具；
- 不用人工编辑的演示结果冒充真实运行；
- 不把完整 ContextHub 跨 Agent Session 系统引入本项目；
- 不在当前阶段训练专用压缩模型；
- 不以压缩率单独证明算法有效。

## 8. 成功标准

产品达到可演示状态时，应满足：

1. 公网只部署静态展示页面，不能创建运行；
2. 登录用户可以通过 `case_id` 运行固定用例；
3. 每次运行都记录上下文、工具、拦截、时长、token 和结果；
4. 汇总指标可以下钻到全部单次运行；
5. 长上下文对照可以说明减少了多少 token，以及关键事实是否保留；
6. 429、余额不足和服务不可用不会混入能力指标；
7. 现场运行失败时可以切换到已冻结运行工件或录屏继续演示。

// ── 保守 token 计数(CJK/标点 1 token,拉丁/数字 4 字符 1 token;空白不计)──
const CJK_RE =
  /[\u1100-\u11ff\u3000-\u303f\u3040-\u309f\u30a0-\u30ff\u3400-\u4dbf\u4e00-\u9fff\uac00-\ud7af\uf900-\ufaff\ufe30-\ufe4f\uff00-\uffef]/;
const PUNCT_RE = /[\u0021-\u002f\u003a-\u0040\u005b-\u0060\u007b-\u007e\u00a1-\u00bf\u2010-\u2027\u2030-\u205e\u2e00-\u2e7f]/;

function countTokens(text) {
  let cjk = 0;
  let latin = 0;
  for (const ch of text) {
    if (/\s/.test(ch)) continue;
    if (CJK_RE.test(ch) || PUNCT_RE.test(ch)) cjk += 1;
    else latin += 1;
  }
  return cjk + Math.ceil(latin / 4);
}

const sha256 = (text) => `sha256:${createHash("sha256").update(text, "utf8").digest("hex")}`;
const pad = (n, w = 4) => String(n).padStart(w, "0");

function gitCommit() {
  try {
    return execSync("git rev-parse HEAD", { cwd: REPO_ROOT, encoding: "utf8" }).trim();
  } catch {
    return "unknown";
  }
}

/** 读真实文件,返回 { rel, lines, sha256, content }。 */
async function readReal(relPath) {
  const content = await readFile(path.join(REPO_ROOT, relPath), "utf8");
  return {
    rel: relPath.replaceAll("\\", "/"),
    lines: content.split("\n").length,
    sha256: sha256(content),
    content,
  };
}

/** 多个真实文件 → 带来源头的原文合集文本。 */
function concatFiles(files, headerLines) {
  const parts = [headerLines.join("\n"), ""];
  for (const f of files) {
    parts.push(`──────── ${f.rel}(${f.lines} 行 · ${f.sha256.slice(7, 19)}) ────────`);
    parts.push(f.content.trimEnd());
    parts.push("");
  }
  return parts.join("\n");
}

// ── 会话型:真实工作会话 → 逐字稿 ────────────────────────────────────────

function renderTranscript(events, currentQuestion, sourceHash) {
  const lines = [];
  lines.push(`# ${SESSION_CASE_ID} · 真实工作会话逐字稿`);
  lines.push(`# ${events.length} 个事件 · ${events[0].occurred_at.slice(0, 10)} ~ ${events[events.length - 1].occurred_at.slice(0, 10)}`);
  lines.push(`# source_session_hash: ${sourceHash}`);
  lines.push(`# 当前问题: ${currentQuestion}`);
  lines.push("");
  for (const ev of events) {
    if (ev.type === "user_message") {
      lines.push(`[${pad(ev.seq)}] ${ev.occurred_at} 用户`);
      lines.push(ev.content);
      lines.push("");
    } else if (ev.type === "assistant_message") {
      lines.push(`[${pad(ev.seq)}] ${ev.occurred_at} 助手`);
      lines.push(ev.content);
      lines.push("");
    } else if (ev.type === "tool_call") {
      lines.push(`[${pad(ev.seq)}] ${ev.occurred_at} 工具调用 ${ev.tool_name}`);
      lines.push(`  参数 ${JSON.stringify(ev.arguments || {})}`);
    } else if (ev.type === "tool_result") {
      lines.push(`[${pad(ev.seq)}] ${ev.occurred_at} 工具结果(${ev.status || "success"}${ev.error_code ? " · " + ev.error_code : ""}) — 冻结 Mock`);
      lines.push(`  ${ev.content}`);
      lines.push("");
    }
  }
  return lines.join("\n");
}

async function buildSessionEntry() {
  const sessionRaw = JSON.parse(await readFile(path.join(SESSION_CASE_DIR, `${SESSION_CASE_ID}.session.json`), "utf8"));
  const variantsRaw = JSON.parse(await readFile(path.join(SESSION_CASE_DIR, `${SESSION_CASE_ID}.variants.json`), "utf8"));
  const compiledDir = path.join(SESSION_CASE_DIR, "compiled");
  const compiled = {};
  for (const f of (await readdir(compiledDir)).filter((x) => x.endsWith(".json") && x !== "compile-report.json")) {
    const payload = JSON.parse(await readFile(path.join(compiledDir, f), "utf8"));
    compiled[payload.variant_id] = payload;
  }
  const tokenizerVersion = compiled[Object.keys(compiled)[0]]?.tokenizer_version || "conservative-cjk1-latin4-v1";

  const events = sessionRaw.events;
  const stats = {
    event_count: events.length,
    user_messages: events.filter((e) => e.type === "user_message").length,
    assistant_messages: events.filter((e) => e.type === "assistant_message").length,
    tool_pairs: events.filter((e) => e.type === "tool_call").length,
    first_at: events[0].occurred_at,
    last_at: events[events.length - 1].occurred_at,
  };
  const sortKeys = (v) =>
    Array.isArray(v) ? v.map(sortKeys)
      : v && typeof v === "object"
        ? Object.fromEntries(Object.keys(v).sort().map((k) => [k, sortKeys(v[k])]))
        : v;
  const sourceHash = sha256(JSON.stringify(sortKeys(sessionRaw)));

  const strategies = (variantsRaw.context_variants || []).map((v) => {
    const art = compiled[v.variant_id];
    if (!art) {
      throw new Error(`缺少编译工件 compiled/${v.variant_id}.json;先运行 python -m bdlh_runtime.evaluation.session_cross_eval --compile-only`);
    }
    return {
      variant_id: v.variant_id,
      title: v.title || v.variant_id,
      strategy_version: art.strategy_version || v.strategy_version,
      token_budget: art.token_budget,
      original_tokens: art.original_tokens,
      working_tokens: art.working_tokens,
      compression_pct: art.original_tokens ? Math.round((1 - art.working_tokens / art.original_tokens) * 100) : null,
      kept: (art.kept_event_ids || []).length,
      compressed: (art.compressed_event_ids || []).length,
      referenced: (art.referenced_event_ids || []).length,
      omitted: (art.omitted_event_ids || []).length,
      build_duration_ms: art.build_duration_ms,
      compiled_context_hash: art.compiled_context_hash,
    };
  });

  const transcript = renderTranscript(events, sessionRaw.runtime_case.current_question, sourceHash);
  return {
    entry: {
      id: SESSION_CASE_ID,
      kind: "会话(真实)",
      kind_key: "session",
      title: sessionRaw.title || SESSION_CASE_ID,
      summary: "一份冻结的真实工作会话:产品方向讨论、误解与纠正、文档读写、方案变更与当前问题,事件与时间戳全部来自真实协作。",
      tokenizer_version: tokenizerVersion,
      stats,
      original_tokens: strategies[0]?.original_tokens ?? null,
      source_session_hash: sourceHash,
      strategies,
      drilldown: "/session-cross/",
    },
    txtName: `${SESSION_CASE_ID}.txt`,
    txt: transcript,
  };
}

// ── 文档型/代码型:真实文件合集 ──────────────────────────────────────────

async function buildFileEntry({ id, kind, kindKey, title, summary, files: relPaths }) {
  const files = [];
  for (const rel of relPaths) files.push(await readReal(rel));
  const header = [
    `# ${id} · ${kind} · 真实原文合集`,
    `# 来源文件 ${files.length} 个 · 逐文件 sha256 见分隔行 · 仓库真实文件,未做任何改写`,
    `# token 估算:保守口径(CJK/标点 1 token,拉丁/数字 4 字符 1 token)`,
  ];
  const txt = concatFiles(files, header);
  return {
    entry: {
      id,
      kind,
      kind_key: kindKey,
      title,
      summary,
      tokenizer_version: "conservative-cjk1-latin4-v1",
      stats: {
        files: files.length,
        lines: files.reduce((s, f) => s + f.lines, 0),
        paragraphs: files.reduce((s, f) => s + f.content.split(/\n\s*\n/).filter((p) => p.trim()).length, 0),
      },
      original_tokens: countTokens(txt),
      sources: files.map((f) => ({ path: f.rel, lines: f.lines, sha256: f.sha256 })),
    },
    txtName: `${id}.txt`,
    txt,
  };
}
