# 数据库总体设计

> 状态：数据库设计与手动执行依据  
> 可执行 SQL：`db/postgresql/setup/` 和 `db/postgresql/changes/`

## 1. 设计目标

PostgreSQL 是私有运行环境的事实记录中心。数据库需要完整回答以下问题：

- 运行的是哪一道固定用例、哪个版本和哪个数据变体；
- 对照的是哪种 Agent 实现、哪种上下文策略和哪个代码版本；
- 原始上下文是什么，哪些内容被保留、压缩、引用或省略；
- 模型和工具分别调用了几次，每次用了多少 token 和时间；
- 本次运行为什么成功、失败或无效；
- 网页上的一个数字来自哪个批次和哪些单次运行。

数据库不负责执行 Agent，不负责决定上下文，也不直接给公开网页提供数据。公开网页只读取发布脚本生成的静态 JSON。

## 2. 数据库边界

### 2.1 PostgreSQL 保存什么

- 固定用例、不可变用例版本和用例变体；
- 固定长上下文和模拟工具返回；
- 每次运行使用的冻结数据快照；
- Agent 实现版本和上下文策略版本；
- 实验批次、单次运行、模型调用和工具调用；
- 原始上下文条目、压缩决定和实际模型消息；
- token、成本、分阶段耗时和评测指标；
- 内部运行记录与公开静态工件之间的发布关系。

### 2.2 PostgreSQL 不保存什么

- 模型隐藏思维过程；
- 密钥、数据库密码和完整认证令牌；
- 真实用户的长期聊天历史；
- 公开网页的运行时会话；
- 大型录屏、完整网页原文和超大工具响应正文。

大文本和二进制文件放对象存储或本地工件目录。数据库只保存内容摘要、存储位置和 hash。建议单字段超过 256 KB 时使用外部存储，避免数据库备份和查询被少数大字段拖慢。

账号密码只保存加盐 hash（bcrypt/argon2），登录会话只保存令牌的 `sha256:<hex>` hash。明文密码和完整会话令牌不进入数据库，也不进入 Git。

## 3. 是否需要向量数据库

当前版本不需要 `pgvector`，原因是：

1. 问题由固定用例指定，不需要从大量用户输入中寻找相似问题；
2. 长上下文也是固定数据集，测试必须可重复，不能让召回结果随索引变化；
3. 当前比较重点是 Agent 实现和上下文压缩，不是语义检索质量；
4. 普通 PostgreSQL 已经能完成版本、来源、hash、运行记录和网页聚合查询。

如果以后新增“检索算法对照实验”，再把向量检索作为一种可选策略。届时必须同时保存嵌入模型版本、切分规则版本、向量索引参数和实际召回条目，不能只保存最终摘要。

## 4. 数据关系

```text
case_definitions
    └─ case_versions
        ├─ case_steps
        └─ case_variants
            ├─ case_variant_fixtures ── fixture_sets
            │                            ├─ fixture_context_items
            │                            └─ fixture_tool_responses
            └─ data_snapshots

agent_implementations ── agent_versions ─┐
                                         ├─ agent_runs ── context_builds
context_strategy_versions ───────────────┤      │          ├─ context_items
                                         │      │          ├─ context_decisions
run_batches ─────────────────────────────┘      │          └─ context_messages
                                                ├─ model_calls ── model_call_messages
                                                ├─ tool_calls
                                                ├─ guardrail_checks
                                                ├─ run_events
                                                ├─ run_measurements
                                                ├─ evaluation_results
                                                ├─ evaluation_metrics
                                                └─ run_artifacts

run_batches ── publications ── publication_runs ── agent_runs

accounts ── auth_sessions
accounts ── audit_log

tool_operations ─┐
toolsets ────────┼─ tool_capabilities
tool_skills ─────┘
```

关系设计遵循三个原则：

- 配置有版本，历史运行只引用确定版本；
- 运行输入先冻结成快照，运行后不能覆盖；
- 高频查询字段使用普通列，结构不稳定的详细说明使用 JSONB。

## 5. 表分组

### 5.1 固定用例

| 表 | 用途 | 关键字段 |
|---|---|---|
| `case_definitions` | 用例主记录 | `id`、标题、状态、当前版本 |
| `case_versions` | 不可变的问题和规则版本 | 问题、场景、权限、允许工具、token 预算、评测条件 |
| `case_variants` | 同一问题的不同输入条件 | 上下文策略、数据定义、是否公开 |
| `case_steps` | 预设多步用例 | 步骤顺序、固定消息、预期检查 |

修改问题正文、工具范围或评测条件时必须新增 `case_versions.version`，不能直接覆盖旧版本。`current_version` 只表示新运行默认使用哪个版本。

### 5.2 固定数据和长上下文

| 表 | 用途 | 关键字段 |
|---|---|---|
| `fixture_sets` | 一组固定测试数据的版本 | 编号、版本、类型、来源 hash、采集时间 |
| `fixture_context_items` | 长上下文中的独立信息 | 类型、分类、正文或引用、来源、时间、优先级、token |
| `fixture_tool_responses` | 固定工具请求和返回 | 工具名、参数 hash、固定返回、状态、模拟耗时 |
| `case_variant_fixtures` | 用例变体使用哪些固定数据 | 用例变体、用途、数据集版本 |
| `data_snapshots` | 一次运行真正使用的冻结输入 | 用例版本、变体、数据内容、来源 hash |

`fixture_sets` 是可复用的测试数据定义，`data_snapshots` 是某次运行的输入证据。即使多个运行使用同一个数据集，也必须让运行引用明确的快照。

上下文条目分类使用现有四种普通状态：

- `required`：安全规则、固定问题、权限和关键事实，必须保留；
- `compressible`：可以结构化压缩或摘要；
- `reference_only`：正文不进入模型，只保留内部引用；
- `distractor`：专门用于验证无关信息过滤能力。

### 5.3 实验配置

| 表 | 用途 | 关键字段 |
|---|---|---|
| `agent_implementations` | 三种 Agent 实现的稳定编号 | 实现类型、名称、状态 |
| `agent_versions` | 实现的可运行版本 | 入口、提示词版本、工具目录版本、运行配置 |
| `context_strategy_versions` | 上下文算法的可运行版本 | 策略类型、算法版本、tokenizer 版本、配置 |

首批 Agent 编号固定为：

- `baseline-tool-calling`：直接 Tool Calling；
- `langgraph-react`：LangGraph ReAct；
- `full-system`：完整工程实现。

首批上下文策略编号固定为：

- `full`：完整上下文；
- `recent-n`：固定窗口；
- `single-summary`：一次性摘要；
- `budgeted`：按预算选择和压缩。

“实现名称”和“版本”必须分开。展示名称可以调整，但运行引用的编号和版本不能随意修改。

### 5.4 批次和运行

| 表 | 用途 | 关键字段 |
|---|---|---|
| `run_batches` | 一组公平对照实验 | 唯一变量、固定条件、重复次数、随机种子、状态 |
| `agent_runs` | 一次独立 Agent 运行 | 用例、快照、Agent 版本、上下文策略版本、模型、Git commit |
| `run_events` | 可观察的运行时间线 | 顺序、事件类型、事件正文、发生时间 |

Agent 对照批次的 `experiment_variable` 使用 `AGENT_IMPLEMENTATION`；上下文策略对照使用 `CONTEXT_STRATEGY`。同一个批次只能改变这一项，其余条件放在 `fixed_conditions` 中冻结。

批次和运行都支持 `idempotency_key`。网络重试时使用相同键，避免重复运行和重复产生模型费用。

### 5.5 上下文处理

| 表 | 用途 | 关键字段 |
|---|---|---|
| `context_builds` | 一次上下文构建总结果 | 策略、算法版本、token 预算、压缩 token、耗时、校验结果 |
| `context_items` | 本次构建收到的原始候选信息 | 内容、来源、分类、优先级、原始 token、hash |
| `context_decisions` | 每条信息的处理决定 | 保留、压缩、引用、省略或隔离，以及原因 |
| `context_messages` | 最终发送给模型的消息 | 顺序、角色、正文、token、hash |

固定数据中的 `fixture_context_items` 与运行中的 `context_items` 不能合并。前者描述测试数据定义，后者证明某次运行实际收到了什么。

压缩后内容保存在 `context_decisions.output_content`，原始内容保存在 `context_items.content` 或 `content_ref`。这样网页可以展示压缩前后 token 和处理理由，内部也能复查关键事实是否丢失。

### 5.6 模型、工具、耗时和成本

| 表 | 用途 | 关键字段 |
|---|---|---|
| `model_calls` | 每一次模型请求 | 用途、模型、输入输出 hash、token、耗时、重试、错误 |
| `model_call_messages` | 每次模型调用实际收到的输入消息 | 顺序、角色、正文或引用、token、hash |
| `tool_calls` | 每一次工具执行 | 工具名、参数、结果摘要、来源时间、耗时、审计码 |
| `guardrail_checks` | 代码守卫检查明细 | 时点、决定、审计码、规则、理由、关联调用 |
| `run_measurements` | 网页和报告需要的汇总指标 | 分阶段耗时、token、成本、计价快照 |

`model_calls.purpose` 区分主 Agent、上下文压缩和评测调用。压缩算法如果调用模型，必须计入 `COMPRESSION`，不能只统计主 Agent 的 token。

`model_call_messages` 记录每次模型调用实际收到的消息快照。首轮近似等于 `context_messages`，后续轮次在其上追加了工具结果；大消息正文通过 `content_ref` 引用对象存储，数据库只保存引用和 hash。

`guardrail_checks` 记录 plan、action、data_quality、response 四个时点的守卫决定。拦截（block、modify、ask_user）必须记录稳定 `audit_code` 和理由，放行可按审计需求记录，便于网页展示工具被代码拒绝或修正的完整原因。

`run_measurements` 一次运行一行，适合计算 p50、p95 和最大值。模型价格会变化，因此除计算结果外还要保存 `pricing_snapshot`，避免以后用新价格重算出不同历史结果。

### 5.7 评测和发布

| 表 | 用途 | 关键字段 |
|---|---|---|
| `evaluation_results` | 完整评测结果 | 评测器版本、运行是否有效、检查详情、完整指标 |
| `evaluation_metrics` | 可直接聚合的指标 | 指标名、数值、是否通过、单位 |
| `run_artifacts` | 内部原始工件的位置 | 类型、存储位置、hash、是否允许发布 |
| `publications` | 一次公开数据生成记录 | 批次、版本、字段规则版本、状态、公开索引 hash |
| `publication_runs` | 公开工件与内部运行的对应关系 | 运行编号、公开文件位置、公开内容 hash |

`PUBLISHED` 只表示脱敏和完整性检查已经通过。公开站仍然只部署 `web/public/showcase-data/`，不允许连接数据库。

### 5.8 登录和审计

| 表 | 用途 | 关键字段 |
|---|---|---|
| `accounts` | 项目所有者账号 | 用户名、显示名、密码 hash、状态、失败次数、锁定 |
| `auth_sessions` | 登录会话 | 账号、令牌 hash、过期、撤销、来源 IP 和 UA |
| `audit_log` | 登录和关键操作审计 | 账号、动作、成败、详情、IP、时间 |

产品只有「项目所有者」一类登录用户，`accounts` 通常只有极少数账号。密码只保存加盐
hash，会话只保存令牌的 `sha256:<hex>` hash，公开站不持有任何账号或会话数据。

`run_batches.created_by` 保存发起者用户名，与 `accounts.username` 对应，用于把批次和
运行追溯到具体账号；登录成败和关键操作（创建运行、发布等）写入 `audit_log`。

### 5.9 工具目录

| 表 | 用途 | 关键字段 |
|---|---|---|
| `tool_operations` | 操作证目录 | 编号、说明 |
| `toolsets` | 工具集目录 | 名称、说明 |
| `tool_capabilities` | 工具能力登记（唯一真源） | 适配器、是否需登录、必填参数、依赖、操作证、工具集 |
| `tool_skills` | 技能（能力与操作证分组） | 版本、状态、启用 |
| `tool_skill_operations` | 技能关联的操作证 | 操作证、是否必选 |
| `tool_skill_capabilities` | 技能关联的工具能力 | 能力名、是否必选 |

工具目录是装载器、检索索引和治理中间件的共同数据源。engine 经 data 服务
`/internal/v1/tool-catalog` 读取目录，不在代码里维护第二份清单（测试替身由
seed 同步测试守卫）。工具面向模型的双目的描述与参数 JSON Schema 仍由代码层
投影（`tools/catalog.py`），数据库保存的 description 是运维文案。

## 6. JSONB 使用规则

以下内容适合使用普通列：

- 用例编号、版本、状态；
- Agent 和策略编号；
- token、成本、耗时；
- 工具名、事件顺序、hash；
- 需要筛选、排序、分组或建立外键的字段。

以下内容适合使用 JSONB：

- 不同场景结构不同的数据快照；
- 模型或策略的少量可选配置；
- 工具参数和结构化结果摘要；
- 完整评测检查明细；
- 发布规则和计价快照。

不要把所有内容放进一个 `payload` 字段。网页需要经常筛选和聚合的字段必须有固定列。

## 7. 时间、token 和 hash

- 所有时间使用 `TIMESTAMPTZ`，服务端统一以 UTC 写入，页面按用户时区显示；
- 所有耗时统一使用毫秒，字段名以 `_ms` 结尾；
- token 必须记录 tokenizer 或模型版本，不允许只有一个脱离版本的数字；
- 内容 hash 统一采用 `sha256:<hex>` 格式；
- 同一份 JSON 计算 hash 前必须进行稳定序列化，字段顺序不能影响结果；
- `created_at` 表示数据库写入时间，`observed_at` 或 `source_time` 表示数据本身的时间，两者不能混用。

## 8. 正反例

### 8.1 正例：用新版本保存修改后的题目

```text
case_definitions.id = portfolio-value-001
case_versions        = version 3（历史运行继续引用）
                     + version 4（新问题或新规则）
case_definitions.current_version = 4
```

这样旧运行仍能精确还原。

### 8.2 反例：直接更新历史问题

```sql
UPDATE touchstone.case_versions
SET message = '新问题'
WHERE case_id = 'portfolio-value-001' AND version = 3;
```

这会让历史运行记录指向被改写的输入，禁止这样操作。

### 8.3 正例：压缩调用也记录成本

主 Agent 调用写入一条 `model_calls(purpose='AGENT')`，摘要模型调用写入一条 `model_calls(purpose='COMPRESSION')`，两者共同汇总到 `run_measurements`。

### 8.4 反例：只保存最终答案

只保存最终答案无法解释工具选择、关键事实是否进入上下文、失败发生在哪个阶段，也无法证明网页数据。因此单次运行必须至少保存快照、上下文构建、模型/工具调用、评测和汇总指标。

### 8.5 正例：大文本使用引用

数据库保存 `content_ref`、内容 hash、字符数、token 数和安全摘要；正文放受控对象存储。

### 8.6 反例：把整篇网页和录屏写入 JSONB

这样会放大数据库、备份、复制和查询成本，也会增加敏感信息泄漏范围。

## 9. 常用查询

按 Agent 实现计算有效运行总时长的 p50 和 p95：

```sql
SELECT r.agent_id,
       percentile_cont(0.50) WITHIN GROUP (ORDER BY m.total_duration_ms) AS p50_ms,
       percentile_cont(0.95) WITHIN GROUP (ORDER BY m.total_duration_ms) AS p95_ms
FROM touchstone.agent_runs r
JOIN touchstone.run_measurements m ON m.run_id = r.id
JOIN touchstone.evaluation_results e ON e.run_id = r.id
WHERE r.batch_id = :batch_id
  AND e.valid_run = true
GROUP BY r.agent_id;
```

检查压缩后是否仍有强制项被省略：

```sql
SELECT b.run_id, i.item_key, d.action
FROM touchstone.context_builds b
JOIN touchstone.context_items i ON i.context_build_id = b.id
JOIN touchstone.context_decisions d
  ON d.context_build_id = b.id AND d.item_key = i.item_key
WHERE i.classification = 'required'
  AND d.action NOT IN ('kept', 'compressed', 'isolated');
```

追踪公开页面中的一条运行记录：

```sql
SELECT p.batch_id, pr.run_id, pr.public_storage_ref, pr.public_content_hash
FROM touchstone.publications p
JOIN touchstone.publication_runs pr ON pr.publication_id = p.id
WHERE p.status = 'PUBLISHED' AND pr.run_id = :run_id;
```

## 10. 数据保留和删除

- 固定用例版本、数据集版本和已发布批次默认长期保留；
- 失败和无效运行至少保留到问题复盘结束，不能为了提高成功率删除；
- 临时未发布批次可以按环境配置保留 30～90 天；
- 删除批次前先检查是否存在 `publications` 引用；
- 对象存储文件必须通过 `run_artifacts` 或公开工件引用计数后再清理；
- 数据清理使用后台任务分批进行，不能在公开请求中执行大范围级联删除。

## 11. 手动执行和变更

新数据库按 `db/postgresql/setup/` 中的编号顺序手动初始化。应用启动不读取 SQL，
Data 服务也不具有建表或改表职责。

执行规则：

1. 新数据库依次执行 `01`、`02`、`03`、`04`；
2. 每份脚本在独立事务中执行，错误时整体回滚；
3. 成功脚本写入 `touchstone.database_changes`；
4. 数据库投入使用后的修改放入 `db/postgresql/changes/`；
5. 已经在任一环境成功执行的脚本不能修改；
6. 正式环境执行前先备份，并确认目标数据库；
7. 结构变更需要停服务时，必须在变更文件说明中明确写出。

具体命令见 [`../postgresql/setup/README.md`](../postgresql/setup/README.md)。

## 12. 验收标准

1. 同一个运行可以还原用例、数据、Agent、上下文策略、模型和代码版本；
2. 每条压缩决定可以定位到原始上下文和压缩后内容；
3. 主 Agent、压缩和评测模型调用分别计数；
4. 工具调用可以看到参数 hash、来源、耗时、模拟数据命中和错误；
5. p50、p95、token、成本和成功率可以直接从数据库回算；
6. 网络重试不会创建重复计费运行；
7. 公开工件可以追溯到内部运行，但公开站不连接数据库；
8. 基础设计不依赖向量扩展；
9. PostgreSQL 初始化脚本可按顺序在空库中手动执行完成；
10. 数据表和代码使用同一套 Agent 与上下文策略编号；
11. 所有者登录凭据只以加盐 hash 保存，会话只保存令牌 hash，仓库不含明文凭证。

# 部署

## 本地原生启动（不走 Docker）

本地开发只做原生进程互访（隧道 → data 18081 → engine 8090 → web 8082），
镜像构建/推送在云服务器执行。模块、环境变量、端口与排查见
[`本地启动说明.md`](./本地启动说明.md)。

## 密钥管理

- `deploy/.env` 只在本机使用，已被 `.gitignore` 覆盖，**永不提交**；真实密钥
  （数据库密码、`DATA_INTERNAL_TOKEN`、`LLM_API_KEY`）建议从密码管理器取出后
  现场注入，不在工作区长期明文存放；
- 云环境密钥走托管平台的 secret 注入，不写进镜像、compose 文件或命令记录；
- 任何密钥疑似泄漏（误提交、打包、录屏、共享）立即轮换：`LLM_API_KEY` 在厂商
  控制台重置；`POSTGRES_PASSWORD` 与 `DATA_INTERNAL_TOKEN` 轮换时需同步更新
  data 与 engine 两侧环境后滚动重启；
- `.env.example` / `.env.ci` 只允许占位值。

## 本地完整环境

包含 PostgreSQL、`data`、`engine` 和 `web`：

```powershell
Copy-Item deploy/.env.example deploy/.env
docker compose --env-file deploy/.env -f deploy/docker-compose.yml up -d postgres
```

第一次部署时，按照 [`db/postgresql/setup/README.md`](../db/postgresql/setup/README.md)
手动执行数据库初始化脚本 `init.sql`（单一入口，含全部建表与种子数据）。
数据库准备完成后再启动应用：

```powershell
docker compose --env-file deploy/.env -f deploy/docker-compose.yml up -d --build data engine web
```

Engine 端口默认只绑定 `127.0.0.1`。如果通过网关提供私有运行页面，网关仍需做项目所有者登录；运行接口本身已要求账号会话令牌，不应暴露给浏览器或公开站。

## 云环境

`docker-compose.cloud.yml` 使用已经发布的三个镜像，并连接托管 PostgreSQL。先使用
`psql` 按 [`db/postgresql/setup/README.md`](../db/postgresql/setup/README.md) 初始化托管数据库，
然后启动服务：

```powershell
docker compose --env-file deploy/.env.cloud -f deploy/docker-compose.cloud.yml up -d
```

云环境需要设置 `IMAGE_REGISTRY`、`IMAGE_TAG`、`DATABASE_URL`、`DATABASE_USER`、`DATABASE_PASSWORD`、`DATA_INTERNAL_TOKEN`、`LLM_API_KEY` 和 `GIT_COMMIT`。数据服务和运行服务应放在私有网络；只让展示站或经过登录保护的反向代理暴露公网端口。

**TLS 强制要求**：云端 web 默认 `CONSOLE_BIND=0.0.0.0` 提供的是明文 HTTP，公网流量
必须在网关/负载均衡终止 TLS 后再转发到该端口。不要把 `CONSOLE_PORT` 的明文端口
直接暴露到公网；网关需配置证书并强制 HTTP→HTTPS 跳转。

    public void completeBatch(UUID batchId, CompleteBatchRequest request) {
        if (!List.of("COMPLETE", "FAILED", "CANCELLED").contains(request.status())) {
            throw new IllegalArgumentException("invalid terminal batch status: " + request.status());
        }
        int updated = jdbc.update(

                       compression_input_tokens, compression_output_tokens
                FROM touchstone.run_measurements WHERE run_id = ?
                """,
                runId));
        run.put("artifacts", jdbc.queryForList(
                """
                SELECT artifact_type, storage_ref, content_hash, "public", created_at
                FROM touchstone.run_artifacts WHERE run_id = ?
                """,
                runId));
        return run;
    }

    private String json(JsonNode node) {
        try {
            return objectMapper.writeValueAsString(node);
        } catch (JsonProcessingException exception) {
            throw new IllegalArgumentException("payload is not valid JSON", exception);
        }
    }

    private String jsonOrEmpty(JsonNode node) {
        return node == null ? "{}" : json(node);
    }

    private String jsonOrNull(JsonNode node) {
        return node == null ? "null" : json(node);
    }

    private String jsonOr(JsonNode node, String fallback) {
        return node == null ? fallback : json(node);
    }
