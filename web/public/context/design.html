长短对照设计 · 上下文压缩

六套用例 × 两条变体

方向覆盖金融 3(组合诊断 / 估值口径 / 新闻去重)+ 其他 2(出行天气 / 长文档手册)+ 闲聊 1(长历史)。每套两条变体挂同一份上下文条目,只变处理策略:

  • full-raw:全量透传(大预算);
  • budgeted-comp:按预算压缩(小预算)。

条目数据在库(changes/20260821-long-context-cases.sql,批量条目由确定性生成,有业务含义),执行时经数据服务读取,运行记录关联真实变体与快照;条目元信息与原文下载见长上下文库。

上下文断言

与编排对照同一 Agent 逻辑、同一冻结工具数据、同一判官之外,压缩对照新增四类断言:

  • required 保留率 100%(构建报告逐条核对);
  • required_facts 出现:关键事实取值必须出现在构建后的工作上下文;
  • forbidden_facts 不入答案:过期/旧口径取值不得出现在最终答案;
  • 注入隔离:untrusted 条目不在指令区且被包裹(或被整体隔离)。

联动对照(压缩质量 × 实现方式)

压缩对照只换上下文处理策略、Agent 实现固定为完整工程模式;要回答「压缩后的内容到底好不好」,可发起联动对照:同一套长上下文的原始内容(full-raw)与压缩内容(budgeted-comp)分别过三种实现方式(裸 tool calling / LangGraph ReAct / 完整工程模式),得到 2 变体 × 3 组共 6 格对照——若压缩格在工具选择、关键事实召回、禁用事实泄漏上不劣于原始格,压缩即是划算的。登录后在运行台或长上下文库发起;结果口径见用例结果。

如何发起

登录后进入运行台:「压缩对照批次」或「联动对照(三组 × 两变体)」按钮,或 CLI python -m bdlh_runtime.evaluation.context_eval:六套 × 两变体 × N 次;每变体运行产出九段工件与 context_builds 处理报告(条目/决策/消息级)。结果见用例结果。
